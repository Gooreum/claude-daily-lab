## 1. Anthropic이 자체 버전 관리 시스템 Scion을 만들었다 — 하루 병합 3만 건, 체크아웃 2,500만 건을 대부분 에이전트가 요청해서 git 미러가 감당이 안 됐다
- 날짜: 2026-10-19
- 출처: https://www.anthropic.com/engineering/redesigning-source-control
- 요약: 모노레포의 하루 병합이 5월 약 2,500건에서 9월 3만 건 이상으로 늘고, main 이력이 약 100GB에 하루 체크아웃이 약 2,500만 건(거의 전부 항상 온라인인 에이전트·CI)이라 git의 "전체 복제본" 모델과 미러 운영이 병목이 됐다. 일곱 명이 다섯 달 만에 서버가 이력·병합을 맡고 클라이언트는 필요한 파일만 받는 Scion으로 옮겼고, 인프라 CPU·메모리는 미러의 약 200분의 1, 체크아웃은 분 단위에서 초 단위가 됐다. 글은 Scion이 범용 git 대체가 아니며 공개 제품도 아니라고 밝히고, 병합 큐의 전역 락을 병합 후 테스트로 바꾼 점과 엔지니어의 일이 "아니오"를 말하는 설계 제약·의도 리뷰로 옮겨 갔다는 점을 교훈으로 든다.
- 현실 적용:
  - 에이전트가 하루 수십 번 `git clone`하는 CI를 가진 팀 → 체크아웃 단계에 `--depth 1 --filter=blob:none`(부분 복제)을 넣고 전후 시간을 잡 로그로 비교한다 → 전체 복제본이 필요 없는 잡의 대기 시간을 오늘 줄인다
  - 에이전트 PR이 몰려 병합 큐가 막히는 저장소 → 큐 전체에 거는 잠금 대신 병합 후 스모크 테스트와 배포 전 검사로 나눈 안을 한 페이지로 써서 팀에 올린다 → 병합 처리량 병목이 어디인지 숫자(큐 대기 분)로 논의한다
  - 에이전트가 읽기만 하는 잡이 많은 플랫폼팀 → 저장소 정보 조회(blame, 경로 이력)를 로컬 클론이 아니라 GitHub API로 하게 바꾼 잡을 하나 골라 시험한다 → 클론 없이 끝나는 잡이 늘어 러너 디스크·네트워크 비용이 준다
  - 이 저장소의 daily-lab 워크플로 → `actions/checkout`의 `fetch-depth`를 1로 줄일 수 있는지 `git log` 의존 단계를 grep으로 확인한다 → 매일 06:45 실행의 체크아웃 시간을 줄인다
  - 시스템 설계 글을 읽고 스터디하는 개인 개발자 → 글의 "변경 집합 + 파생 데이터(blame을 부모 값에서 계산)" 구조를 100줄짜리 파이썬 장난감으로 따라 만든다 → 서버 중심 VCS의 사고방식을 손으로 익힌다

## 2. Claude Code 2.1.304 — 모드 훅이 "사람만 승인" 표시를 받고, Code Review에 Quick·Standard·Deep 단계가 생기고, 스킬 훅에 상한이 붙는다
- 날짜: 2026-10-19
- 출처: https://code.claude.com/docs/en/changelog
- 요약: 모드의 `tool.check` 답에 `decider: "person"`이 생겨 권한 대화상자나 호스트 콜백만 승인할 수 있고, 이 이벤트에 `e.isReadOnly`도 붙는다. 스킬 훅은 세션당 소스마다 1,024개와 매처 글자 16,384자로 제한되고, `settings.read` 훅은 레이어별 설정을 받아 합쳐진 설정을 고쳐 쓸 수 있다. Code Review는 조직·저장소별로 Quick/Standard(기본)/Deep을 고르고 조직 전체 저장소(나중에 추가된 것 포함)를 한 번에 켤 수 있다. 버그 수정 중에는 PreToolUse 거부 사유가 타임아웃 오류로 덮이던 문제, `--max-turns`·Stop 이후에도 플러그인이 헤드리스 실행을 붙잡던 문제, `rm -r` 안전 프롬프트 누락이 있다. SDK(TypeScript)는 v0.3.304로 같이 나왔다.
- 현실 적용:
  - 훅 거부 사유를 로그에 의존하는 개인 개발자 → 2.1.303 이하에서 "타임아웃 오류"로 보이던 거부 사유 로그를 모아 2.1.304로 올린 뒤 같은 입력을 다시 흘려 본다 → 막힌 이유가 정확히 남는 훅 로그로 바뀐 것을 확인한다
  - 코드 리뷰 비용을 줄이고 싶은 팀 → 문서·설정 위주 저장소는 Quick, 결제 코드 저장소는 Deep으로 저장소별 단계를 나눠 켠다 → 리뷰 시간과 비용을 위험도에 맞춘다
  - 플러그인으로 헤드리스 배치를 돌리는 사람 → `claude -p --max-turns 3`로 플러그인을 켠 상태에서 한 번 돌려 정말 3턴에서 끝나는지 시간을 잰다 → 플러그인이 프로세스를 붙잡아 CI가 멈추는 일을 확인·종료한다
  - 스킬을 많이 만든 팀의 플랫폼 담당 → 스킬별 훅 개수와 매처 글자 수를 세는 스크립트로 1,024개·16,384자 상한 대비 여유를 표로 만든다 → 상한 때문에 조용히 훅이 잘리는 날을 미리 피한다
  - 이 저장소의 `mod-audit`·`hook-exit-audit` → 2.1.304의 `decider: "person"`과 `isReadOnly`를 점검 규칙(사람 승인 우회 가능성)으로 추가하는 이슈를 남긴다 → 새 모드 API가 감사 도구에서 빠지는 일을 막는다

## 3. 아무도 안 보는 루프 하나가 밤새 구독 한도 13%를 태웠다 — 종료 조건이 없었고, 방어는 "연속 실패 3 · 호출 200 · 3시간" 세 상한이다
- 날짜: 2026-10-19
- 출처: https://dev.to/sungwoo_lee_e0f26be4a29fd/one-unattended-claude-loop-burned-13-points-of-plan-usage-215d
- 요약: 글쓴이는 종료 조건이 없는 LLM 루프를 밤새 돌렸다가 구독 사용량 13퍼센트포인트를 쓴 사고를 정리한다. 더 싼 모델로 바꿔도 루프가 안 끝나는 건 같고 느리게 태울 뿐이라는 것이 요지다. 모든 무인 루프에 코드로 강제하고 테스트한 상한을 둘 이상 두라며 연속 실패 3회, 총 호출 200회, 경과 3시간을 예로 든다. 429 대기는 상한이 아니라 다음 한도 창에서 루프를 되살리고, 종료 시 멈춘 이유와 사용량을 기록해야 한다.
- 현실 적용:
  - 퇴근 전 `while true`로 Claude를 돌려 두는 개인 개발자 → 호출 횟수·연속 실패·경과 시간을 세는 래퍼를 앞에 씌운다 → 종료 조건을 깜빡해도 3시간 안에 코드가 끊는다
  - 야간 Routine·cron을 여러 개 가진 사람 → 래퍼가 멈춘 이유(`max_calls`·`max_failures`·`max_hours`)를 JSONL 한 줄로 남기게 하고 아침에 `tail`로 읽는다 → 어느 작업이 왜 멈췄는지 로그를 열지 않고 안다
  - 구독 한도를 팀이 공유하는 조직 → 무인 작업 목록(스크립트 경로·상한 값)을 표로 만들어 월 1회 검토한다 → 상한 없는 작업이 몰래 한도를 먹는 일을 찾는다
  - 에이전트에게 "될 때까지 재시도"를 시키는 프롬프트 작성자 → 프롬프트 대신 바깥 래퍼가 재시도 횟수를 세게 옮긴다 → 모델이 "한 번 더"를 반복해도 한도 안에서 멈춘다
  - 이 저장소의 daily-lab 워크플로 → `timeout-minutes`와 별개로 `claude -p` 호출을 상한 래퍼 안에서 부르는 안을 테스트로 먼저 만든다 → 하루 루틴이 멈추지 않을 때 비용이 무한정 늘지 않는다

## 4. "Rate limit reached"는 세 가지 다른 일이다 — 재시도해도 풀리는 건 스로틀과 529뿐이고 지출 한도 429는 계속 실패한다
- 날짜: 2026-10-19
- 출처: https://dev.to/aobaworks/claude-code-rate-limit-reached-retry-setup-for-cron-jobs-1ioi
- 요약: 한도 메시지는 분당 스로틀, 구독 허용량(5시간·주간) 소진, 지출 상한의 세 가지를 가리키고, 지출 상한 429에는 `retry-after`가 없어 재시도가 소용없다. cron 작업에는 `CLAUDE_CODE_RETRY_WATCHDOG=1`(429·529 재시도, 지출 한도는 즉시 실패)과 요청당 대기 상한 `CLAUDE_CODE_RETRY_WATCHDOG_MAX_WAIT_MS`를 두고, 헤드리스 `-p`는 세션 한도를 넘겨 이어 가지 못하니 다음 실행을 리셋 뒤로 잡으라고 한다. 래퍼는 종료 코드와 출력의 "spend limit" 같은 문구로 할당량 중단을 구분하고, cron 시각은 `*/7`·`*/11`처럼 어긋나게 둔다.
- 현실 적용:
  - cron으로 `claude -p`를 돌리는 개인 개발자 → 래퍼 앞쪽에서 `CLAUDE_CODE_RETRY_WATCHDOG=1`과 대기 상한 30분을 환경 변수로 건다 → 스로틀은 알아서 넘기고 지출 한도는 즉시 알린다
  - 실패 알림을 받는 운영 담당 → 출력의 "spend limit|session limit|weekly limit|credit balance"를 종료 코드 2로 분류해 일반 실패(그 외 코드)와 다른 채널로 알린다 → 새벽 알림이 "고쳐야 할 오류"인지 "그냥 한도 소진"인지 한눈에 구분된다
  - 같은 시각에 Routine 여러 개를 켜 둔 사람 → 시작 분을 7·11분 간격으로 흩는다 → 동시에 429를 맞는 폭주를 줄인다
  - 헤드리스 작업을 한도 리셋 뒤로 미루고 싶은 사람 → 한도 중단 감지 시 다음 실행 시각을 파일에 적고 래퍼가 그 시각 전에는 바로 종료하게 한다 → 한도 소진 상태에서 호출만 반복해 연속 실패 카운트를 채우지 않는다
  - 이 저장소의 `spend-gate` → 래퍼가 쓰는 "중단 사유 분류" 표를 훅 README에 옮겨 적는다 → 비용 상한과 한도 소진을 같은 말로 부르던 오해를 정리한다

## 5. 208개 세션 로그로 본 구독 한도 소모처 — 캐시 만료 뒤 재개, 중간 모델 전환, 서브에이전트가 큰 몫이었다
- 날짜: 2026-10-19
- 출처: https://dev.to/raman_8527359ba62faa0a58e/where-my-claude-code-quota-actually-went-208-sessions-of-logs-1jkk
- 요약: 글쓴이는 208개 세션 기록에서 가장 긴 세션이 9,849턴·압축 68회이고, 60분 넘는 공백 뒤 캐시를 다시 쓴 일이 280번(약 8,160만 토큰), 5분 넘는 공백은 417번이었다고 센다. 세션 중 모델을 바꾼 37번은 약 907만 토큰을 캐시 없이 다시 읽게 했고 서브에이전트가 원시 토큰의 24%를 차지했다. 처방은 캐시 TTL보다 길게 쉬었으면 요약만 들고 새 세션을 열고, 자연스러운 끊김에서 `/compact`하고, 모델·effort는 처음에 정하고, CLAUDE.md는 약 1,500토큰 이하로 두는 것이다. 캐시 읽기가 토큰의 98%여도 한도의 98%라는 뜻은 아니라는 단서가 붙고, 큰 파일 읽기 영향은 검증하지 않았다는 댓글이 있다.
- 현실 적용:
  - 하루에 세션을 오래 재개하는 개인 개발자 → 트랜스크립트의 이전 줄 시각과 다음 줄 시각 차이로 5분·60분 초과 재개 횟수를 세는 스크립트를 돌린다 → "점심 뒤 재개"가 실제로 몇 번 캐시를 날렸는지 숫자로 본다
  - 세션 중 `/model`을 자주 바꾸는 사람 → 로그에서 모델이 바뀐 줄 수를 세어 전환당 재읽기 토큰을 추정한다 → 오늘부터 모델은 세션 첫 줄에서만 고르는 규칙을 시험한다
  - 서브에이전트를 많이 쓰는 팀 → 사이드체인 줄의 토큰 합을 전체와 비교해 비율을 표로 낸다 → 비율이 높은 에이전트 정의의 프롬프트부터 좁힌다
  - CLAUDE.md가 비대한 저장소 → `wc -w`로 CLAUDE.md 토큰을 대략 재고 1,500토큰 초과 파일의 상위 섹션을 `docs/`로 옮긴다 → 매 턴 다시 읽는 고정 비용을 줄인다
  - 이 저장소의 `cache-meter`(10-10) → 공백 길이별(5분/60분 초과) 재개 횟수 칸을 추가하는 이슈를 쓴다 → 캐시 이득 측정이 "공백 때문에 날린 양"까지 보여 준다

## 6. security-guidance 플러그인 후속 수정 4건 — 중첩 저장소 제외, 자격 증명이 없으면 리뷰가 조용히 건너뛰지 않고 알림, 노트북 셀 검사, 파이썬 3.10+ 탐색
- 날짜: 2026-10-19
- 출처: https://github.com/anthropics/claude-plugins-official/commits/main.atom
- 요약: 공식 `security-guidance` 플러그인이 작업 트리 안의 서브모듈·벤더 체크아웃처럼 자체 `.git`이 있는 폴더를 건드리지 않게 됐다. `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`·`DISABLE_TELEMETRY`·`DO_NOT_TRACK` 때문에 자격 증명이 훅에 안 가면 Stop·커밋·푸시 리뷰가 소리 없이 건너뛰어졌는데, 이제 주 1회 알림을 보이고 건너뛴 리뷰를 `no_creds`로 기록한다. NotebookEdit 셀 편집이 패턴 검사를 못 받던 문제도 고쳐졌고(이슈 #6718), `python3`가 3.10보다 낮은 맥에서는 python3.14~3.19를 찾아 커밋 리뷰어가 꺼지지 않게 했다. 10-15·10-16 갱신(리뷰별 토큰·비용 로그)의 후속이다.
- 현실 적용:
  - 텔레메트리를 꺼 둔 채 security-guidance를 쓰는 개발자 → `env | grep -E 'DISABLE_TELEMETRY|DO_NOT_TRACK|NONESSENTIAL'`로 켜져 있는지 확인하고 플러그인을 갱신해 알림이 뜨는지 본다 → "리뷰가 돌고 있다고 믿었지만 실제로는 건너뛰던" 상태를 오늘 확인한다
  - 주피터 노트북으로 분석하는 데이터팀 → 노트북 셀에 `os.system("rm -rf ...")` 같은 샘플을 넣어 플러그인 경고가 뜨는지 시험한다 → 셀 편집이 보안 검사 사각지대였던 곳이 막혔는지 확인한다
  - 서브모듈·`vendor/` 체크아웃이 있는 모노레포 → 갱신 뒤 `git status`와 리뷰 대상 목록이 중첩 저장소를 빼는지 한 번 돌려 본다 → 남의 코드를 내 코드로 오인한 경고 소음이 줄었는지 센다
  - stock macOS(파이썬 3.9)에서 커밋 훅을 쓰는 팀원 → `python3 --version`을 `scripts/doctor.sh` 한 줄에 넣는다 → 커밋 리뷰어가 조용히 꺼진 맥을 온보딩 때 찾는다
  - 이 저장소의 `onfailure-secret-guard`·`disaster-guard` → "자격 증명이 없어 검사를 건너뛴 경우 소리 내어 알린다"를 테스트 케이스로 추가한다 → 가드가 조용히 꺼지는 실패(fail-open)를 직접 만든 훅에서도 막는다

## 오늘의 선정
- 3·4번을 합쳐, 아무도 안 보는 `claude -p` 반복 실행에 **연속 실패·총 호출·경과 시간 세 상한**을 코드로 걸고 한도/지출 중단은 즉시 멈추는 래퍼 **loop-caps**를 만든다.
- spend-gate(10-13)는 비용 상한 훅이고, 어제 hook-exit-audit까지는 가드가 "정말 막는지" 재는 도구였다. 반복 실행 자체에 상한을 거는 래퍼는 아직 없다. 표준 라이브러리만으로 가짜 명령으로 테스트해 키·모델 없이 CI에서 돈다.
