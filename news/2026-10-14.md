## 1. Anthropic이 Git을 자체 버전 관리 시스템 Scion으로 바꿨다 — 에이전트 worktree 7.1분 → 5.1초
- 날짜: 2026-10-14
- 출처: https://news.hada.io/topic?id=35309
- 요약: Anthropic 엔지니어링 블로그의 "Redesigning source control at Anthropic"을 GeekNews가 소개한 글이다. AI 코딩으로 하루 병합이 5월 약 2,500건에서 9월 3만 건 넘게 늘어 Git 미러와 CI 체크아웃이 병목이 됐고, 항상 온라인인 에이전트에 맞춰 커밋·병합·리베이스를 서버에서 처리하고 필요한 파일만 받는 구조로 갈아탔다. 에이전트의 새 worktree 생성이 7.1분에서 5.1초로, 변경 요청당 소스 관리 시간이 34분에서 3.7분으로 줄었다고 한다. 거대 모노레포용이며 일반 Git 대체는 아니라고 선을 긋는다.
- 현실 적용:
  - 병렬 에이전트를 돌리는 팀 → 새 worktree를 만드는 데 걸리는 시간을 오늘 한 번 `time git worktree add`로 재 본다 → 에이전트 수를 늘리기 전에 병목이 Git에 있는지 모델에 있는지 가른다
  - 대형 저장소를 쓰는 회사 → `git sparse-checkout`과 partial clone(`--filter=blob:none`)을 CI 체크아웃 단계에 켜 본다 → Scion과 같은 "필요한 파일만 받기" 효과를 Git 안에서 일부 얻는다
  - 이 저장소의 daily-lab 루틴 → Actions 로그에서 체크아웃·설치에 쓰는 초를 단계별로 적어 둔다 → 모델 시간 외에 줄일 수 있는 고정 비용이 보인다
  - 팀 CLAUDE.md → 에이전트가 push 후 병합 대기에 걸리는 시간을 PR 기준으로 한 달치 뽑는다 → 병합 속도가 사람 검토인지 CI인지 데이터로 안다
  - 개인 사이드 프로젝트 → 에이전트 여러 개를 띄우기 전에 저장소 `.git` 크기와 클론 시간을 확인한다 → 병렬화의 이득이 얼마일지 미리 어림한다

## 2. claude-bulkhead: 병렬 Claude Code 세션이 서로의 프로세스·포트·메모리를 건드리지 않게 막는 플러그인
- 날짜: 2026-10-13
- 출처: https://news.hada.io/topic?id=35290
- 요약: worktree마다 세션을 띄워 쓰던 작성자가 한 에이전트의 `taskkill /F /IM node.exe`로 다른 세션의 개발 서버와 테스트가 함께 죽고, 세 세션이 동시에 빌드해 메모리가 바닥나 PC가 멈춘 일을 겪고 만든 플러그인이다. 셸 명령 실행 전에 다른 세션의 프로세스·포트·여유 메모리를 보고, 이름으로 프로세스 죽이기, 남이 쓰는 포트로 서버 띄우기, 메모리 부족 중 빌드, 남이 작업하는 폴더에서의 `git checkout`·`reset`을 막는다. 세션이 끝나고 남은 개발 서버는 몇 초 안에 정리한다.
- 현실 적용:
  - 한 노트북에서 세션 3개 이상 돌리는 개인 개발자 → 세션 간 충돌을 막는 PreToolUse 훅을 `~/.claude/settings.json`에 단다 → 한 에이전트의 `pkill node`가 나머지 세션을 죽이는 사고를 막는다
  - 프론트엔드 팀 → 세션마다 다른 `PORT`를 쓰게 하고 이미 다른 세션이 쓰는 포트면 훅이 다른 번호를 알려 준다 → "포트 사용 중" 오류로 에이전트가 엉뚱한 프로세스를 죽이는 연쇄를 끊는다
  - 16GB 노트북에서 빌드가 무거운 모노레포 → 여유 메모리가 1GB 밑이면 `npm run build`·`cargo build`를 보류시킨다 → 세 세션 동시 빌드로 맥이 얼어붙는 일을 막는다
  - 이 저장소의 로컬 daily-lab 실행 → 다른 세션이 같은 폴더에서 돌 때 `git checkout`을 막는다 → 사람이 다른 작업 중인 브랜치를 루틴이 바꿔 버리는 일이 없다
  - 에이전트를 SSH 원격에 보내는 팀 → 원격 쪽에도 같은 훅을 두고 세션 장부를 공유 폴더에 둔다 → 원격 서버를 여럿이 쓸 때 서로의 서버 프로세스를 정리하지 않는다

## 3. 라이브러리가 학습 데이터에 없으면: 규칙을 쌓지 말고 지식·컴파일러·린터·평가로 알려 줘라
- 날짜: 2026-10-13
- 출처: https://dev.to/kevinccbsg/your-library-isnt-in-the-training-data-making-ai-agents-use-it-well-5a34
- 요약: 모델이 모르는 라이브러리를 쓰게 하면 가장 비슷한 아는 API로 빈틈을 메워 겉보기엔 맞는 틀린 코드를 낸다는 글이다. 처방은 "하지 마라" 목록 대신 전체 시그니처·반환값·필수 순서·동작하는 예제를 주는 것, 엄격한 타입으로 컴파일러가 API를 가르치게 하는 것, 타입이 못 보는 것은 규칙 4개짜리 린터로 잡는 것, JSON 리포트와 종료 코드를 두는 것이다. 지시문을 효과로 검증하는 평가(스캐폴드·프롬프트·채점기, 대부분 결정적 채점)를 만들었고 5케이스 전체 실행이 약 1.8달러라고 한다.
- 현실 적용:
  - 사내 전용 SDK를 쓰는 팀 → 32KB 단일 참조 문서를 8KB 핵심 + `references/` 폴더로 쪼갠다 → 세 줄짜리 작업에서도 문서 전체가 컨텍스트에 실리는 낭비를 없앤다
  - 새 라이브러리를 막 도입한 개인 프로젝트 → 모델이 자주 틀리는 호출 5개를 모아 정규식 린터 규칙으로 만든다 → 같은 실수를 프롬프트가 아니라 코드가 매번 잡는다
  - 지시문(CLAUDE.md·스킬)을 자주 고치는 팀 → 결함을 심어 둔 파일에서 시작하는 케이스 5개를 평가로 두고 지시문을 바꿀 때마다 돌린다 → 문장 수정이 실제로 정확도를 올렸는지 점수로 본다
  - 플러그인을 배포하는 팀 → CI에 `claude plugin validate --strict`와 "참조한 파일이 모두 존재하는가" 검사를 넣는다 → 이름을 바꾼 뒤 깨진 링크가 배포되지 않는다
  - 이 저장소의 SKILL.md → "~했던 버전" 같은 버전 메모를 찾아 현재 동작 설명으로 고친다 → 시간이 지나 거짓이 되는 지시문이 쌓이지 않는다

## 4. 한 저장소에서 Claude Code와 Codex를 병렬로: worktree 함정 5가지와 교차 리뷰
- 날짜: 2026-10-13
- 출처: https://dev.to/offrun/running-claude-code-and-codex-in-parallel-on-one-repo-git-worktree-gotchas-and-cross-review-41eg
- 요약: 같은 저장소에서 두 에이전트를 돌릴 때 부딪히는 git worktree 문제를 정리한 글이다. 같은 브랜치를 두 worktree에서 못 쓰고, 새 worktree에는 `.env`·`node_modules` 같은 추적 안 되는 파일이 없고, 모든 worktree가 stash를 공유하며, 폴더를 `rm -rf`로 지우면 등록이 남아 `git worktree prune`이 필요하다. 다른 회사 모델이 짠 코드를 다른 에이전트가 읽기 전용으로 리뷰하게 하되 `git add -N .`로 새 파일도 diff에 포함하라고 권한다.
- 현실 적용:
  - 병렬 에이전트를 쓰는 개인 개발자 → `wt <이름>` 셸 함수로 worktree 생성과 `.env` 복사를 한 번에 한다 → 새 worktree에서 "환경변수 없음"으로 에이전트가 헤매는 첫 5분을 없앤다
  - 팀 CLAUDE.md → "stash 금지, 임시 커밋 사용" 한 줄을 넣는다 → 한 에이전트가 만든 stash를 다른 worktree 에이전트가 pop해 코드를 섞는 사고를 막는다
  - PR 올리기 전 개인 루틴 → `git add -N . && git diff HEAD | claude -p "버그·누락 테스트만 보고하라"`를 별칭으로 둔다 → 새 파일까지 포함한 diff를 사람이 읽기 전에 두 번째 눈이 먼저 본다
  - 코드 리뷰가 병목인 팀 → 리뷰 에이전트에 `--tools ""`로 읽기 전용을 강제하고 지적만 받는다 → 리뷰어와 작성자 에이전트가 같은 파일을 동시에 고치는 충돌이 없다
  - worktree를 자주 만드는 사람 → 주간으로 `git worktree prune`과 `git worktree list`를 점검한다 → 폴더만 지워진 유령 등록 때문에 같은 브랜치 이름이 거부되는 일을 없앤다

## 5. security-guidance 플러그인 수정이 드러낸 사실: asyncRewake 훅은 additionalContext가 아니라 stderr(또는 stdout)를 읽는다
- 날짜: 2026-10-13
- 출처: https://github.com/anthropics/claude-plugins-official/commit/8d392c8169665866be1d95f2bfeda5aaae7149dd
- 요약: 공식 플러그인 security-guidance가 커밋·푸시 검토 결과를 `additionalContext`로만 내보내고 있었는데, 비동기 깨우기(asyncRewake) 훅에서는 Claude Code가 그 필드를 읽지 않고 stderr 또는 stdout을 모델에게 보여 준다는 점이 문제였다. 안쪽에서 돌린 `claude` CLI가 경고를 stderr에 찍으면 모델은 검토 결과 대신 그 경고를 봤다. 이제 결과를 항상 stderr에 쓰고 SDK 로그는 디버그 파일로 돌리며, 이를 확인하는 테스트를 추가했다.
- 현실 적용:
  - 훅을 직접 짜는 개인 개발자 → 훅 스크립트가 모델에게 보여 줄 메시지를 stderr에 쓰는지 한 번씩 점검한다 → 메시지를 JSON 필드에만 넣어 모델이 못 보는 훅을 찾아낸다
  - 훅 안에서 `claude -p`나 SDK를 부르는 팀 → 안쪽 CLI의 stderr를 로그 파일로 돌린다 → 안쪽 경고가 바깥 훅의 메시지를 가리는 일이 없다
  - 회사의 보안 리뷰 훅 → 커밋·푸시 직전 훅이 낸 결과가 모델 컨텍스트에 실제로 들어갔는지 세션 트랜스크립트에서 확인한다 → 검토는 돌았는데 결과가 버려진 상태로 코드가 나가는 일을 잡는다
  - 훅 테스트 → "훅 출력의 모델 가시 본문에 기대한 문구가 있다"를 단위 테스트로 둔다 → 출력 채널을 바꾼 리팩터링이 조용히 기능을 끊는 것을 막는다
  - 이 저장소의 훅 결과물(spend-gate·disaster-guard) → 차단 이유가 stderr로 나가는지 e2e에서 다시 확인한다 → 차단은 됐는데 이유가 모델에게 안 가서 같은 명령을 반복하는 루프를 예방한다

## 오늘의 선정
- 2번(claude-bulkhead)과 4번(worktree 함정)·1번(병렬 에이전트 시대)의 "현실 적용"이 만나는 지점: 한 기기에서 도는 병렬 세션이 서로를 죽이지 않게 하는 PreToolUse 훅 **session-bulkhead**를 직접 만든다(이름 기반 프로세스 종료·남의 포트·메모리 부족 중 빌드·남의 폴더에서 git checkout/reset 차단).
- 기존 disaster-guard(파괴적 명령 규칙)는 세션 간 상태를 모르고, spend-gate는 비용만 본다. 세션 장부 파일로 "다른 세션이 있다"를 아는 훅은 처음이며, 5번의 교훈대로 차단 이유를 stderr로 내고 e2e로 모델에게 전달되는지 확인한다.
