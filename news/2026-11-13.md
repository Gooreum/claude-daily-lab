## 1. Claude Code 2.1.323 (11-12) — 실험적 Code Mode, 플러그인 `engines["claude-code"]`, 긴 훅 실행 중 30초 하트비트, Bash 허용 규칙 변수 값 `*` 경고
- 날짜: 2026-11-12
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.323 (변경 기록: https://code.claude.com/docs/en/changelog)
- 요약: Claude가 도구를 하나씩 부르는 대신 JavaScript를 써서 도구를 호출하는 Code Mode가 실험적 옵트인으로 들어왔고, 조직 단위로 끌 수도 있다(안내 페이지는 오늘 시점에 404였다). 플러그인은 `plugin.json`에 지원 Claude Code 버전 범위를 적을 수 있고 범위 밖이면 설치·갱신·로드가 막히며, `claude plugin validate`가 플러그인 TypeScript 훅 모듈의 타입을 검사한다. `claude -p`·SDK 세션은 훅이 오래 돌 때 30초마다 진행 신호를 보내 호스트가 멈춘 줄 알고 끝내지 않게 하고, `Bash(PORT=* npm run dev)`처럼 변수 값에 `*`가 든 허용 규칙은 시작할 때 경고한다.
- 현실 적용:
  - 플러그인을 사내에 배포하는 팀 → `plugin.json`에 `engines["claude-code"]`로 최소 버전을 적고 구버전 노트북에서 설치가 막히는지 한 번 시도한다 → 새 훅 기능을 쓰는 플러그인이 옛 버전에서 조용히 안 도는 문제를 설치 단계에서 잡는다
  - 훅이 5분 넘게 도는 CI 파이프라인(`claude -p`로 돌리는 리뷰 자동화) → 2.1.323 이상으로 올린 뒤 Desktop·SDK 호스트에서 같은 작업을 돌려 중간에 끊기는 횟수를 센다 → 30초 하트비트로 "멈춘 줄 알고 종료"가 사라졌는지 숫자로 본다
  - `.claude/settings.json`에 `Bash(PORT=* npm run dev)` 같은 허용 규칙을 둔 개발자 → `grep -n '=\*' .claude/settings.json`으로 변수 값에 `*`가 든 규칙을 찾아 고정 값으로 바꾼다 → 새 시작 경고가 뜨기 전에 넓은 허용을 좁힌다
  - 도구 호출이 많은 반복 작업(파일 100개 이름 정리)을 하는 개인 → Code Mode를 켠 세션과 끈 세션에서 같은 작업의 턴 수와 걸린 시간을 비교한다 → "JavaScript로 도구를 부르는" 방식이 이득인 작업의 크기를 내 환경 기준으로 안다
  - 이 저장소의 루틴 → 설정·훅 점검 도구(sandbox-lint, hook-manners)가 보는 설정 파일 목록에 `autoMode` 블록을 더하는 점검기를 만든다 → 새 설정 키가 생길 때마다 "설정이 의도대로 먹었나"를 사람 눈 대신 스크립트로 본다
  - 조직 관리자 → Code Mode를 끄는 조직 설정이 어디 있는지 안내 문서가 열리면 확인하고, 그 전에는 실험적 옵트인이라 기본값이 꺼짐인지 신입 기기 한 대에서 확인한다 → 실험 기능이 승인 없이 퍼지는 것을 막는다

## 2. Anthropic 11-12 "Operate Claude Managed Agents inside your security perimeter" — Managed Agents 서비스 전체(하네스·샌드박스·자격증명·세션 기록)를 내 클라우드·온프레미스에서 돌리는 self-hosted 비공개 베타
- 날짜: 2026-11-12
- 출처: https://claude.com/resources/articles/self-hosted-claude-managed-agents
- 요약: 지금까지 Managed Agents는 Anthropic이 운영하는 호스팅 서비스였고 샌드박스만 직접 둘 수 있었다. 이번엔 Managed Agents 서버와 그 데이터베이스, 도구를 실행하는 워커까지 직접 운영하고 세션 기록도 내 DB에 쌓이며, 모델 요청은 Anthropic·Bedrock·Google·Foundry·자체 게이트웨이 중 고른 곳으로 간다. 설계 원칙으로 두뇌(하네스)와 손(샌드박스)을 분리하고, 자격증명은 샌드박스 밖 프록시가 요청에 붙이며, 환경마다 허용 호스트 목록을 두고, 모든 세션 기록을 OpenTelemetry로 내보낸다고 설명한다. 비공개 베타다.
- 현실 적용:
  - 금융·의료처럼 코드가 사내망을 못 나가는 팀 → 빌드 실패를 고치는 에이전트 하나를 정해 허용 호스트를 "사내 git 서버와 패키지 저장소" 둘만 적은 환경 정의서를 오늘 써 본다 → 베타 승인이 나기 전에 보안 팀과 환경 범위 합의를 끝낸다
  - 에이전트 세션을 이미 OpenTelemetry로 모으는 팀 → Managed Agents 세션 기록의 이벤트 이름을 현재 쓰는 대시보드 필드와 표로 대응시킨다 → self-hosted로 옮길 때 대시보드를 다시 만들지 않는다
  - 자격증명을 `.env`로 샌드박스에 넣어 쓰는 개인 개발자 → 키를 샌드박스 밖 프록시가 붙이는 구조(vault)와 비교해, 내 에이전트 스크립트에서 키가 에이전트 눈에 보이는 지점을 세 곳 적는다 → 자격증명이 에이전트 컨텍스트에 노출되는 경로를 줄이는 첫 걸음이 된다
  - 규제 산업의 컴플라이언스 담당 → 데이터 보존(ZDR) 계약이 있는 조직에서 "세션 기록은 내 DB, 모델 요청만 ZDR 적용"이라는 책임 경계를 한 장 표로 만든다 → 감사 때 어떤 기록이 어디 남는지 즉답할 수 있다
  - 이 저장소의 루틴 → 매일 돌리는 수집·제작을 "허용 호스트 목록"으로 재서술하고 `읽기 불가(403 host_not_allowed)`가 난 출처를 목록과 대조한다 → 네트워크 제한 환경에서 어떤 소스가 막혔는지 소스 점검 표가 자동으로 설명된다
  - 모델 요청을 사내 게이트웨이로 보내려는 플랫폼 팀 → 게이트웨이 앞단에서 모델 ID 허용 목록을 두고 `deniedModels` 설정과 같은 목록을 쓰는지 대조한다 → 에이전트 쪽과 게이트웨이 쪽 정책이 서로 어긋나는 일을 막는다

## 4. dev.to 11-12 "My Claude Code auto mode config still said GITHUB_ACCOUNT_HERE. One command found it." — auto mode 설정의 자리표시자와 `"$defaults"` 누락 두 가지를 `claude auto-mode config`로 점검
- 날짜: 2026-11-12
- 출처: https://dev.to/rapls/my-claude-code-auto-mode-config-still-said-githubaccounthere-one-command-found-it-2mb7 (규칙 근거: https://code.claude.com/docs/en/auto-mode-config)
- 요약: 저자는 `~/.claude/settings.json`의 `autoMode.environment`에 "GitHub 계정 GITHUB_ACCOUNT_HERE의 저장소는 신뢰한다"라는 자리표시자를 써 두고 몇 주를 쓴 것을 발견했다. 점검은 둘이다. 첫째, `soft_deny`·`hard_deny`·`allow` 배열에 `"$defaults"`가 없으면 내장 규칙을 전부 대체한다. 둘째, `claude auto-mode config`가 설정과 기본값을 합친 실제 적용 설정을 보여 주니 그걸 grep한다. 공식 문서를 직접 열어 확인한 바로는 `soft_deny`를 `"$defaults"` 없이 쓰면 force push·`curl | bash`·운영 배포·auto mode 우회 같은 내장 차단이 전부 사라지고, `hard_deny`는 데이터 유출 규칙이 사라지며, 분류기는 프로젝트의 `.claude/settings.json`·`settings.local.json`의 `autoMode`를 읽지 않는다.
- 현실 적용:
  - auto mode를 쓰는 개발자 → `jq '.autoMode' ~/.claude/settings.json`을 오늘 한 번 찍어 `GITHUB_ACCOUNT_HERE` 같은 자리표시자와 `"$defaults"` 없는 배열을 찾는다 → 분류기가 내 계정을 모르거나 force push 차단이 꺼진 상태를 바로 고친다
  - `.claude/settings.local.json`에 `autoMode` 블록을 넣어 둔 팀원 → 문서대로 이 파일은 분류기가 읽지 않으니 `~/.claude/settings.json`으로 옮기게 하고 점검 스크립트로 확인한다 → "설정했는데 안 먹는다"로 허비하는 시간을 없앤다
  - 조직 관리자 → managed settings의 `autoMode.soft_deny`에 `"$defaults"`가 있는지 배포 전 점검 스크립트로 확인한다 → 개발자 수백 명의 기기에서 내장 차단이 통째로 빠지는 사고를 배포 전에 막는다
  - 점검 도구가 필요한 보안 담당 → 자리표시자 패턴(`_HERE`·`<...>`·`example.com`·`acme-corp`)과 `"$default"` 오타를 린트 규칙으로 만든다 → 사람이 눈으로 읽어 놓치는 오타를 기계가 잡는다
  - 이 저장소 → 기존 `sandbox-lint`·`mod-audit` 옆에 `autoMode` 전용 린터를 만들어 `bash test.sh`로 고정 시험한다 → 설정 점검 도구 묶음에 빠져 있던 분류기 설정을 채운다

- 4번의 "autoMode 블록 린터"를 만든다. `~/.claude/settings.json`과 프로젝트 설정 파일을 읽어 자리표시자, `"$defaults"` 누락, 프로젝트 파일에 둔 autoMode(무시됨), 형식 오류를 찾는 CLI `auto-mode-lint`. 모델·키·네트워크 없이 고정 설정 파일로 시험한다.
- 이유: 공식 문서(auto-mode-config)에서 `"$defaults"` 규칙과 읽는 범위를 직접 확인해 근거가 확실하고, 오늘 당장 내 설정에 돌려 볼 수 있다. 저장소의 설정 점검 도구 중 autoMode를 보는 것은 없다. 1번의 `engines` 필드는 공식 문서에 아직 없어 근거 부족으로 미룬다.
