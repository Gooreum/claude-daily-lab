## 1. Claude Code 2.1.318 — 저장된 claude.ai 로그인이 언제 끝나는지 `claude auth status`(`loginExpiresAt`)와 `claude -p` JSON 결과(`credential_expires_at`)에 표시하고, 만료 10일 전부터 stderr에 한 줄 경고한다 (SDK TS 0.3.318에도 같은 필드)
- 날짜: 2026-11-04
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.318 (SDK: https://github.com/anthropics/claude-agent-sdk-typescript/releases/tag/v0.3.318)
- 요약: 무인으로 `claude -p`를 돌리는 환경에서 로그인이 어느 날 갑자기 끝나 "Not logged in"으로 멈추던 문제에 대비하는 변경이다. 만료일이 상태 명령과 JSON 결과에 생기고, 텍스트 출력에는 열흘 전부터 경고가 붙는다. 만료된 뒤의 실패 메시지도 바뀌어 `claude -p`에서는 `claude auth login`과 `claude setup-token`을 안내한다. 이 기능을 쓰려면 기계가 읽을 수 있는 필드를 누군가 감시해야 한다.
- 현실 적용:
  - 이 저장소처럼 `CLAUDE_CODE_OAUTH_TOKEN`으로 매일 아침 Actions를 돌리는 사람 → 실행 직전 `claude auth status`의 `loginExpiresAt`을 읽어 7일 이내면 이슈 알림을 내는 점검 단계를 워크플로 앞에 넣는다 → 어느 날 아침 조용히 "Not logged in"으로 실패하기 전에 재발급할 시간을 번다
  - 맥미니에서 야간 배치로 `claude -p`를 도는 개인 개발자 → 배치 래퍼가 JSON 결과의 `credential_expires_at`을 로그 한 줄로 남기고 10일 미만이면 종료 코드 2로 끝나게 한다 → 배치 모니터링이 "성공"과 "곧 멈춤"을 구분한다
  - 팀 공용 빌드 서버에 `claude`를 설치한 DevOps 담당 → 서버별 만료일을 모으는 cron을 만들어 한 표로 보고 가장 빠른 서버부터 재로그인한다 → 서버 여러 대의 로그인이 같은 주에 한꺼번에 끊기는 사고를 피한다
  - 여러 계정으로 Routine을 운영하는 프리랜서 → 계정별 만료일을 노션 표 한 줄로 기록하는 스크립트를 주 1회 돌린다 → 고객별 자동화가 만료로 멈춘 걸 고객에게 먼저 듣는 일을 없앤다
  - Agent SDK로 자체 에이전트 서비스를 만든 개발자 → 결과 메시지의 `credential_expires_at`을 서비스 헬스체크 응답에 노출한다 → 대시보드에서 로그인 만료가 임박한 인스턴스를 바로 본다

## 2. Claude Code 2.1.318 설정 파일 보호 — 비대화형 실행이 깨진 `~/.claude.json`을 기본값으로 덮어쓰지 않고 복구 방법을 알리며 실패하고, 네트워크 홈 디렉터리에서 로그인·설정이 비거나 옛 사본으로 바뀌는 문제를 줄였다 (SDK는 `config_file_invalid` 시작 실패 사유 추가)
- 날짜: 2026-11-04
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.318 (SDK: https://github.com/anthropics/claude-agent-sdk-typescript/releases/tag/v0.3.318)
- 요약: 잘못된 JSON인 `~/.claude.json`을 비대화형 실행이 말없이 기본값으로 갈아엎던 동작이 사라지고, 시작이 실패하며 복구 명령을 보여 준다. 빈 파일을 손상으로 오판하던 것과, 복구 명령이 비었거나 잘린 백업을 가리키던 것도 고쳐졌다. `claude mcp add/remove`는 이제 설정 파일 잠금을 기다리거나 코드 1로 끝나며, `claude plugin validate`가 통과시킨 마켓플레이스 파일을 `marketplace add`가 거절하던 불일치도 고쳐졌다.
- 현실 적용:
  - 공용 NFS 홈을 쓰는 연구실·학교 서버 관리자 → 사용자별 `~/.claude.json`을 하루 한 번 `python3 -m json.tool`로 검사하는 cron을 넣는다 → 시작 실패가 났을 때 파일 손상인지 계정 문제인지 즉시 가른다
  - 여러 터미널에서 `claude mcp add`를 스크립트로 부르는 온보딩 담당 → 종료 코드 1을 재시도 조건으로 넣고 두 번 연달아 돌리는 테스트를 붙인다 → 설정 동시 쓰기로 MCP 서버가 사라지는 신입 PC를 막는다
  - 플러그인 마켓플레이스를 사내에 운영하는 팀 → CI에서 `claude plugin validate`와 `claude plugin marketplace add`를 같은 파일에 연달아 돌린다 → 검증은 통과했는데 설치가 거절되는 배포를 푸시 전에 잡는다
  - 컨테이너로 `claude -p` 잡을 돌리는 개발자 → 이미지에 `~/.claude.json` 백업을 시작 전에 복사하는 한 줄을 넣고 손상 파일로 시작 실패를 한 번 재현한다 → 새 실패 메시지의 복구 명령이 실제로 통하는지 알고 운영 문서에 옮긴다
  - Agent SDK로 서비스를 운영하는 개발자 → 시작 실패 사유에 `config_file_invalid`가 오면 일반 오류와 다른 알림 문구("설정 JSON 손상, 복구 필요")로 분기한다 → 원인 찾기 시간을 줄인다

## 3. Anthropic 텍스트 워터마크 — Claude Mythos 5·Opus 4.7·Sonnet 4.6이 생성한 텍스트에 워터마크가 붙고, Sonnet 4.6에서 `temperature`·`top_p`·`top_k`를 기본값이 아니게 쓰면 안 붙을 수 있다
- 날짜: 2026-11-03
- 출처: https://platform.claude.com/docs/en/release-notes/overview (상세: https://platform.claude.com/docs/en/build-with-claude/text-watermark)
- 요약: 릴리스 노트가 지정 플랫폼에서 위 세 모델의 생성 텍스트에 Anthropic의 텍스트 워터마크가 들어간다고 밝혔다. Sonnet 4.6에서는 샘플링 파라미터를 기본값이 아니게 지정한 요청의 결과가 워터마크를 갖지 못할 수 있다. 어떤 플랫폼에 적용되는지는 별도 문서에 있다.
- 현실 적용:
  - AI 생성 글 공개 여부를 정책으로 정해야 하는 콘텐츠 팀 → 정책 문서에 "워터마크는 보조 신호이고 단독 증거가 아니다"를 넣고 Sonnet 4.6 샘플링 예외를 각주로 단다 → 감지 실패를 "사람이 썼다"로 오해하는 일을 막는다
  - 학교 과제 검사를 맡은 교사·조교 → 의심 사례 5건을 직접 문서의 감지 방법으로 확인해 절차 메모를 만든다 → 워터마크 유무만으로 학생을 판단하는 실수를 피한다
  - Sonnet 4.6로 대량 생성하는 백엔드 개발자 → 요청 로그에서 `temperature`·`top_p`·`top_k`를 기본값이 아니게 보낸 호출 비율을 센다 → 워터마크가 안 붙을 수 있는 출력의 규모를 안다
  - 법무·컴플라이언스 담당 → 사내 생성 텍스트를 쓰는 서비스 목록에 사용 모델과 플랫폼을 열로 추가한다 → 워터마크 적용 대상과 아닌 곳을 한 표로 본다
  - 이 저장소의 `model-stale`(10-25) → 구형 모델 판정 표에 "워터마크 적용 모델" 열을 후속 후보로 올린다 → 모델 이전 때 워터마크 동작이 바뀌는지 같이 본다

## 4. Playwright MCP 스냅샷이 한 페이지에 22,556 토큰 — 400건 주문 대시보드 작업에서 컨텍스트가 22K에서 44K로 뛰고, 이후 모든 호출이 그 스냅샷을 다시 읽는다 (개발자 본인의 제품 Deputy 홍보 글, 측정은 3회 중앙값)
- 날짜: 2026-11-04
- 출처: https://dev.to/falaq_ai/playwright-mcp-snapshots-cost-me-22556-tokens-per-page-heres-what-i-measured-34km
- 요약: 에이전트가 브라우저를 다룰 때 접근성 스냅샷이 대화에 쌓여 호출마다 반복 청구된다는 측정이다. 주문 필터링 과제를 Claude Code(Sonnet)로 돌려 호출당 컨텍스트가 19.2K→22.1K→44.6K…46.3K로 늘었고, 10턴에 24.5만 토큰이 들었다고 한다. 글쓴이는 폼을 타입 있는 도구로 바꾸는 자기 제품이 3턴·약 7.3만 토큰이라고 주장한다. 제품 홍보라는 점을 글쓴이도 밝혔고 숫자는 직접 검증하지 못했다.
- 현실 적용:
  - Playwright MCP로 QA 자동화를 하는 개발자 → 같은 시나리오를 세 번 돌린 트랜스크립트에서 턴별 컨텍스트 길이를 뽑아 점프 지점을 표로 만든다 → 어느 페이지의 스냅샷이 비용을 키우는지 숫자로 안다
  - 관리자 대시보드 자동화 담당 → 페이지에서 필요한 영역만 가리키는 지시("표 첫 20행만")를 프롬프트에 넣고 전후 토큰을 비교한다 → 스냅샷 크기를 사람이 줄일 수 있는지 확인한다
  - 비용 상한을 둔 개인 개발자 → 이 저장소 `spend-gate`(10-13)에 브라우저 도구 호출 뒤 컨텍스트가 두 배 가까이 뛰면 경고하는 후속 규칙을 올린다 → 폭주 전에 알린다
  - 외부 제품 홍보 글을 읽는 팀 리더 → 글의 숫자를 우리 작업 하나로 재현해 보기 전에는 도입 검토에 쓰지 않는다는 체크 항목을 만든다 → 홍보 수치로 도구를 바꾸는 일을 막는다
  - 이 저장소의 `cache-break`(10-24) → 세션 로그에서 "한 번에 컨텍스트가 두 배로 뛴 턴"을 찾는 옵션을 후속 후보로 올린다 → 브라우저 스냅샷 같은 큰 도구 결과를 자동으로 짚는다

## 오늘의 선정
- 1번 로그인 만료일 노출을 고른다. `claude auth status`의 `loginExpiresAt`과 `claude -p` JSON의 `credential_expires_at`을 읽어 남은 날짜로 ok/경고/만료를 판정하는 `login-watch`를 만든다(키·로그인 없이 `--dry-run`·fixture로 검증).
- 이유: 이 저장소 자신이 토큰 하나로 매일 무인 실행되어 만료가 곧 중단이고, 2번~4번은 재현에 실제 환경이나 외부 제품이 필요하다.
