## 1. Anthropic이 Agent Skills 표준을 Agentic AI Foundation에 기증 — 이름·로고·`agentskills` GitHub 조직·도메인이 넘어가고, 버전 릴리스·제안 절차·스킬 작성자와 설치자용 보안 지침이 로드맵에 오른다
- 날짜: 2026-10-22
- 출처: https://www.anthropic.com/news/donating-agent-skills-to-the-agentic-ai-foundation
- 요약: 스킬은 `SKILL.md`와 필요한 스크립트·참고 자료를 담은 폴더이고, 이 표준과 이름·로고·GitHub 조직·`agentskills.io` 도메인이 Linux Foundation 산하 AAIF로 넘어간다. 글에 따르면 70곳이 넘는 에이전트 플랫폼이 이미 채택했고 게시된 스킬은 100만 개, 설치는 2억 8천만 건에 가깝다. 이번 글에는 규격 변경이 없고, 제안된 로드맵은 버전이 붙은 릴리스, 공식 제안 절차, 스킬을 쓰고 설치하는 사람을 위한 보안 지침 세 가지다. 유지관리자는 Anthropic·Google·OpenAI 등의 엔지니어가 개인 자격으로 맡는다.
- 현실 적용:
  - 팀 공용 스킬 저장소(`.claude/skills/`)를 관리하는 리드 → 스킬 폴더마다 `name`이 폴더 이름과 같은지, `description`이 1024자를 안 넘는지 검사하는 한 줄을 CI에 둔다 → 어느 에이전트에서 열어도 로드되는 스킬만 머지된다
  - 외부 스킬을 설치해 쓰는 개인 개발자 → 설치 전에 `scripts/` 안의 `curl … | sh`, `rm -rf`, 홈 디렉터리 읽기 줄을 목록으로 뽑아 본다 → 보안 지침이 나오기 전에도 "이 스킬이 내 컴퓨터에서 뭘 할 수 있나"를 눈으로 확인한다
  - 스킬을 `claude.ai`에 올리거나 Skills API로 패키징하는 담당 → 포터블 키(`name`·`description`·`license`·`compatibility`·`metadata`·`allowed-tools`) 밖의 프런트매터 키를 업로드 전에 찾는다 → Claude Code에서는 조용히 무시되던 키가 업로드 단계에서 하드 에러가 되는 일을 미리 막는다
  - `allowed-tools: Bash`처럼 넓은 권한을 스킬 프런트매터에 적어 둔 사람 → 스킬별 `allowed-tools`를 한 표로 모아 가장 넓은 것부터 좁힌다 → 스킬이 호출되는 턴에 묻지 않고 허용되는 범위를 줄인다
  - 이 저장소의 `.claude/skills/daily-lab`·`daily-lab-apply` → 새 표준 규칙으로 점검해 어긋난 곳을 고치고 결과를 README에 남긴다 → 매일 도는 스킬이 규격 변경에 깨지지 않는지 확인한다

## 2. "서브에이전트를 메인 루프로 접을 때" — 서브에이전트 호출은 모델 루프를 한 겹 더 도는 것이라 한 고객은 단일 루프로 약 2배 빨라졌고, 이전은 단계별로 한다
- 날짜: 2026-10-22
- 출처: https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop
- 요약: 글은 서브에이전트가 난립하고(팀마다 하나씩 만들어 주인 없는 에이전트가 수백 개), 시스템 프롬프트에 상충하는 문장이 쌓이고, 문제 종류별로 쪼갠 탓에 넘길 때마다 정보가 새는 경우 메인 루프로 접으라고 한다. 반대로 컨텍스트가 커져 성능이 떨어지거나, 새 컨텍스트로 병렬 작업이 필요하거나, 도구·지침이 충돌하면 서브에이전트가 맞다고 한다. 이전 순서는 ① 서브에이전트를 도구로 호출해 기준 점수를 만들고 ② 서로 연쇄하는 전문가를 합치고 ③ 하나씩 접어(프롬프트→스킬, API 호출→MCP 도구) 평가 점수를 비교하는 것이다. 도구 정의가 30~50개를 넘으면 선택이 나빠지고, 시작용 평가 예시는 10개면 된다고 한다.
- 현실 적용:
  - `.claude/agents/`에 정의가 10개 넘게 쌓인 팀 → 정의마다 `description`이 서로 겹치는 쌍과 같은 도구 목록을 쓰는 쌍을 표로 뽑는다 → 합치거나 스킬로 접을 후보를 눈대중이 아니라 목록으로 정한다
  - 서브에이전트를 전부 `general-purpose`로 부르는 개인 개발자 → 한 작업을 서브에이전트 호출 유무로 두 번씩 돌려 시간과 토큰을 `/cost`로 비교한다 → 병렬·격리가 필요 없는 호출을 접어 지연을 줄인다
  - 에이전트 제품에 도구 정의가 40개 넘게 붙은 팀 → 도구를 사용자 의도별로 묶어 목록을 줄이는 PR을 만들고 골든 예시 10개로 전후 정답률을 잰다 → 도구 선택 혼동이 정말 줄었는지 숫자로 본다
  - 메인 루프에 "항상 ~하라, 단 ~는 예외" 문장이 계속 붙는 시스템 프롬프트 담당 → 상충하는 문장 쌍을 찾아 스킬로 빼고 프롬프트 줄 수를 기록한다 → 프롬프트가 누더기가 되는 속도를 눈에 보이게 한다
  - 이 저장소의 `agent-radar` → 서브에이전트 호출 수와 경과 시간을 하루 단위로 모아 "호출은 많은데 결과는 짧은" 서브에이전트를 접기 후보로 표시하는 이슈를 쓴다 → 모드가 이미 보여 주는 숫자를 정리 판단에 쓴다

## 3. Google Cloud에서 Anthropic이 직접 운영하는 Claude Platform 정식 출시 — 하나의 Google Cloud 청구서와 IAM으로 쓰고, Opus 5.5 fast mode도 정식(최대 2.5배 빠름, 입력 100만 토큰당 8달러·출력 40달러)
- 날짜: 2026-10-22
- 출처: https://claude.com/resources/articles/claude-models-on-google-cloud-anthropic-managed
- 요약: Google Cloud 고객이 Anthropic이 운영하는 Claude Platform 전체(Managed Agents 베타, 코드 실행, 컴퓨터 사용, 에이전트 스킬, Files API, 웹 검색·fetch, MCP 커넥터 베타, 프롬프트 캐싱, 배치)를 기존 Google Cloud 약정과 IAM으로 쓴다. 새 기능과 베타가 Claude Platform과 같은 날 열리고, 지금은 US와 Global 엔드포인트만 있다. 데이터 처리자가 Anthropic인 방식이라, Google이 처리자여야 하거나 엄격한 지역 보관 요건이 있으면 Google 관리형을 권한다. 기존 할인은 과거 사용분에 소급되지 않는다.
- 현실 적용:
  - Google Cloud 약정 소진 목표가 있는 플랫폼 팀 → 개발 환경 하나만 이 경로로 연결해 같은 프롬프트의 응답 시간과 청구서 표시 방식을 일주일 비교한다 → 전사 이전 전에 약정 소진 효과와 운영 차이를 숫자로 본다
  - 지역 보관 요건이 있는 규제 업종 보안 담당 → "US와 Global만 제공"을 요건표와 대조해 해당 업무는 Google 관리형에 남긴다 → 데이터 처리자·지역 요건 위반을 도입 전에 걸러낸다
  - 지연에 민감한 챗 UI를 만드는 개발자 → Opus 5.5 fast mode를 켠 호출과 기본 호출을 같은 입력 20개로 돌려 첫 토큰·전체 시간과 비용 차이를 표로 만든다 → 8달러·40달러 단가가 사용자 체감 속도 향상에 값하는지 정한다

  - 이 저장소의 `model-caps` → 새 엔드포인트에서 `GET /v1/models`가 같은 능력 표를 주는지 비교하는 옵션을 이슈로 쓴다 → 경로가 달라도 같은 모델 능력이라는 가정을 검사한다

## 4. Claude Code 2.1.308·2.1.309 — 샌드박스 Bash가 셸 시작 파일을 샌드박스 밖에서 실행하던 문제, `--mcp-config` 파일 변조, 컴파운드 명령 권한 검사 구멍을 대량으로 막았다
- 날짜: 2026-10-22
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.309
- 요약: 2.1.309는 샌드박스 Bash가 매 명령 전에 셸 시작 파일을 샌드박스 밖에서 실행하던 것, 샌드박스 명령과 자동 승인 편집이 `--mcp-config`로 넘긴 MCP 설정 파일을 바꿀 수 있던 것, `cd`가 감싸이거나 접두가 붙은 git 컴파운드 명령이 권한을 묻지 않던 것, `Edit(path)` deny 규칙이 서브셸이 섞인 리다이렉트를 못 막던 것을 고쳤다. PowerShell 훅이 종료 코드 2로 막지 못하던 문제와 Windows에서 Git for Windows가 없을 때 `PreToolUse`·`PermissionRequest` 훅이 열려 버리던 문제, 모드의 `turn.step` 훅이 `haiku` 같은 별칭으로 모델을 지정하면 모든 요청이 실패하던 문제도 포함된다. 2.1.308은 버그 수정뿐이고, Agent SDK Python 0.2.172·0.2.173과 TypeScript 0.3.308·0.3.309가 이 CLI를 번들한다.
- 현실 적용:
  - 샌드박스를 켜고 쓰는 팀 → 2.1.309로 올린 뒤 `~/.bashrc`에 `touch /tmp/sandbox-probe` 줄을 심고 샌드박스 명령을 한 번 돌려 샌드박스 밖 실행이 없는지 확인한다 → 시작 파일이 샌드박스를 우회하던 경로가 닫혔는지 직접 검증한다
  - `claude -p --mcp-config`로 야간 작업을 돌리는 개인 개발자 → 설정 파일을 읽기 전용(`chmod 444`)으로 두고 해시를 작업 시작·종료에 비교한다 → 자동 승인 편집이 연결할 MCP 서버를 바꾸는 사고를 파일 수준에서도 막는다
  - Windows에서 PowerShell 훅을 쓰는 팀 → 종료 코드 2를 내는 테스트 훅을 만들어 도구 호출이 정말 막히는지 확인한다 → 이전 버전에서 가드가 조용히 통과시키던 상태를 찾아낸다
  - `Edit(path)`·`Bash(git *)` deny 규칙을 믿고 있는 보안 담당 → 이 저장소의 `hook-exit-audit`로 규칙에 서브셸·`cd` 접두 변형 입력을 넣어 막히는지 표로 만든다 → 이번에 고쳐진 형태들이 우리 설정에서 실제로 막히는지 확인한다
  - `mods`에서 `turn.step` 훅을 `haiku` 별칭으로 쓰던 모드 제작자 → 2.1.309 이전 버전 사용자에게 보이는 모델 오류를 README에 기록하고 모델 ID를 명시한다 → 설치자가 버전 차이로 겪는 실패를 줄인다

## 5. "조용한 실패"를 잡는 법 — 돌지 않은 작업은 외부 하트비트로, 비어 있거나 오래된 결과 파일은 `Stop` 훅으로, API 오류는 `StopFailure` 훅으로, 비용 폭주는 `--max-budget-usd`로 잡는다
- 날짜: 2026-10-22
- 출처: https://dev.to/aobaworks/ai-agent-monitoring-in-claude-code-catch-silent-failures-34kc
- 요약: 글쓴이는 에이전트 작업이 오류 없이 끝났지만 실제로는 일을 못 한 여섯 경우(작업 미실행, 빈·미완성 출력, 어제 파일, 조용한 API 오류, 비용 폭주, 서브에이전트 잘못된 인계)를 나누고 각각의 감시 장치를 제시한다. `Stop` 훅은 에이전트 마지막 말이 아니라 산출 파일 자체를 검사하고(최소 줄 수 2, 최대 파일 나이 90분), 종료 코드 2로 한 번만 더 고치게 한다. 크론 래퍼는 예산 상한(작업 평균이 0.3달러면 2달러)을 걸고 비용을 CSV에 남기며 마지막에 하트비트를 보낸다. `--continue`·`--resume`은 누적 합계를 보고하니 예약 작업은 새 세션으로 시작하라고 한다.
- 현실 적용:
  - 매일 아침 `claude -p`로 리포트를 만드는 개인 개발자 → 산출 파일의 줄 수와 수정 시각을 검사하는 `Stop` 훅을 걸고, 파일을 일부러 지운 채 한 번 돌려 막히는지 본다 → "성공으로 끝났는데 파일이 비었다"를 아침에 알게 된다
  - 크론으로 Claude 작업을 여러 개 돌리는 팀 → 작업 시작·성공·실패 때 Healthchecks.io에 핑을 보내는 래퍼를 공통으로 쓴다 → 아예 돌지 않은 날을 알림으로 받는다
  - 요금 상한을 정해야 하는 운영자 → 최근 일주일 실행의 `total_cost_usd` 평균을 구해 `--max-budget-usd`를 평균의 5~7배로 둔다 → 폭주 시에는 막고 정상 변동은 통과시킨다
  - 레이트 리밋·결제 오류가 새벽에 나는 경우가 있는 사람 → `StopFailure` 훅이 오류 종류를 JSONL로 남기게 하고 주 1회 종류별로 센다 → 반복되는 한도 문제를 추측이 아니라 기록으로 본다
  - 이 저장소의 `loop-caps` → 연속 실패 상한에 더해 "산출 파일이 비었거나 어제 것이면 실패로 센다"는 검사를 래퍼에 더하는 이슈를 쓴다 → 상한이 못 잡던 "성공했지만 빈손" 실행을 실패로 센다

## 6. 리뷰 판정은 읽은 커밋 해시 아래에 저장해야 한다 — HEAD가 리뷰 중에 움직이면 무효, 리뷰가 읽기 전용이어도 파일이 바뀌면 무효, 리뷰어 엔진은 만든 엔진과 달라야 한다
- 날짜: 2026-10-22
- 출처: https://dev.to/iliyaoblakov/why-my-review-gate-saves-each-verdict-under-the-exact-commit-hash-3d11
- 요약: 글쓴이는 리뷰가 오래 걸리는 사이 새 커밋이 들어오면 승인이 옛 커밋에 대한 것이 되는 문제와, 읽기 전용이어야 할 리뷰에서 모델이 추적 파일을 고친 사례(CLAUDE.md의 "수정 금지" 규칙만으로는 Edit 도구가 막히지 않았다)를 든다. 그래서 리뷰 시작 때 HEAD 전체 해시를 읽고 판정을 해시 앞 12자 이름의 파일로 저장하며 첫 줄에 40자 해시를 적는다. 리뷰 뒤 HEAD가 움직였거나 `.ai/` 밖 파일이 바뀌었으면 무효로 하고, 병합 검사는 해시가 같은 판정과 테스트 통과 기록이 있을 때만 통과시킨다. 자체 한계로 보안 경계는 아니라고 밝힌다.
- 현실 적용:
  - Claude Code Review 결과로 병합을 막는 팀 → 판정 파일 첫 줄에 리뷰한 커밋 SHA를 적고 병합 단계에서 현재 HEAD와 비교한다 → 리뷰 중 푸시된 커밋이 검토 없이 들어가는 일을 막는다
  - 리뷰어를 읽기 전용으로 돌리려는 개인 개발자 → `claude -p --tools "Read,Grep,Glob"`처럼 도구 자체를 읽기 전용으로 제한하고, 리뷰 전후 `git status --porcelain`을 비교한다 → 지침 문구가 아니라 도구 목록으로 쓰기를 막는다
  - 테스트 통과를 말로 확인하던 팀 → 테스트 통과 기록을 `.ai/tests/<해시>.pass`처럼 커밋별 파일로 남기고 병합 검사가 그 파일을 요구한다 → 다른 커밋에서 통과한 테스트가 지금 커밋의 통과로 둔갑하는 일을 없앤다
  - 코드를 Claude로 만들고 같은 Claude로 리뷰하는 개인 → 리뷰를 다른 모델이나 도구로 한 번 돌리는 단계를 병합 전 체크리스트에 넣는다 → 만든 쪽의 같은 맹점이 리뷰를 그대로 통과하는 일을 줄인다
  - 이 저장소의 `review-gate` → 체크런이 읽은 커밋과 현재 HEAD가 같은지 비교하는 검사를 더하는 이슈를 쓴다 → 개수만 보고 막던 게이트가 낡은 리뷰를 걸러내게 한다
