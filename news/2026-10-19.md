## 1. 훅이 `exit 1`로 끝나면 막히지 않는다 — 차단 메시지를 찍은 9건이 전부 실행됐고, 크래시(트레이스백·`jq` 없음)도 같은 이유로 가드를 꺼 버린다
- 날짜: 2026-10-18
- 출처: https://dev.to/ji_ai/claude-code-hooks-exit-code-1-doesnt-block-9-of-9-commands-ran-44h
- 요약: 글쓴이의 `PreToolUse` Bash 훅은 "BLOCKED"를 찍고 `sys.exit(1)`로 끝났는데, 3주치 세션 기록을 뒤지니 그 문구가 9번 나왔고 9건(`rm -rf` 5, `git push --force` 3, `git reset --hard` 1)이 모두 실행됐다. 막는 코드는 2뿐이고, 1이나 크래시로 인한 1, `jq` 부재로 인한 127은 사용자에게 stderr만 보여 주고 도구는 그대로 돈다. 위험 명령 40개를 재생하니 `exit(1)`은 0개, `exit(2)`는 40개를 막았고, `NameError` 오타가 난 `exit(2)` 훅도 0개를 막았다(`try/except`로 감싸 크래시도 2로 보내야 한다). 정규식 차단은 Claude가 `find -delete`나 `shutil.rmtree`로 돌아가는 6건 중 2건을 놓쳐 속도 방지턱일 뿐이라고 한다.
- 현실 적용:
  - 개인 `~/.claude/settings.json`에 가드 훅을 몇 개 쌓아 둔 개발자 → 각 훅 스크립트에 위험 명령 JSON을 흘려 넣어 종료 코드를 찍는 점검 도구를 돌린다 → 막는 줄 알았던 훅이 사실 `exit 1`이라 아무것도 막지 않는 것을 오늘 찾는다
  - 팀 공용 훅 저장소를 관리하는 플랫폼팀 → 훅 PR마다 "위험 입력은 2, 깨진 JSON은 2, 안전 입력은 0"을 확인하는 단계를 CI에 넣는다 → 훅을 고치다 `NameError` 한 줄로 가드가 조용히 꺼지는 일을 머지 전에 잡는다
  - `jq`로 stdin을 파싱하는 셸 훅을 쓰는 사람 → 훅 첫 줄에 `command -v jq`가 없을 때 `exit 2`로 가는 분기가 있는지 정적으로 검사한다 → 새 맥·컨테이너에서 `jq`가 빠져 승인 게이트가 통째로 꺼지는 사고를 막는다
  - 훅 `matcher`를 직접 쓰는 사람 → `"bash"`처럼 대소문자가 틀리거나 존재하지 않는 도구 이름이 있는지 점검한다 → 아무 입력에도 발동하지 않는 훅을 "설정은 됐다"며 믿고 지나가지 않는다
  - 이 저장소의 `session-bulkhead`·`disaster-guard`·`spend-gate` 훅 → 새 점검 도구로 세 훅을 먼저 돌려 README에 종료 코드 표를 붙인다 → 직접 만든 가드가 위험 입력에서 정말 2로 끝나는지 숫자로 남긴다

## 2. force-push를 22가지로 우회해 보니 deny 규칙이 막은 건 7개 — 나머지는 refspec·`git -C`·`sh -c`·스크립트 안에 숨어 훅 없이는 통과했다
- 날짜: 2026-10-18
- 출처: https://dev.to/teefayb/i-tried-22-ways-to-force-push-past-my-teams-claude-code-rules-7-were-hard-blocked-2b5d
- 요약: 팀 설정에 `git push --force origin main` 류 deny 규칙을 두고 22가지 변형을 던졌더니 7개만 막혔다(`-f`, `--force-with-lease`, 환경 변수 접두사, `&&`·`;` 연결은 규칙이 잘라서 검사). 나머지 15개는 `+main`·`HEAD:main` 같은 refspec, 브랜치 이름 없는 `git push`, `--mirror`, `git -C`·`git -c`·별칭, `/usr/bin/git`·`sh -c`·`eval`·`xargs`, `bash ship.sh`처럼 규칙 패턴이 못 보는 모양이었다. 해법은 permission 규칙보다 먼저 도는 `PreToolUse` 훅이 명령을 풀어 플래그와 refspec을 검사하고 `exit 2`로 막는 것이며, 후속 수정에서 `remote.origin.push` 설정 때문에 맨 `git push`가 모든 브랜치를 강제로 밀 수 있다는 점이 드러났다. 결국 서버 쪽 브랜치 보호가 마지막 방어선이라고 글쓴이는 정리한다.
- 현실 적용:
  - `main` 직접 푸시를 쓰는 이 저장소와 같은 개인 프로젝트 → 22가지 변형 목록을 그대로 테스트 입력 파일로 만들어 내 가드 훅에 흘린다 → `git push origin +HEAD:main` 같은 변형이 통과하는 곳을 오늘 찾는다
  - 팀 설정에 deny 규칙만 있는 팀 → deny 규칙과 훅을 각각 같은 변형 목록으로 돌려 "규칙만 막은 것 / 훅만 막은 것 / 둘 다 못 막은 것"을 표로 만든다 → 서버 브랜치 보호를 켤 근거를 숫자로 만든다
  - GitHub 저장소 관리자 → `main` 브랜치 보호(force-push 금지, PR 필수)가 켜졌는지 `gh api repos/{owner}/{repo}/branches/main/protection`으로 확인하는 스크립트를 주 1회 돌린다 → 훅이 놓친 우회가 있어도 서버가 마지막에 거부한다
  - 에이전트에게 `bash scripts/ship.sh`를 맡기는 팀 → 스크립트 안의 `git push` 줄을 grep해 래퍼 스크립트도 훅 검사 대상으로 올린다 → 규칙이 `bash ship.sh`만 보고 지나치는 경로를 막는다
  - 이 저장소의 daily-lab 루틴 → `git push origin main`만 허용하고 `--force`·`+refspec`·`--mirror`는 막는 PreToolUse 훅을 테스트 22건과 함께 만든다 → 규칙이 "main 직접 푸시"를 허용하는 만큼 "강제 푸시"는 코드가 막는다

## 3. 세션 로그를 읽을 때 걸리는 함정 4가지 — "user" 줄 대부분은 요청이 아니고, 포크는 부모의 기록을 복사해 시작한다
- 날짜: 2026-10-18
- 출처: https://dev.to/ji_ai/reading-claude-code-and-codex-session-logs-four-traps-3f57
- 요약: 세션 JSONL의 `user` 줄에는 도구 결과, 압축 요약, 작업 알림, 인터럽트 표시, `!` 셸 출력이 섞여 있어 사용자가 입력한 요청만 세려면 여러 접두사(`<task-notification`, `<system-reminder`, `[Request interrupted` 등)와 메타·사이드체인 표시를 걸러야 한다. 포크 서브에이전트의 로그는 부모 대화 사본으로 시작해 부모의 타임스탬프를 달고 있어 그대로 읽으면 일을 두 번 한 것처럼 보이므로, 포크 메타 파일의 `toolUseId`를 찾아 그 뒤부터 세야 한다. 요청의 끝은 대화형(`turn_duration` 줄)과 `claude -p`(마지막 `end_turn` 답변)가 다르고, 워크플로 저널에는 시계가 없어 시작 시각을 파일 생성 시각에서 얻는다.
- 현실 적용:
  - 세션 로그로 비용·시간을 분석하는 개인 개발자 → 요청 수를 셀 때 `tool_result`·`<system-reminder`·`isSidechain` 줄을 빼는 필터를 먼저 쓰고 전후 숫자를 비교한다 → "오늘 요청 300건"이 실은 40건이었다는 식의 부풀림을 바로잡는다
  - `claude -p`를 CI에서 돌리는 팀 → 요청 종료를 마지막 `end_turn` 답변으로 잡아 실행 시간을 계산한다 → `turn_duration` 줄이 없어 시간이 비는 로그에서도 지연을 잰다
  - 포크 서브에이전트를 켠 저장소(2.1.302부터 `claude -p` 기본값) → 포크 로그의 부모 복사분을 건너뛰는 리더를 만들어 서브에이전트별 토큰을 센다 → 같은 일을 부모와 포크 양쪽에 이중 청구하는 집계를 피한다
  - 에이전트 감사 로그를 보관하는 보안 담당자 → 로그 요약 도구가 접두사 목록 기준으로 "사람이 직접 한 요청"만 세는지 테스트 로그로 확인한다 → 시스템이 넣은 줄을 사용자 행동으로 오인한 감사 보고를 막는다
  - 이 저장소의 `otel-tap`·`spend-gate` → 트랜스크립트 usage를 읽는 부분에 포크 사본 줄이 이중으로 잡히는 입력을 테스트 케이스로 추가한다 → 비용 상한 훅이 포크 때문에 실제보다 일찍 발동하는지 확인한다

## 오늘의 선정
- 1번 첫째·둘째·셋째·넷째를 합쳐, `settings.json`의 PreToolUse 훅을 읽어 그 명령을 위험 입력·깨진 JSON·빈 입력으로 직접 돌려 종료 코드를 표로 찍고(`exit 1` 같은 fail-open을 짚음), 스크립트의 정적 신호(`jq` 의존·`try/except` 부재·matcher 오타)도 보는 CLI **hook-exit-audit**을 만든다.
