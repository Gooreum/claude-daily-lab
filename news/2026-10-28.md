## 1. Claude Code 2.1.312 — 이름이 잘못된 명령 하나가 모든 명령 로딩을 막아 `claude -p`가 출력 없이 끝나던 문제 수정, 프롬프트·에이전트 훅은 세션당 동시 24개로 제한, 큰 CLAUDE.md를 앞부분만 보고 덮어쓰던 문제 수정
- 날짜: 2026-10-27
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.312
- 요약: 2.1.312는 수정 중심이다. 이름이 잘못된 명령 하나가 모든 명령의 로딩을 막아 `claude -p`가 아무 출력 없이 끝날 수 있던 것과, 아주 큰 CLAUDE.md·규칙 파일·`@` 포함 파일을 앞부분만 본 채 덮어쓰던 것을 고쳤다(이제 Write가 전체를 읽거나 제자리 편집을 요구한다). 프롬프트·에이전트 훅은 서브에이전트까지 합쳐 세션당 동시에 24개까지만 돌고, 시간 제한이 1초 미만이면 1초로 센다. 하위 디렉터리의 `paths:` 스킬이 Bash `cd` 뒤에 안 찾아지던 것, Claude apps 게이트웨이의 `oidc.user_id_claim`(Entra ID의 `oid` 같은 claim으로 사람 식별) 추가, 클라우드 세션에서 WebFetch가 허용 목록 밖 호스트를 설명하는 변경도 들어 있다.
- 현실 적용:
  - `.claude/commands/`에 명령 파일을 직접 만들어 쓰는 개인 개발자 → 2.1.312로 올린 뒤 파일명에 공백·대문자·점이 든 명령이 없는지 `ls`로 한 번 훑고, `claude -p "/help"`가 출력을 내는지 확인한다 → 명령 하나 때문에 야간 `-p` 작업이 조용히 비는 일을 첫날 잡는다
  - 프롬프트 훅을 서브에이전트마다 걸어 둔 팀 → 서브에이전트 5개를 병렬로 돌릴 때 훅 개수를 세어 24개 상한에 닿는지 계산하고, 닿으면 훅을 `command` 타입으로 바꾸거나 합친다 → 상한에 걸려 훅이 밀리며 느려지는 일을 미리 피한다
  - 수백 줄짜리 CLAUDE.md를 에이전트에게 고치게 하던 리드 → 업그레이드 뒤 "CLAUDE.md의 한 규칙만 바꿔 줘"를 시켜 전체 읽기 또는 제자리 편집으로 처리되는지 보고 diff가 규칙 한 줄인지 확인한다 → 앞부분만 보고 파일을 덮어써 규칙이 날아가는 사고를 막는다
  - 하위 폴더마다 `paths:` 스킬을 두는 모노레포 팀 → 스킬이 켜지는 폴더로 `cd`한 뒤 스킬 목록에 나타나는지 점검 스크립트로 확인한다 → 깊이 들어갔을 때 스킬이 안 켜져 규칙이 빠진 코드가 나가는 것을 막는다
  - 이 저장소의 `daily-lab` Actions 워크플로 → 로그 첫 줄에 `claude --version`을 남기는지 보고, 2.1.312 이상에서 `daily-lab` 스킬이 로딩되는지 로컬에서 `claude -p`로 한 번 확인한다 → 스킬 이름 문제로 Actions가 출력 없이 초록색으로 끝나는 날을 막는다

## 2. 다운로드 폴더에 놓인 AGENTS.md·CLAUDE.md가 코딩 에이전트를 조종했다 — 설정 파일을 고치게 하는 데 Codex는 90% 넘게, Claude Code는 약 절반 성공, 토큰 유출은 다섯 번에 한 번꼴 (Forever Security 실험을 전한 글)
- 날짜: 2026-10-27
- 출처: https://dev.to/raxxostudios/agentsmd-files-in-downloads-can-hijack-codex-and-claude-code-538o
- 요약: 보안 업체 Forever Security가, `~/Downloads` 같은 폴더에 심어 둔 지침 파일을 에이전트가 프로젝트 설정으로 믿고 따르는지 시험한 결과를 전한 글이다. Codex는 90% 넘는 시도에서 전역 설정(`~/.codex/config.toml`)에 악성 항목을 넣었고, Claude Code는 약 절반에서 자기 설정 파일을 고쳤으며 다섯 번에 한 번쯤 코드를 실행하고 OAuth 토큰을 새게 했다고 한다. 연구자들은 에이전트가 설계대로 움직인 것이라 패치가 없다고 했고, 글은 모르는 폴더에서 에이전트를 열지 말고 받은 지침 파일은 읽고 쓰며 훅으로 행동을 검사하라고 권한다.
- 현실 적용:
  - 압축 파일이나 GitHub 코드를 받아 `cd` 후 바로 `claude`를 켜는 개인 개발자 → 켜기 전에 그 폴더와 부모 폴더의 지침·설정 파일을 훑어 `curl … | sh`, `base64 -d`, 토큰 경로 읽기 같은 줄을 찾는 사전 점검을 쉘 함수로 둔다 → 모르는 지침 파일이 첫 프롬프트에서 실행되기 전에 사람이 본다
  - 외부 기여자 PR 브랜치를 로컬에서 열어 리뷰하는 메인테이너 → 체크아웃 직후 PR이 건드린 지침·설정·훅 파일만 diff로 골라 점검 결과를 PR 코멘트 초안으로 만든다 → 코드는 멀쩡한데 지침 파일에 지시가 숨은 PR을 리뷰 단계에서 잡는다
  - 신입에게 "이 레포 받아서 돌려 보세요"라고 안내하는 팀 → 온보딩 문서에 "처음 여는 폴더는 위 점검을 통과해야 `claude` 실행" 한 줄과 점검 명령을 넣는다 → 누가 올린 샘플 레포든 같은 절차로 연다
  - `~/.claude/settings.json`에 훅·허용 규칙을 쌓아 둔 사람 → 폴더 점검과 함께 전역 설정에 낯선 `hooks`·`permissions.allow`·`env`가 있는지 목록으로 뽑아 주 1회 눈으로 확인한다 → 에이전트가 몰래 고친 전역 설정이 몇 주 뒤에야 발견되는 일을 줄인다
  - 이 저장소의 `daily-lab`이 도는 Actions 러너 → 체크아웃된 저장소 루트의 지침·설정 파일이 허용 목록(`CLAUDE.md`, `.claude/skills/daily-lab/**`)과 다르면 실행을 거부하는 단계를 둔다 → 푸시 권한이 있는 러너가 모르는 지침을 따르는 경로를 닫는다

## 3. 자동 압축 22건 중 진짜 압축은 12건 — 절반은 한 턴에 컨텍스트가 폭증해서였고, 어드바이저 호출 턴에서 컨텍스트가 약 2.05배 → 2.20배로 커졌다. 전부 `requestId`로 중복을 걷어야 사용량이 1.9배 부풀지 않는다
- 날짜: 2026-10-27
- 출처: https://dev.to/sungwoo_lee_e0f26be4a29fd/claude-code-auto-compact-12-of-22-drops-were-real-half-were-one-turn-1aab
- 요약: 두 프로젝트에서 컨텍스트가 갑자기 줄어든 22번을 분석하니 진짜 자동 압축은 12번뿐이고, 3번은 어드바이저(전체 대화를 받는 더 강한 모델) 왕복 뒤 되돌아온 것, 7번은 세션 재개 때문에 생긴 착시였다. 진짜 압축의 절반은 천천히 쌓여서가 아니라 한 턴에 컨텍스트가 폭증해 일어났고, 모두 어드바이저가 불린 턴이었다. 구분 기준은 캐시 쓰기 크기(약 5만 이상이면 진짜 압축, 1만 이하면 어드바이저 왕복)이고, 압축 한 번에 약 8.5만~12.5만 토큰이 든다. 줄이는 순서는 어드바이저 덜 부르기, 파일 통째로 읽기 피하기, 도구 출력 줄이기, 고정 머리(지침·메모리) 줄이기다.
- 현실 적용:
  - 하루 몇 번 자동 압축이 나는지 모르는 개인 개발자 → 어제 트랜스크립트를 `requestId`로 중복 제거하고 캐시 쓰기 5만 이상인 하락만 세어 "오늘 진짜 압축 N번"을 뽑는다 → 압축 때문에 날리는 토큰이 하루 몇 만인지 숫자로 안다
  - 123KB 로그를 통째 읽게 시키던 사람 → 그 턴의 컨텍스트 증가량을 점검해 한 턴 +3만 토큰 넘는 읽기를 찾아 `offset`/`limit`이나 `grep`으로 바꾼다 → 압축 여유 공간이 한 번에 사라지는 일을 막는다
  - 어드바이저를 항상 켜 둔 팀 → 압축 직전 턴이 어드바이저 호출 턴인 비율을 보고, 비가역 작업(스키마 변경·배포)에서만 부르도록 지침을 고친다 → 같은 품질을 유지하면서 압축 횟수를 반으로 줄인다
  - CLAUDE.md와 메모리가 합쳐 9만 바이트 가까이 되는 사람 → 고정 머리 크기와 압축 후 바닥(약 9.1만~13만 토큰)을 나란히 적고 규칙 중 안 쓰는 줄을 지운다 → 압축할 때마다 되돌려 읽는 고정 비용이 줄어든다
  - 이 저장소의 `cache-break`(10-24) 옆 → 압축 전후 하락을 "진짜 압축 / 어드바이저 왕복 / 재개 착시"로 가르는 출력 모드를 후속 이슈로 쓴다 → 캐시 낭비와 압축 낭비를 한 도구에서 구분한다

## 4. Google Cloud에서 Claude Code 비용 관리·ROI 입증 가이드 — Claude apps 게이트웨이의 사용자·IdP 그룹별 일·주·월 한도, 한도 75%·95%에서 CLI 경고, 한도에서는 429, 지표는 PR당 비용이 아니라 "작업당 비용"
- 날짜: 2026-10-27
- 출처: https://claude.com/resources/articles/how-to-manage-costs-and-demonstrate-roi-for-claude-code-on-google-cloud
- 요약: 조직이 Claude Code 비용을 관리하고 효과를 보여 주는 방법을 정리한 글이다. 게이트웨이에서 사용자·IdP 그룹·조직별로 일·주·월 한도를 걸 수 있고(그룹·조직 한도는 공유 풀이 아니라 개발자별 기본값), 75%와 95%에서 CLI가 경고하며 한도에 닿으면 HTTP 429로 막힌다. 모델 기본값과 허용 목록은 서버가 매 요청마다 강제하고, OpenTelemetry 지표로 사용자·모델·스킬·플러그인·에이전트·MCP 서버별 사용량과 추정 비용을 본다. 효과는 도입 전 기준선과 비교해 PR 소요 시간, 리뷰 반복 횟수, 엔지니어당 병합 PR로 보고, 비용 지표는 작업당 비용을 권한다.
- 현실 적용:
  - 혼자 Claude Code 구독을 쓰는 개인 개발자 → 한 주 동안 `/usage`나 트랜스크립트로 하루 사용량을 적고 "75% 경고선·95% 차단선"을 내 한도에 직접 그어 둔다 → 한도에 막히기 전에 그날 작업 순서를 바꾼다
  - 개발자 20명에게 Claude Code를 처음 푸는 팀장 → 팀 한도를 걸기 전에 `OTEL_RESOURCE_ATTRIBUTES`에 `cost_center=팀명`을 넣어 2주 동안 쓰기만 하고 상위 사용자 3명의 스킬·MCP별 비용을 본다 → 한도를 감이 아니라 실제 분포로 정한다
  - "AI 도입 효과를 보여 달라"는 요청을 받은 리드 → 도입 전 4주의 PR 소요 시간·리뷰 반복 수를 먼저 뽑아 두고, 같은 종류의 PR(예: 버그 수정)만 세어 비교한다 → 모든 PR을 섞어 평균을 내서 효과가 희석되는 일을 피한다
  - 부서마다 쓸 수 있는 모델이 달라야 하는 운영자 → 그룹별 모델 허용 목록을 표로 만들어 기본은 중간 모델, 큰 모델은 설계·리뷰 그룹에만 연다 → 비용이 큰 모델이 단순 수정에 쓰이는 것을 서버에서 막는다
  - 이 저장소의 `spend-gate`(10-13) → 75%·95% 두 단계 경고와 차단을 같은 설정 파일로 넣을 수 있는지 보고 두 번째 임계를 후속으로 쓴다 → 차단만 있던 장치에 미리 알림이 생겨 한도 직전에 작업을 정리할 수 있다

## 5. Anthropic이 Claude를 Claude로 내보내는 방식 (latent.space 대담) — 두뇌와 손을 분리하고, 비밀값은 샌드박스에 두지 않고 송신 프록시가 끼워 넣으며, 큰 이식은 그림자 트래픽 비교로 검증한다
- 날짜: 2026-10-27
- 출처: https://latent.space/p/opus55/
- 요약: Anthropic 엔지니어들이 모델을 안전하게 내보내는 방식을 설명한 대담이다. 하네스와 세션 기록은 지속되는 서버에 두고 코드 실행은 필요할 때만 뜨는 별도 샌드박스에 맡겨, 샌드박스가 죽어도 세션이 산다. 비밀값은 별도 금고에 두고 에이전트에게는 자리표시자만 보이며, 송신 프록시가 나가는 요청에서 진짜 값을 끼워 넣어 생성된 코드가 비밀값을 못 본다. 네트워크는 기본 차단 또는 도메인 허용 목록이고, Messages API의 Rust 재작성은 그림자 트래픽을 두 시스템에 흘려 출력을 비교하고 기능 플래그로 배포하되 이식 중에는 새 기능을 넣지 않았다고 한다.
- 현실 적용:
  - `.env`에 실제 API 키를 두고 에이전트를 돌리는 개인 개발자 → 에이전트가 쓰는 셸에는 `API_KEY=__PLACEHOLDER__`만 주고, 실제 값은 명령 직전에 치환하는 래퍼 한 개를 만든다 → 에이전트가 만든 코드·로그에 진짜 키가 남지 않는다
  - 에이전트 샌드박스의 외부 접속을 열어 둔 팀 → 외부 도메인 허용 목록을 패키지 저장소와 사내 API 두세 개로 줄이고, 막힌 요청 로그를 일주일 모아 필요한 도메인만 추가한다 → 생성된 코드가 임의의 서버로 나가는 길이 닫힌다
  - 큰 의존성·언어 이식을 앞둔 팀 → 새 구현이 준비되면 실제 요청 복사본을 두 구현에 보내 응답 차이를 로그로 비교하고 차이가 0에 가까울 때 플래그로 5%부터 전환한다 → 배포 날에야 터지는 동작 차이를 미리 본다
  - 에이전트 하네스가 세션 상태를 프로세스 안에만 둔 개발자 → 대화 기록을 파일(JSONL)로 이어 쓰고 실행기는 매번 새로 띄우게 나눠 본다 → 실행기가 죽어도 마지막 기록부터 이어 간다
  - 이 저장소의 `secret-envoy`(10-11) → 자리표시자 치환이 명령 인자뿐 아니라 환경 변수 주입에도 되는지 점검하고 안 되면 후속으로 쓴다 → 비밀값이 에이전트 눈에 닿는 경로가 하나 줄어든다
