## 1. Claude Code 2.1.319 — 권한 확인창 대신 거절하는 `permissions.denyInsteadOfPrompting`, MCP 작업(task)을 백그라운드로 보내기, 자동(auto) 모드 점검 불가 시 `claude -p`가 exit 1, `/claude-api latency-optimize`, 피처 플래그만 끄는 `CLAUDE_CODE_DISABLE_FEATURE_FLAGS`
- 날짜: 2026-11-06
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.319 (Agent SDK: https://github.com/anthropics/claude-agent-sdk-python/releases/tag/v0.2.179, https://github.com/anthropics/claude-agent-sdk-typescript/releases/tag/v0.3.319)
- 요약: 권한 확인창에서 멈출 도구 호출을 대신 거절하고 턴을 이어 가게 하는 설정(`permissions.denyInsteadOfPrompting`)이 터미널 세션·서브에이전트·팀원 모두에 추가됐다. 자동 모드는 텔레메트리나 피처 플래그가 꺼져 있거나 LLM 게이트웨이 뒤에 있으면 서버가 확인하지 못하는 호출을 묻거나 거절하며, `claude -p`는 안전 점검을 못 해 행동이 거절됐을 때 예전엔 0으로 끝났지만 이제 텍스트·JSON 출력 모두 exit 1이다. MCP 서버가 도구 호출을 task로 돌리면 곧바로 백그라운드로 옮기고 끝나면 알려 주며, `CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND`로 끌 수 있다. Bash deny·ask 규칙이 따옴표 낀 단어로 쓴 명령을 놓치던 버그도 고쳤다.
- 현실 적용:
  - 밤새 `claude -p`를 돌리는 개인 개발자 → 어젯밤 세션 기록(JSONL)의 도구 호출을 내 `settings.json` 규칙에 대 보고 "이 설정을 켰다면 거절됐을 호출" 목록을 뽑는다 → 켜기 전에 allow 규칙 몇 줄을 보태야 할지 알고, 밤사이 조용히 거절되는 일을 막는다
  - GitHub Actions에서 Claude를 부르는 플랫폼 팀 → 워크플로 마지막에 `claude -p` 종료 코드가 1이면 이슈를 올리는 단계를 넣는다 → 자동 모드가 점검 불가로 거절했는데 초록 체크로 끝나던 날을 없앤다
  - 사내 LLM 게이트웨이를 운영하는 인프라 담당 → `CLAUDE_CODE_AUTO_MODE_SERVER`를 0·1로 바꿔 보며 `/status`와 `claude -p` 종료 코드가 어떻게 달라지는지 표로 남긴다 → 게이트웨이 도입 뒤 자동 모드가 왜 거절하는지 사용자 문의에 바로 답한다
  - 이 저장소의 `/daily-lab` 루틴(클라우드·Actions) → `permissions.denyInsteadOfPrompting`을 켜고도 필요한 도구가 allow에 다 들어 있는지 점검한다 → 사람 없는 자리에서 확인창에 걸려 멈추는 하루를 막는다
  - MCP 서버를 만드는 개발자 → 오래 걸리는 도구를 task로 돌리게 바꾸고 백그라운드 완료 알림이 오는지 시험한다 → 긴 도구 호출이 대화를 막지 않는다

## 2. dev.to 11-06 "Claude Code on zsh: 7,795 Commands Broke, 5,559 Still Exited 0" — 세션 기록 32일치 분석: Bash 호출 166,430건 중 7,795건이 zsh에서만 나는 확장 오류를 냈고 그중 71%는 종료 코드가 0
- 날짜: 2026-11-06
- 출처: https://dev.to/ji_ai/claude-code-on-zsh-7795-commands-broke-5559-still-exited-0-37i9
- 요약: 글쓴이는 macOS에서 Claude Code 2.1.319로 10-06~11-06의 세션 기록을 읽어 따옴표 없는 `grep --include=*.ts`(4,489건, 97%가 exit 0)와 `echo ======`(1,973건)가 zsh에서 "no matches found"로 실패하는 비율을 셌다. 명령이 실행조차 안 됐는데도 뒤따르는 명령이 돌아 성공처럼 보이고, 에이전트가 같은 실수를 반복한 기록 비율은 61%였다. `CLAUDE_CODE_SHELL=/bin/bash`로 두 유형이 사라졌다고 하나, 글쓴이 한 사람의 환경 측정이라 일반화는 조심해야 한다.
- 현실 적용:
  - macOS에서 Claude Code를 쓰는 개발자 → `~/.claude/projects/*.jsonl`에서 tool_result 안의 `no matches found`·`(eval):1:` 줄을 세는 스크립트로 내 비율을 잰다 → 소문이 아니라 내 환경의 낭비를 안다
  - 프로젝트 CLAUDE.md를 관리하는 팀 리드 → "grep의 `--include=` 값과 `=====` 구분선은 항상 따옴표로 감싼다" 한 줄을 넣고 전후 비율을 비교한다 → 같은 실수 반복을 줄인다
  - 종료 코드로 에이전트 성공을 판정하는 CI 담당 → 종료 코드 0이어도 결과 텍스트에 zsh 오류 줄이 있으면 실패로 보는 PostToolUse 훅을 만든다 → 실행 안 된 검사를 통과로 세는 일을 막는다
  - 무인 야간 작업을 돌리는 개인 개발자 → `CLAUDE_CODE_SHELL=/bin/bash`를 켠 날과 안 켠 날의 실패 호출 수를 비교한다 → 설정 하나로 줄었는지 숫자로 확인한다
  - 이 저장소의 `hook-exit-audit`(10-19)·`run-receipt`(10-27) → "exit 0인데 실패"를 잡는 검사 목록에 셸 확장 오류 패턴을 후보로 올린다 → 종료 코드를 믿는 도구들의 사각지대를 하나 줄인다
