## 1. Claude Ship 베타 — Claude Code `/ship`, PR을 리뷰·수정하는 PR Steward, 저장소의 정책 파일로 승인 여부를 정하는 Claude Approvals

- 날짜: 2026-11-23
- 출처: https://claude.com/resources/articles/introducing-claude-ship
- 요약: Claude Ship은 이미 정식인 Code Review에 베타 에이전트 둘을 더한 묶음이다. PR Steward는 실패한 CI·머지 충돌·리뷰 지적에 대응해 푸시하고 바꾼 내용과 되돌리는 법을 댓글로 남기며(승인·머지는 하지 않는다), Claude Approvals는 팀이 저장소에 파일로 둔 승인 정책을 읽어 일상적인 변경은 Claude가 승인하고 민감한 변경은 사람의 승인을 요구한다. 개발자는 Claude Code에서 `/ship`을 치면 푸시·PR 열기·리뷰·피드백 대응까지 이어지고, 관리자는 저장소 단위로 켜며 처음에는 관찰 모드로 돌리길 권한다. Team·Enterprise 플랜의 GitHub 저장소 전용이고 ZDR·HIPAA 구성·고객 관리 암호화 키 조직에서는 못 쓰며, 사용량은 토큰으로 과금된다.
- 현실 적용:
  - 혼자 쓰는 사이드 프로젝트 저장소를 가진 개인 개발자 → 다음 기능 브랜치가 끝났을 때 `/ship`을 쳐서 푸시부터 CI 실패 대응까지 한 번에 맡기고 걸린 시간을 기존 수동 흐름과 비교한다 → 푸시·PR 작성·리뷰 대기를 오가는 컨텍스트 전환을 줄인다
  - 승인 규칙이 CODEOWNERS 하나뿐인 5인 팀 → 저장소 루트에 정책 파일을 관찰 모드로 먼저 올리고 일주일 동안 "Claude였다면 승인했을 PR"과 실제 사람 승인을 대조한다 → 켜기 전에 오탐·누락 비율을 숫자로 안다
  - 의존성 갱신 PR이 하루 열 건씩 쌓이는 플랫폼 팀 → 의존성 봇이 연 PR 중 리뷰가 통과한 것만 사람 0명으로 승인하도록 정책 한 줄을 쓴다 → 사람이 락파일 diff를 읽는 반복 작업이 사라진다
  - 결제·인증 코드가 한 저장소에 섞인 회사의 보안 담당 → 그 경로에만 두 사람 승인을 요구하는 규칙을 따로 두고 나머지는 Claude 승인을 허용한다 → 위험이 큰 곳에만 사람 시간을 쓴다
  - 이 저장소(`claude-daily-lab`)의 일일 푸시 → 정책 파일이 어떤 변경을 어떻게 판정할지 PR을 열기 전에 손으로 시뮬레이션해 보는 도구를 만든다 → 정책을 서버에 올린 뒤에야 "예상과 다른 판정"을 발견하는 일을 피한다
  - 월 지출 상한을 정해야 하는 엔지니어링 매니저 → 저장소 한 곳에서만 Code Review를 Standard로 켜고 한 달 뒤 PR당 비용과 되돌린 PR 비율을 본다 → 전 저장소에 켜기 전에 비용 대비 효과를 확인한다

## 2. Claude Code v2.1.331 — 트레이스 스팬에 `gen_ai.usage.*` 추가, 플러그인 매니페스트에 `optionalDependencies`, `claude doctor`의 API 연결 점검

- 날짜: 2026-11-23 (UTC 21:34 릴리스, 한국 시각 11-24 새벽)
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.331
- 요약: `claude_code.llm_request` 트레이스 스팬에 `gen_ai.usage.*`·`gen_ai.response.model`·`gen_ai.operation.name` 속성이 붙었고, 입력 토큰 값에는 프롬프트 캐시 토큰이 포함된다. 플러그인 매니페스트에 `optionalDependencies`가 생겨 함께 설치되되 따로 끄거나 지울 수 있는 플러그인을 선언할 수 있고, `claude doctor`에 API에 닿는지와 HTTP 상태를 알려 주는 연결 절이 생겼다. 프록시가 압축 응답을 끊을 때 쓰는 `CLAUDE_CODE_DISABLE_RESPONSE_COMPRESSION`, Bedrock·Foundry 등에서의 Code Mode 지원, Stop 훅이 마지막 응답을 놓치던 문제와 `/compact`가 요약 일부를 잃던 문제의 수정도 들어 있다.
- 현실 적용:
  - 사내 OpenTelemetry 수집기를 이미 운영하는 플랫폼 팀 → 스팬의 `gen_ai.usage.input_tokens`를 팀·저장소 라벨별로 집계하는 대시보드 패널을 하나 만든다 → 로그 파싱 없이 표준 속성으로 토큰 사용을 본다
  - 캐시 적중률을 따지는 개인 개발자 → 스팬 값에 캐시 토큰이 합산돼 있다는 점을 고려해 "입력 토큰 대비 캐시 읽기" 비율 계산식을 다시 쓴다 → 합산 정의를 모르고 적중률을 과대·과소 계산하는 일을 막는다
  - 회사 프록시 뒤에서 응답이 가끔 끊긴다는 불만이 있는 팀 → `claude doctor`의 새 연결 절 출력을 이슈에 붙이고, 끊김이 계속되면 응답 압축 비활성화 변수를 한 번 켜 본다 → "네트워크 문제 같다"는 추측 대신 상태 코드로 원인을 가른다
  - 훅으로 마지막 응답을 읽어 알림·기록을 남기는 사람 → 11-23 이전 버전에서 Stop 훅이 마지막 응답을 놓친 적이 있는지 기록을 열어 보고 업그레이드 후 같은 기록과 비교한다 → 빠졌던 응답 때문에 요약·알림이 어긋난 곳을 찾는다
  - 플러그인을 배포하는 팀 → 필수 아닌 보조 플러그인(예: 린트 도우미)을 `optionalDependencies`로 옮기는 매니페스트 초안을 만든다 → 사용자가 보조 기능만 따로 끌 수 있어 항의가 줄어든다
  - 이 저장소의 `cache-break`·`ctx-growth` → 트랜스크립트 대신 스팬 속성에서도 같은 값을 읽을 수 있는지 필드 이름 대응표만 먼저 적는다 → 도구가 한 가지 입력 형식에 묶이는 것을 줄인다

## 4. Enterprise Frontier Safeguards(EFS) 베타 — 데이터를 보관하지 않는 ZDR과 오용 탐지를 함께 쓰되, 암호화된 안전 데이터 사본은 고객 클라우드 버킷에 둔다

- 날짜: 2026-11-23
- 출처: https://claude.com/resources/articles/zero-data-retention-with-enterprise-frontier-safeguards
- 요약: EFS는 가장 능력이 높은 모델을 쓰는 ZDR 대상 조직에 정교한 오용 탐지를 붙이되 Anthropic이 프롬프트·응답을 보관하지 않게 하는 구성이다. 암호화된 사본(Sealed Safety Data)은 고객의 자기 클라우드 계정 버킷으로 가고, Claude Platform·AWS의 Claude Platform·Google Cloud의 Claude 모델에서 베타로 쓸 수 있다. 같은 날 발표된 Claude Ship은 ZDR 조직에서 쓸 수 없다고 못 박고 있어, 두 기능을 같은 조직에서 함께 쓸 수 없다는 제약이 생긴다.
- 현실 적용:
  - 금융·의료 고객 데이터를 다루는 팀의 보안 담당 → 지금 계약이 ZDR인지 확인하고 EFS 신청 때 필요한 버킷·키 항목을 체크리스트로 적는다 → 베타 신청 때 필요한 준비물을 한 번에 모은다
  - Claude Ship을 도입하려던 엔지니어링 매니저 → 조직이 ZDR·HIPAA 구성·고객 관리 키 중 하나에 해당하는지 먼저 확인하고 해당하면 Ship 대신 기존 Code Review 흐름을 계획한다 → 도입 결정 뒤에야 사용 불가를 알게 되는 일을 막는다
  - 감사 대응을 맡은 컴플라이언스 팀 → 안전 데이터 사본이 어느 계정·어느 리전 버킷에 쌓이는지를 데이터 흐름도 한 장으로 그린다 → 감사관이 묻는 "대화 기록은 누가 갖고 있나"에 도식으로 답한다
  - 버킷 비용을 걱정하는 인프라 담당 → 하루 요청 수에 요청당 평균 크기를 곱해 한 달 저장량을 추정하고 수명 주기 규칙 초안을 쓴다 → 보관하지 않는 쪽 대신 고객이 보관하게 된 사본의 저장 비용을 예측한다
  - 이 저장소의 `/daily-lab-apply` 단계 → 적용안에서 "조직 설정(ZDR·HIPAA)에 따라 못 쓰는 기능" 조건을 근거 항목으로 적도록 확인 목록에 한 줄을 더한다 → 쓸 수 없는 기능을 적용안으로 올리는 일을 줄인다

- 현실 적용:
  - 훅을 만들어 배포하는 개발자 → 자기 훅이 출력에 싣는 값 목록을 README에 "무엇을 싣고 무엇을 싣지 않는지"로 정리한다 → 사용자가 훅을 켜기 전에 데이터 범위를 판단할 수 있다
  - 사내 정책상 원격 측정을 끄는 보안팀 → 새 절이 가리키는 변수들을 관리형 설정에 넣고, 끈 뒤에도 플러그인이 리뷰를 계속 도는지 한 저장소에서 확인한다 → "지표를 끄면 보안 리뷰까지 꺼지는지" 모호함을 없앤다
  - 훅이 실패하면 첫 줄만 보인다는 점을 모르고 긴 오류를 쓰는 사람 → 자기 훅의 실패 메시지를 첫 줄에 원인을 넣는 형태로 바꾸고 `echo '{...}' | python3`로 시험한다 → 터미널에서 잘려 원인이 안 보이는 일을 막는다
  - 파이썬 버전 관리자(pyenv 등)를 쓰는 개발자 → 훅이 시작되지 않을 때 `python3 --version`·`python --version`·`py -3 --version`을 차례로 쳐 어느 쪽이 버전 관리자의 shim(대리 실행 파일)인지 가린다 → "파이썬이 없다"로 오해해 재설치하는 시간을 아낀다
  - 이 저장소의 훅 도구들(`hook-merge`·`matcher-lint`) → 훅 출력에 비밀값·경로를 싣지 않는다는 점을 검사하는 항목을 테스트에 하나 더한다 → 훅 로그와 대화 기록에 민감한 값이 사본으로 남는 일을 줄인다
