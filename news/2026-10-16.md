## 1. Code Review가 정식 출시(GA) — 리뷰 3배 빨라지고 Quick·Standard·Deep 선택, `REVIEW.md`로 조정
- 날짜: 2026-10-15
- 출처: https://claude.com/resources/articles/code-review-is-now-generally-available
- 요약: GitHub PR을 여러 에이전트가 읽고 검증 단계를 거쳐 인라인 코멘트로 알려 주는 Code Review가 Team·Enterprise에서 연구 프리뷰를 끝내고 정식 출시됐다. 대부분의 리뷰가 약 20분에서 6~10분으로 빨라졌고, 관리자가 저장소마다 Quick·Standard·Deep 중 깊이를 고른다. 문서에 따르면 결과는 🔴 Important·🟡 Nit·🟣 Pre-existing 세 등급이며, `Claude Code Review` 체크런은 실패로 끝나지 않고 본문 마지막 줄의 `bughunter-severity` 주석에 등급별 개수가 들어 있어 CI에서 읽어 병합 게이트로 쓸 수 있다.
- 현실 적용:
  - 병합 규칙을 직접 관리하는 저장소 관리자 → CI 잡이 `gh api`로 `Claude Code Review` 체크런을 읽어 Important가 1개 이상이면 잡을 실패시킨다 → 리뷰는 절대 차단하지 않는다는 기본 동작 위에 우리 팀 기준의 병합 관문을 얹는다
  - 리뷰가 안 끝났거나 실패한 PR을 놓치기 싫은 팀 → 개수 줄이 없는 체크런을 "0개"가 아니라 "판정 없음"으로 따로 처리해 재실행 안내를 띄운다 → 리뷰가 타임아웃된 PR이 조용히 통과하는 사고를 막는다
  - 니트가 너무 많아 리뷰를 무시하게 된 팀 → 기본 브랜치 루트에 `REVIEW.md`를 넣고 "니트는 최대 5개, 생성 파일 제외"를 적은 뒤 병합한다 → 같은 PR에서 고친 `REVIEW.md`는 적용되지 않으므로 병합 먼저 해야 한다는 함정을 피한다
  - 결제·인증 코드를 따로 두는 모노레포 → `services/billing/REVIEW.md`에 테넌트 범위 쿼리·로그에 PII 금지 같은 추가 점검을 적는다 → 중요 경로만 더 엄격하게 보고 나머지는 Quick 수준으로 둔다
  - 이 저장소의 daily-lab 루틴 → 결과물 폴더 PR이 생기면 `@claude review` 한 번으로 리뷰를 받고 개수만 요약 메일에 한 줄 붙인다 → 하루 한 개 실험물의 숨은 버그를 사람 눈 전에 한 번 걸러낸다

## 2. Claude Code 2.1.301: OTel `tool_decision`에 분류기 판정 추가, `fable` 별칭 폴백, 모델 전환 시 요약
- 날짜: 2026-10-15
- 출처: https://code.claude.com/docs/en/changelog
- 요약: OpenTelemetry `tool_decision` 이벤트에 `classifier_verdict`·`permission_mode`가 붙어 자동 모드 분류기의 결정과 권한 규칙의 결정을 구분할 수 있고, `OTEL_LOG_TOOL_DETAILS=1`이면 어떤 내장 규칙에 걸렸는지 `classifier_category`로 나온다. 최신 Fable 모델을 쓸 수 없는 조직에서 `fable`·`best` 별칭이 오류 나던 문제는 이전 Fable 모델로 한 번 재시도하도록 고쳐졌고, 컨텍스트가 작은 모델로 바꿀 때는 대화를 이전 모델이 먼저 요약한다. 모드에는 여러 줄 `rows` 입력과 훅 `.catch` 동작 변경이 들어갔다.
- 현실 적용:
  - 자동 모드를 쓰는 개인 개발자 → 로컬 OTel 수신기에서 `tool_decision`을 `classifier_verdict`별로 센다 → 분류기가 막은 도구 호출과 내 권한 규칙이 막은 호출을 구분해 규칙을 정리한다
  - 보안팀 → `OTEL_LOG_TOOL_DETAILS=1`로 `classifier_category`를 수집해 자주 걸리는 내장 규칙 상위 5개를 뽑는다 → 허용 목록을 늘릴지 프롬프트를 고칠지 근거가 생긴다
  - 모델을 자주 바꾸는 사람 → 큰 컨텍스트 세션에서 작은 모델로 전환하기 전에 `/context`로 길이를 확인한다 → 요약에 쓰이는 이전 모델 호출을 의식하고 불필요한 전환을 줄인다
  - 조직에서 모델 롤아웃이 단계적인 팀 → 스크립트가 `fable` 별칭 대신 고정 모델 ID를 쓰고 있는지 점검한다 → 별칭 폴백에 기대어 모르는 사이 이전 모델로 도는 일을 막는다
  - 모드를 만드는 개발자 → `Input`의 `rows`로 여러 줄 프롬프트 편집기를 붙인다 → 긴 지시문을 터미널에서 줄바꿈하며 쓸 수 있다

## 4. 스킬은 설명만 항상 로드된다 — `SKILL.md` 단계별 작성법과 1,536자·`skillOverrides` 규칙
- 날짜: 2026-10-15
- 출처: https://dev.to/gabrielanhaia/write-a-claude-code-skill-that-loads-only-when-its-needed-skillmd-step-by-step-44n6
- 요약: 스킬은 이름과 설명만 시작 때 컨텍스트에 올라가고, 본문은 설명이 요청과 맞을 때만, 번들 파일은 읽을 때만 로드된다고 정리한다. `description`과 `when_to_use`는 합쳐 1,536자에서 잘리므로 핵심 용례를 앞에 쓰고, 이름이 겹치는 요청에 잘못 켜지면 제외 조건을 적으라고 한다. 문서로 확인한 사실은 `skillOverrides`(`on`·`name-only`·`user-invocable-only`·`off`), 앞머리 YAML이 깨지면 스킬은 로드되지만 필드가 비어 있다는 점, 앞머리는 첫 줄이 `---`일 때만 읽힌다는 점이다.
- 현실 적용:
  - 스킬을 20개 넘게 설치한 개인 개발자 → 스킬 폴더를 훑어 설명이 1,536자를 넘거나 YAML이 깨진 것을 목록으로 뽑는다 → 설명이 잘려 호출이 안 되는 스킬과 몰래 비어 있는 스킬을 찾는다
  - 팀 공용 스킬 저장소 → PR마다 `SKILL.md` 앞머리를 검사하는 CI 잡을 둔다 → 설명에 `: `가 따옴표 없이 들어가 앞머리가 통째로 무효가 되는 실수를 병합 전에 잡는다
  - 컨텍스트 예산을 아끼려는 팀 → 거의 안 쓰는 스킬을 `skillOverrides`에서 `name-only`로 내린다 → 매 세션 설명 토큰을 줄이고 필요하면 직접 호출한다
  - 이 저장소의 `/daily-lab` 스킬 → 설명 길이와 앞머리 파싱을 테스트에 넣는다 → 스킬 수정 때 루틴이 조용히 안 켜지는 사고를 막는다
  - 플러그인을 배포하는 사람 → 설명 첫 문장에 사용자가 실제로 치는 표현을 넣었는지 점검 항목을 만든다 → 자동 호출률이 올라 문서 없이도 쓰인다

## 5. 에이전트가 이전 결정을 뒤집는 다섯 가지 이유 — 결정과 이유를 세션 밖에 적어 두고 압축 뒤 다시 주입
- 날짜: 2026-10-15
- 출처: https://dev.to/alfredoizjr/why-ai-coding-agents-contradict-earlier-decisions-and-how-to-stop-it-33hf
- 요약: 결정이 닫힌 채팅에만 있거나, 압축에서 빠지거나, 도구마다 규칙 파일이 따로이거나, 규칙 파일이 낡았거나, "무엇"만 적고 "왜"를 안 적어서 에이전트가 결정을 뒤집는다고 정리한다. 처방은 결정 한 건당 이유 한 문장을 트랜스크립트 밖에 저장하고, 압축 뒤 훅으로 다시 주입하는 것이다. 작성자는 이 방식의 한계로 저장한 것만 기억하고 낡은 결정이 남을 수 있다는 점을 인정한다.
- 현실 적용:
  - 장기 프로젝트를 혼자 하는 개발자 → `DECISIONS.md`에 날짜·결정·이유 한 문장을 적고 `CLAUDE.md`가 이를 가리키게 한다 → "캐시 레이어를 왜 뺐나"를 다음 세션이 다시 묻지 않는다
  - 압축이 잦은 대형 세션 → 압축 뒤 최근 결정 3개를 다시 출력하는 훅을 건다 → 요약에서 빠진 결정 때문에 같은 논쟁을 반복하는 시간을 줄인다
  - 도구를 섞어 쓰는 팀 → 규칙 파일들을 한 문서에서 생성하거나 한 곳을 가리키게 한다 → 도구마다 규칙이 달라 같은 코드를 서로 되돌리는 일을 막는다
  - 낡은 규칙이 쌓인 저장소 → 결정에 날짜를 달고 분기마다 오래된 것을 지운다 → 에이전트가 바뀐 코드와 어긋난 옛 규칙을 믿는 문제를 줄인다
  - 이 저장소의 daily-lab 루틴 → 루트 README 표의 "다음 후보" 이유를 결정 로그로 남긴다 → 어제 보류한 주제를 이유 없이 오늘 다시 뽑는 일을 막는다
