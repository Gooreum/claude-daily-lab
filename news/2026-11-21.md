- 날짜: 2026-11-20

- 요약: `claude auth login` 뒤에 Enterprise Admin Console이 관리하는 조직의 설정과 클라우드·게이트웨이 경로를 그대로 적용하는 로그인이 생겼다. 내장 모드 easel이 요청하거나 MCP 지표 결과가 나오면 차트를 그리며 `/config`에서 끌 수 있다. 위험한 `rm`(루트·홈·최상위 폴더·작업 폴더 대상)은 더 넓게 승인을 묻고 물어볼 사람이 없으면 거절하며, 반복 예약 작업과 `/loop`는 세션이 살아 있는 한 7일 대신 30일까지 돈다. prompt 훅의 `model` 필드에 `haiku`·`sonnet` 같은 별칭을 쓸 수 있고, "유효한 훅 명령을 Edit가 거부하던" 문제, 여러 프로세스가 동시에 저장하며 사용자 설정이 사라지던 문제, SessionStart 훅이 쓴 환경 변수가 `claude -p --continue`에서 사라지던 문제가 고쳐졌다.

  - `claude -p`를 크론·CI에서 무인으로 돌리는 사람 → 스크립트가 `rm`을 쓰는 단계를 찾아 대상이 작업 폴더·최상위 폴더인 것을 임시 폴더 하위 경로로 바꾼다 → 물어볼 사람이 없을 때 거절돼 파이프라인이 중간에 멈추는 일을 막는다
  - 밤새 `/loop`로 일일 점검을 돌리는 개인 개발자 → 시작 전 `/tasks`에서 종료 예정일(30일 뒤)을 확인하고 달력에 만료 하루 전 알림을 넣는다 → 한 달 뒤 조용히 끝난 점검을 며칠 뒤에야 아는 일을 막는다
  - 분기마다 훅 비용을 줄이고 싶은 팀 → 프롬프트 훅의 `model`을 전체 모델 ID에서 `haiku` 별칭으로 바꾸고 일주일 판정 건수를 비교한다 → 모델 ID를 올릴 때마다 설정 파일 여러 곳을 고치던 수고를 없앤다
  - 이 저장소의 `/daily-lab` 루틴 → 스킬이 로컬 실행 전 점검으로 쓰는 `claude --version`이 2.1.330 이상인지 확인하는 한 줄을 README에 넣는다 → 새 루트 `rm` 확인 때문에 무인 실행이 멈추는 구간을 미리 안다
  - Enterprise Admin Console을 쓰는 회사 → 신입 한 명을 `claude auth login`으로 조직 로그인시키고 `/status`에서 적용된 설정 출처를 캡처해 온보딩 문서에 붙인다 → 처음 쓰는 사람이 조직 정책이 적용됐는지 직접 확인하는 방법이 생긴다

## 2. claude-agent-sdk-typescript v0.3.330 (11-20) — 설정 파일이 검증에 실패해 적용되지 않으면 `settings_not_in_effect` 경고가 오고, `settings`가 파싱 안 되는 JSON 문자열이면 `query()`가 오류를 낸다
- 날짜: 2026-11-20
- 출처: https://github.com/anthropics/claude-agent-sdk-typescript/releases/tag/v0.3.330
- 요약: SDK가 사용자·프로젝트·로컬 설정 파일이 검증에 실패해 적용되지 않을 때 `settings_not_in_effect` 태그가 붙은 시스템 경고를 보낸다. 지난 v0.3.329의 `managed_hooks_not_loaded`(관리형 훅 로드 실패)와 같은 계열로, 설정 하나가 깨지면 조용히 기본값으로 떨어지던 길을 사람이 볼 수 있게 한 것이다. `query()`의 `settings`에 문자열 JSON을 넘겼는데 파싱이 안 되면 이제 오류로 끝난다(전에는 무시되는지 문서에 없다). 같은 릴리스가 SessionStart 훅이 `CLAUDE_ENV_FILE`에 쓴 변수가 `continue`와 함께 Bash 도구에 전달되지 않던 문제, `stopTask()`가 막 끝난 백그라운드 에이전트를 기다리던 문제도 고쳤다.
- 현실 적용:
  - 프로젝트 `.claude/settings.json`에 `permissions.deny`와 가드 훅을 모아 둔 개인 개발자 → 커밋 전에 파일이 설정으로 로드되는지 기계로 확인하는 점검을 훅이나 `git pre-commit`에 넣는다 → 쉼표 하나 때문에 deny와 가드가 통째로 꺼진 채 몇 주를 보내는 일을 막는다
  - Agent SDK로 에이전트를 만들어 `settings`를 문자열로 조립해 넘기는 개발자 → 문자열을 넘기기 전에 `JSON.parse`로 먼저 시험하는 테스트 한 개를 추가한다 → 0.3.330에서 `query()`가 던지는 오류를 운영에서 처음 만나는 일을 막는다
  - SDK 메시지 스트림을 로그로 남기는 서비스 → `system` 메시지 중 `settings_not_in_effect`·`managed_hooks_not_loaded` 태그를 따로 세어 알림으로 보낸다 → 세션은 도는데 정책만 꺼진 상태를 대시보드에서 바로 본다
  - 팀 공용 `.claude/settings.json`을 PR로 받는 리드 → PR마다 CI에서 변경된 설정 파일을 JSON으로 파싱하고 훅·권한 모양을 점검하는 단계를 추가한다 → 리뷰어가 눈으로 쉼표를 세지 않아도 깨진 설정이 머지되지 않는다
  - SessionStart 훅으로 `CLAUDE_ENV_FILE`에 환경 변수를 쓰는 사람 → 2.1.330 이상에서 `claude -p --continue`로 변수가 Bash까지 오는지 `echo $MY_VAR` 한 줄로 확인한다 → 이어 하기에서만 비밀이 빠져 명령이 실패하는 일을 미리 찾는다
  - 이 저장소의 훅 점검 도구 모음(`matcher-lint`·`hook-merge`) → 훅 하나가 아니라 "설정 파일이 로드되는가"를 보는 점검을 앞에 하나 더한다 → matcher를 아무리 잘 짜도 파일이 안 읽히면 전부 헛수고라는 점을 숫자로 보인다

## 3. dev.to 11-20 Embers — 서브에이전트는 5분 캐시라 늦게 돌아오면 컨텍스트를 25배 값으로 다시 쓰고, `subagentPromptCacheTtl`(1시간)은 재작성이 쓰기의 약 38.5%를 넘어야 이득이다
- 날짜: 2026-11-20
- 출처: https://dev.to/ev3nt1ne/where-my-claude-code-usage-went-subagents-i-came-back-to-too-late-3md0
- 요약: 글쓴이는 11-05~11-19의 트랜스크립트 134개 서브에이전트에서 캐시에 10만 토큰 이상 쓰고 직전보다 10만 토큰 이상 덜 읽은 "차가운 재작성"을 24건(약 850만 토큰, 정가로 56.17달러, 서브에이전트 비용의 11.4%) 찾았다. 구독의 메인 대화는 캐시가 1시간이지만 서브에이전트는 5분이라, 5분 넘게 도구를 기다리면 전체 컨텍스트를 읽기 값의 25배(Opus 5.5 기준)로 다시 쓴다. 이슈 #103309·#99808에서는 테스트가 10~15분 도는 동안 생긴 재작성이 다수였고, 해결 설정 `subagentPromptCacheTtl`은 쓰기 값이 1.25배에서 2배로 올라 글쓴이 데이터에서는 재작성 비율 24.8%가 손익분기 38.5%에 못 미쳐 오히려 손해였다. 이 문제를 줄이려고 서브에이전트 캐시를 따뜻하게 유지하는 플러그인 Embers를 공개했다.
- 현실 적용:
  - 서브에이전트로 테스트·린트를 돌리는 개인 개발자 → 지난 2주 트랜스크립트에서 서브에이전트별 "쓰기 10만 이상·읽기 10만 이상 감소" 건수와 쓰기 대비 비율을 뽑아 38.5%와 비교한다 → `subagentPromptCacheTtl`을 켤지 말지를 감이 아니라 내 숫자로 정한다
  - 10분짜리 테스트 스위트를 서브에이전트가 실행하는 팀 → 그 서브에이전트는 테스트를 `run_in_background`로 돌리고 짧게 폴링하도록 정의 파일에 한 줄을 넣는다 → 5분 캐시가 만료되는 구간을 서브에이전트가 가만히 기다리며 지나는 일을 줄인다
  - 구독 한도가 주말 전에 바닥나는 사람 → 한도가 급감한 세션의 서브에이전트 파일에서 직전 요청과 시간 간격이 5분 넘는 요청을 찾아 어느 도구 호출 뒤인지 본다 → 비용이 큰 도구(Bash 테스트, 빌드)를 알아내 그 호출만 따로 다룬다
  - API 키로 서브에이전트를 쓰는 회사 → 모든 서브에이전트가 5분 캐시인 점을 전제로, 도구 대기가 5분을 넘을 수 있는 서브에이전트를 목록으로 만들고 담당자에게 알린다 → 키 사용료에서 가장 큰 항목이 반복되는 재작성인지 확인한다
  - 이 저장소의 `cache-break` 도구 → 서브에이전트별로 "1시간 캐시가 이득인가"를 손익분기와 함께 한 줄로 출력하는 보고를 더한다 → 어제까지는 "재작성이 있었다"만 알았는데 "켜면 얼마 버는가"까지 안다

## 4. anthropic-sdk-python v2.12.0 · anthropic-sdk-typescript sdk-v1.12.0 · bedrock-sdk-v1.1.3 (11-20) — Bedrock의 `user_profile_id`가 헤더가 아니라 본문으로 가고, 지원 안 하는 모델은 400, `image_dimensions_too_large` 오류 코드 추가
- 날짜: 2026-11-20
- 출처: https://github.com/anthropics/anthropic-sdk-python/releases/tag/v2.12.0
- 요약: Amazon Bedrock은 `user_profile_id`를 요청 본문에서만 읽고 `anthropic-user-profile-id` 헤더는 무시해 왔다. 그래서 두 SDK의 Bedrock 클라이언트로 준 프로필 ID는 그동안 적용되지 않았고, 이제 SDK가 헤더 대신 Messages 요청 본문에 넣는다. 사용자 프로필을 지원하지 않는 Bedrock 모델에 프로필 ID를 보내면 전에는 무시되던 요청이 이제 400으로 실패한다. API에는 `image_dimensions_too_large` 오류 코드가 추가됐고, TypeScript는 `ANTHROPIC_CUSTOM_HEADERS`를 `defaultHeaders`와 합치도록 고쳤다.
- 현실 적용:
  - Bedrock으로 Claude를 호출하며 사용자 프로필 ID를 넘기던 서비스 → 호출 코드에서 `user_profile_id`를 쓰는 곳을 검색해 모델별로 지원 여부를 확인하고 지원 안 하는 모델 호출에서는 ID를 뺀다 → 올린 날부터 일부 모델 호출이 400으로 바뀌는 일을 배포 전에 막는다

## 오늘의 선정
- 2번 Agent SDK 0.3.330의 `settings_not_in_effect` — 설정 파일이 검증에 실패해 적용되지 않으면 그 파일에 든 deny 규칙·훅이 통째로 꺼진다. 이를 실행 전에 미리 보는 CLI **`settings-live`**를 만든다: JSON 오류(위치·원인 힌트)·중복 키(뒤에 나온 값만 남음)·권한/훅/env의 모양·오타 키·없는 훅 스크립트를 점검하고, "이 파일이 안 읽히면 꺼지는 deny N·훅 M개"를 보여 준다.
- 이유: `matcher-lint`·`hook-exit-audit`·`hook-merge`는 파일이 로드된다는 전제로 훅 하나하나를 본다. 파일이 로드되지 않는 경우는 아무 도구도 보지 않아 이 저장소의 가드가 모두 헛수고가 될 수 있다. 키·모델 없이 깨진 설정 예제만으로 전부 시험할 수 있다.
