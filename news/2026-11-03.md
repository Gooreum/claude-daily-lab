## 1. Messages API message threads 베타 공식 공지 — `thread` 한 줄로 대화를 서버에 두고 다음 턴부터 새 메시지만 보내며, 5분 지나면 만료돼 404가 나므로 전체 대화를 다시 보내는 경로(replay)를 처음부터 만들어야 한다 (후속: 10-24 3번의 SDK 지원)
- 날짜: 2026-11-02
- 출처: https://platform.claude.com/docs/en/release-notes/overview (상세: https://platform.claude.com/docs/en/build-with-claude/message-threads)
- 요약: 긴 대화와 에이전트 루프에서 요청이 작아지고 첫 토큰이 빨라지는 베타(`message-threads-2026-08-12` 헤더)가 공식 공지됐다. 첫 요청에 `"thread": {"type": "create"}`를 넣어 전체 대화를 보내고, 이후엔 `{"type": "continue", "previous_message_id": ...}`와 새 메시지만 보낸다. 규칙이 촘촘하다: `system`·`tools`는 create에만(continue에 넣으면 400), `model`·`thinking`·`tool_choice` 등은 매 요청 같은 값(다르면 `thread_fingerprint_mismatch`), 응답 id는 한 번만 이어 갈 수 있고, 마지막 요청 5분 뒤 만료, 캐시 중단점은 4개까지다. 앱이 원본 대화를 직접 보관해야 한다.
- 현실 적용:
  - 고객 지원 챗봇을 만드는 백엔드 개발자 → 요청 로그를 JSONL로 남기고, 문서의 규칙(continue에 `system` 금지, 고정 필드 동일, 응답 id 한 번만 이어가기)으로 훑는 린터를 오늘 로그에 돌린다 → 베타 전환 전에 400을 낼 요청 코드를 찾는다
  - 에이전트 루프를 도는 팀(턴당 도구 결과가 수만 토큰) → 같은 작업을 일반 방식과 thread 방식으로 열 번씩 돌려 요청 바이트와 첫 토큰 시간을 표로 비교한다 → 전환할 가치가 있는 작업과 아닌 작업을 숫자로 가른다
  - 대화가 5분 넘게 멈추는 상담·코칭 앱 개발자 → 마지막 요청 시각이 5분을 넘은 continue를 린터가 경고하게 하고, 404면 create로 다시 보내는 분기에 테스트를 붙인다 → 사용자가 자리를 비웠다 돌아온 순간의 오류를 막는다
  - 스트리밍 응답을 쓰는 프런트 개발자 → `message_stop` 전에 다음 continue를 보내는 코드를 로그의 시각 순서로 찾아낸다 → 문서가 경고한 404를 재현 전에 잡는다
  - 이 저장소의 `cost-top`(10-30) 같은 API 호출 도구 → 호출 로그를 읽어 "thread로 바꾸면 줄 요청 바이트"를 계산하는 옵션을 후속 후보로 올린다 → 전환 효과를 호출 전에 추정한다

## 2. Claude Code 2.1.317 — Agent SDK 훅 콜백에 `onFailure: "block"`, 계정 이메일을 네트워크로 보내기 전 확인, OTel에 플랜·좌석 종류 속성, 게이트웨이 비용 보고서 API (Python SDK 0.2.177의 `on_failure="block"` 동반)
- 날짜: 2026-11-03
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.317 (SDK: https://github.com/anthropics/claude-agent-sdk-python/releases/tag/v0.2.177)
- 요약: SDK 훅 콜백이 예외를 내거나 `None`을 돌려주거나 CLI가 거절하는 값을 줘도 지금까지는 "결정 없음"으로 넘어가 동작이 실행됐는데, `onFailure: "block"`(Python은 `on_failure="block"`)을 주면 그 동작을 막는다. 기본값은 `continue`이고, 옛 CLI에 붙여 쓰면 연결 오류가 난다. 그 밖에 웹·셸 도구 호출이 계정 이메일을 네트워크로 보내려 하면 먼저 묻고, OTel 지표·이벤트·스팬에 `anthropic.plan`·`anthropic.seat_type` 등이 붙으며, `claude -p`가 디스크가 가득 차 기록을 잃으면 0이 아니라 1로 끝난다.
- 현실 적용:
  - SDK로 사내 코드 에이전트를 만든 개발자 → 위험 명령 검사 콜백에 `on_failure="block"`을 켜고 콜백이 일부러 예외를 내는 테스트 한 개를 붙인다 → 검사기가 죽은 날 위험 동작이 그대로 실행되는 구멍을 닫는다
  - 이미 `PreToolUse` 가드를 SDK 콜백으로 쓰는 팀 → 콜백이 `None`을 돌려줄 수 있는 분기(조건 누락)를 코드에서 찾아 모두 명시적 allow/deny로 바꾼다 → 옛 기본값(`continue`)에서 조용히 통과하던 경로를 없앤다
  - 야간 무인 `claude -p`를 도는 운영자 → 종료 코드 1을 알림 조건에 추가하고 디스크 여유가 부족한 러너에서 한 번 재현해 본다 → 기록이 사라졌는데 성공으로 보이던 실행을 구분한다
  - 팀 단위 OTel 대시보드 담당자 → `anthropic.plan`·`anthropic.seat_type`으로 지표를 쪼개 좌석 종류별 토큰 사용량 패널을 한 개 만든다 → 좌석 구성을 바꿀 때 근거 숫자를 얻는다
  - 이 저장소의 `hook-manners`(11-02)·`hook-exit-audit`(10-19) → 훅 점검 도구가 SDK 콜백 방식의 실패 정책은 보지 않으니 settings 훅과 SDK 콜백의 차이를 README 6절 후속으로 적는다 → 두 점검 도구의 사각지대가 문서에 남는다

## 3. Python SDK 2.4.0·TypeScript SDK 1.4.0 — 분석·지출 한도·RBAC 정식(GA) 메서드, 세션 오류 타입 `tool_use_limit_reached_error`·`compaction_limit_reached_error` 추가
- 날짜: 2026-11-02
- 출처: https://github.com/anthropics/anthropic-sdk-python/releases/tag/v2.4.0 (TS: https://github.com/anthropics/anthropic-sdk-typescript/releases/tag/sdk-v1.4.0)
- 요약: 두 SDK가 같은 날 나와 분석(analytics)·지출 한도(spend limits)·RBAC의 GA 메서드를 더하고, `group_by`·지출 한도 기간 필터 타입과 외부 키·워크스페이스의 `user_profile_id`를 추가했다. 관리형 에이전트 세션에는 도구 사용 한도와 압축 한도에 닿았음을 알리는 오류 타입 두 개가 생겼다. 지출 한도 증가 요청 승인 응답의 `spend_limit`은 null일 수 있게 고쳐졌다.
- 현실 적용:
  - 조직 관리자 → 10-30에 본 분석 API 호출 스크립트를 베타 헤더 없이 GA 메서드로 바꾸고 응답 필드가 같은지 한 번 비교한다 → 베타 헤더 폐기 때 깨질 코드를 미리 없앤다
  - 부서별로 API 비용을 나눠 관리하는 재무 담당 → 지출 한도 GA 메서드로 워크스페이스별 한도를 읽어 월 말 리포트에 "한도 대비 사용률" 열을 넣는다 → 한도에 닿기 전에 부서에 알린다
  - 관리형 에이전트 세션을 운영하는 팀 → 새 오류 두 개를 에러 핸들러의 분기에 추가해 "도구 한도"와 "압축 한도"를 서로 다른 알림 문구로 나눈다 → 같은 "세션 실패"로 뭉뚱그려 원인을 찾던 시간을 줄인다
  - 외부 키를 쓰는 보안 담당 → `user_profile_id`로 키 소유자를 읽어 퇴사자 키 목록을 뽑는 점검을 월 1회로 정한다 → 주인 없는 키를 찾는다
  - 이 저장소 → SDK 2.x 이전에 만든 `cost-top` 계열이 쓰는 호출 방식을 README 6절에서 GA 메서드로 옮길 후속 후보로 남긴다 → 레거시 경로 의존을 기록해 둔다

## 4. claude-cookbooks에 latency optimization 쿡북 — 모의 보험 청구 에이전트에 지연 줄이는 방법을 하나씩 적용하며 첫 토큰·마지막 토큰 시간과 정확도를 함께 재고 "정확도 기준을 넘는 가장 빠른 설정"을 고른다
- 날짜: 2026-11-02
- 출처: https://github.com/anthropics/claude-cookbooks/commits/main.atom (커밋 "feat(latency_optimization): add latency optimization cookbook (#957)")
- 요약: 에이전트 속도를 높이되 품질을 깎지 않는 평가 중심 가이드다. 합성 데이터로 만든 모의 청구 에이전트에 Claude API의 지연 줄이기 수단을 하나씩 적용하며 첫 토큰 시간, 마지막 토큰 시간, 정확도를 기록하고, 정확도 기준을 만족하는 가장 빠른 조합으로 끝난다. 같은 날 쿡북 전체가 Haiku 5.5와 2.0 SDK 기준으로 정비됐다.
- 현실 적용:
  - 사내 문서 Q&A 봇 담당자 → 쿡북 방식대로 질문 30개와 정답 기준을 만들고 모델·노력도 설정을 바꿔 가며 지연과 정확도를 한 표에 적는다 → "빠르게"가 아니라 "정확도 90% 넘는 가장 빠른 설정"으로 결정한다
  - 이 저장소의 루틴을 돌리는 사람 → `claude -p … --model claude-haiku-5-5 --effort low` 기본값을 실제 실행 10번의 소요 시간과 비교 측정해 README에 남긴다 → 기본값이 감이 아니라 숫자에 근거한다
  - 모바일 앱의 채팅 기능 개발자 → 첫 토큰 시간만 재던 로그에 마지막 토큰 시간 열을 추가한다 → 체감은 빠른데 완료는 느린 요청을 가려낸다
  - 쿡북 예제를 복사해 쓰던 개발자 → Haiku 5.5 정비 커밋의 변경 파일을 보고 자기 코드의 모델 ID와 SDK 호출 방식을 같이 고친다 → 오래된 예제 그대로 쓰다 생기는 오류를 줄인다
  - 에이전트 평가를 처음 만드는 팀 → 쿡북의 "합성 데이터와 로그를 노트북 옆에 두는" 구조를 따라 폴더 하나로 재현 가능한 평가를 만든다 → 남에게 결과를 넘길 때 같은 숫자를 다시 얻는다

## 오늘의 선정
- 1번 message threads의 첫 적용안을 고른다. 문서의 요청 규칙(create 전용 필드, 고정 필드, 응답 id 한 번만 이어가기, 만료, 캐시 중단점 4개)을 키 없이 요청 로그에 적용하는 린터 `thread-lint`를 만든다.
- 이유: 규칙이 많고 어기면 400·404가 나는 새 API라 로컬 점검 도구의 가치가 크다. 2번은 SDK 버전이 필요하고, 3·4번은 호출·측정이 필요해 키 없이 검증하기 어렵다.
