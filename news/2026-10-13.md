## 1. 동적 워크플로(flows): 리드 에이전트가 오케스트레이션 프로그램을 직접 쓴다
- 날짜: 2026-10-12
- 출처: https://www.latent.space/p/claude-dynamic-workflows
- 요약: Managed Agents의 새 멀티 에이전트 기능(10-09 API 릴리스 노트, 베타)을 설명한 글이다. 개발자가 코디네이터와 고정 서브에이전트 목록을 짜는 대신, 리드 에이전트가 작업을 어떻게 쪼갤지 계획하고 에이전트를 띄우고 결과를 모으는 프로그램을 쓴다. 하위 에이전트는 컨텍스트가 분리되고 파일시스템만 공유하며, 단계별 핸드오프 내용은 Console 그래프 뷰에서 볼 수 있다. 단일 에이전트보다 비용이 훨씬 커서 세션 예산을 걸라고 권한다.
- 현실 적용:
  - 회사의 대규모 마이그레이션(수백 개 서비스의 SDK 교체) → 서비스별 하위 에이전트를 flow로 띄우고 세션 예산을 먼저 정한다 → 한 번에 끝나는 일괄 처리에서 비용 폭주를 예산이 끊는다
  - 이 저장소의 daily-lab → 수집(소스 20개)을 flow의 병렬 단계로, 선정·제작은 직렬 단계로 설계해 본다 → 지금 순차로 읽는 소스 점검 시간이 줄어든다
  - 개인 블로그 번역 파이프라인 → 글 하나당 번역·검수·링크 점검 에이전트를 단계로 나눈다 → 핸드오프 payload를 그래프 뷰에서 보고 어느 단계가 품질을 깎는지 찾는다
  - 신규 팀원 온보딩 → 코드베이스 질문 100개를 하위 에이전트에 나눠 던지고 파일시스템에 답변 파일로 모은다 → 사람이 며칠 걸려 쓰던 FAQ 초안을 반나절에 얻는다
  - 팀의 비용 통제 → flow를 쓰기 전 "세션당 상한 $N" 규칙을 문서화하고 상한 훅·콘솔 한도를 짝으로 둔다 → 에이전트가 에이전트를 부르는 구조의 청구서 사고를 막는다

## 2. 코드가 검사할 수 있는 규칙은 프롬프트에서 빼라 — 지시문 56KB → 32KB
- 날짜: 2026-10-13
- 출처: https://dev.to/kevinccbsg/prose-does-not-beat-determinism-stop-asking-your-ai-agent-to-remember-29di
- 요약: 에이전트에게 테스트 작성 규칙을 세 번씩 적어도 `await` 누락이 반복되자, 규칙을 기계가 검사하는 쪽으로 옮긴 사례다. 테스트 전에 TypeScript 컴파일러를 먼저 돌리고, 자동 수정과 안내 메시지가 있는 커스텀 린터를 두고, 콘솔 로그 대신 구조화된 JSON 테스트 리포트를 에이전트에게 줬다. 지시문이 56KB에서 32KB로, 강한 금지어 사용이 13회에서 1회로 줄었고, 린터를 494개 테스트 파일에 돌리니 쓸모없는 규칙 하나가 드러나 지워졌다.
- 현실 적용:
  - 팀 CLAUDE.md → "NEVER/ALWAYS" 문장을 세어 그중 린터·훅으로 옮길 수 있는 것을 표로 만든다 → 컨텍스트가 줄고 어겨도 조용히 지나가던 규칙이 실패로 드러난다
  - 이 저장소 RULES.md → "시크릿 패턴이 없어야 한다" 같은 재확인 항목을 `pre-push` 스크립트로 옮긴다 → 루틴이 사람 없이 돌 때 규칙 위반이 푸시 전에 막힌다
  - 회사 프론트엔드 → PostToolUse 훅이 `tsc --noEmit`을 먼저 돌려 오류를 exit 2로 돌려준다 → 타입 오류를 느린 브라우저 테스트 전에 잡는다
  - 린터를 새로 만들 때 → 기존 코드 수백 파일에 돌려 걸리는 것이 모두 실제 버그인지 본다 → 통과하는 코드를 막는 규칙을 배포 전에 지운다
  - CI 로그가 긴 서비스 → 테스트 결과를 JSON 리포트로 출력하는 옵션을 켜 에이전트에게 그 파일만 읽게 한다 → 로그 꼬리 절단으로 원인이 잘리는 일이 없다

## 3. 서브에이전트가 쓰는 모델은 Agent 호출의 `model`이 이긴다 — 25번 중 21번 opus
- 날짜: 2026-10-13
- 출처: https://dev.to/kruhlikau/your-claude-code-subagents-probably-pick-their-own-model-i-built-a-mod-to-take-that-back-2k2k
- 요약: Claude Code가 서브에이전트 모델을 정하는 순서에서, 호출한 에이전트가 Agent 도구 호출에 직접 넣은 `model`이 에이전트 프론트매터·`CLAUDE_CODE_SUBAGENT_MODEL` 환경변수·메인 모델보다 앞선다는 점을 정리했다. 저자의 세션 두 개에서 Agent 호출 25번 중 21번이 `model: "opus"`를 명시했고, CLAUDE.md에 "리뷰는 Opus"라고 적어 둔 게 기본값 변경을 덮어썼다. 이를 가로채 모델과 effort를 바꾸는 모드(`subagent-tuner`)를 만들었지만 절감액은 측정하지 않았다고 밝혔다.
- 현실 적용:
  - 비용에 민감한 개인 계정 → 오늘 세션 jsonl에서 Agent 호출의 `model` 필드를 집계한다 → 기본값을 Sonnet으로 바꿔 놓고도 Opus로 도는 호출이 얼마나 되는지 숫자로 안다
  - 팀 CLAUDE.md → "리뷰는 Opus로" 같은 모델 지정 문장을 찾아 의도한 것인지 점검한다 → 설정과 문서가 충돌해 비용이 새는 원인을 없앤다
  - PreToolUse 훅 → `Agent` 호출의 `tool_input.model`이 허용 목록 밖이면 exit 2로 돌려보낸다 → 모드 없이 훅 하나로 서브에이전트 모델 정책을 강제
  - 이 저장소의 daily-lab 수집 → 서브에이전트 정의에 `model: haiku`를 명시하고 훅으로 상향 호출을 막는다 → 소스 읽기처럼 단순한 일에 비싼 모델이 쓰이지 않는다
  - 월말 비용 리뷰 → 세션별 모델 사용 비율을 표로 뽑아 팀 회의에서 본다 → "왜 이번 달이 비쌌나"를 추측이 아닌 기록으로 답한다

## 4. Claude Code에는 내장 금액 상한이 없다 — 하드 캡은 제공자 쪽, 훅은 호출 수만 센다
- 날짜: 2026-10-13
- 출처: https://dev.to/akaranjkar08/claude-code-spend-limit-hard-caps-that-stop-a-runaway-bill-1ihi
- 요약: 폭주하는 에이전트 청구서를 막는 수단을 정리한 글이다. 하드 캡은 Anthropic Console의 조직·워크스페이스 한도처럼 제공자 쪽에서 걸어야 하고(둘 중 낮은 쪽 적용), Claude Code에는 문서화된 금액 한도가 없어 가장 가까운 것이 하루 도구 호출 수(예시 1,500회)를 세는 PreToolUse 훅이다. 워크스페이스 한도 $50이면 캐시 없는 Opus 5.5 재시도 루프를 약 26분(78턴) 뒤에 멈추지만, 캐시가 맞으면 네 시간까지 간다. 한도 집행 지연과 훅 크래시 시 fail-open도 한계로 든다.
- 현실 적용:
  - 개인 API 키로 `claude -p` 자동화를 돌리는 사람 → Console 워크스페이스에 월 한도를 오늘 건다 → 새벽 재시도 루프가 계정을 비우는 사고를 제공자가 막아 준다
  - 팀 공용 워크스페이스 → 자동화용과 개발자용 워크스페이스를 나누고 자동화 쪽 한도를 낮게 둔다 → 한 CI 작업의 폭주가 사람 작업까지 막지 않는다
  - 세션 단위 보호가 필요할 때 → 트랜스크립트 `usage`로 비용을 추정해 세션·일 상한을 넘으면 PreToolUse에서 막는 훅을 둔다 → 호출 수가 아니라 달러로 멈춘다(오늘 만들 대상)
  - 훅이 죽으면 통과하는 문제 → `onFailure: "block"`(2.1.295)을 같이 걸어 fail-closed로 만든다 → 가드가 고장 나도 비용 통제가 풀리지 않는다
  - 이 저장소의 GitHub Actions 루틴 → 실행당 비용 상한을 훅으로 걸고 초과하면 요약 이슈에 적는다 → 매일 도는 자동화의 최악 비용이 숫자로 정해진다

## 5. Claude Code 세션끼리 `SendMessage`로 팀처럼 일한다
- 날짜: 2026-10-13
- 출처: https://dev.to/anyesh/my-claude-code-sessions-work-as-a-team-and-they-message-each-other-18b8
- 요약: 내장 `ListAgents`와 `SendMessage`로 같은 기기의 세션들이 서로를 찾아 로컬 유닉스 소켓으로 텍스트를 주고받는 구성을 소개한다. 받는 세션은 다음 도구 라운드에서 교차 세션 태그가 붙은 메시지를 보고, 상태·핸드오프 파일과 공유 인박스 파일로 세션이 끝난 뒤에도 남는 정보를 둔다. 세션을 재시작하면 소켓이 바뀌어 옛 주소로의 전송이 실패하고, 메시지가 엉뚱한 세션에 가거나 같은 일을 중복하는 한계가 있다.
- 현실 적용:
  - 백엔드·프론트 두 저장소를 동시에 고치는 개인 프로젝트 → API 계약이 바뀌면 백엔드 세션이 프론트 세션에 변경 요약을 보낸다 → 두 창을 오가며 복사하던 설명이 사라진다
  - 장시간 마이그레이션 → 진행 세션과 리뷰 세션을 분리하고 리뷰 세션이 `SendMessage`로 지적을 보낸다 → 작성자 컨텍스트가 오염되지 않은 채 리뷰가 들어온다
  - 세션이 여럿인 기기 → 세션 ID 키의 핸드오프 요약 파일을 규칙으로 정한다 → 재시작으로 주소가 바뀌어도 파일로 이어 받는다
  - 병렬 세션이 같은 이름으로 커밋하는 문제 → 세션별 `GIT_AUTHOR_NAME`을 훅으로 넣는다 → 어느 세션이 만든 커밋인지 로그에서 구분된다
  - 회사 온콜 → 장애 대응 세션과 로그 분석 세션을 나눠 분석 결과만 메시지로 받는다 → 대응 세션의 컨텍스트에 로그 수천 줄이 쌓이지 않는다

## 6. claude-bulkhead: 병렬 세션이 서로의 프로세스·포트·메모리를 침범하지 않게 막는 플러그인
- 날짜: 2026-10-13
- 출처: https://news.hada.io/topic?id=35290 (저장소: https://github.com/Myeongseok-Kang/claude-bulkhead)
- 요약: git worktree마다 Claude Code 세션을 병렬로 돌리는 PC에서, 셸 명령 실행 직전에 다른 세션이 쓰는 프로세스·포트·남은 메모리를 확인하는 플러그인이다. 이름 기준 프로세스 종료, 점유된 포트에 개발 서버 실행, 메모리가 모자란 상태의 빌드, 다른 세션 폴더에서의 checkout·reset은 실행 전에 차단하고 대안을 안내한다. 세션이 끝난 뒤 남은 개발 서버·테스트 프로세스는 몇 초 안에 정리하고, 무거운 작업을 SSH로 다른 PC에 보내는 옵션도 있다. 정상 명령이 잘못 막힐 수 있다고 작성자가 밝혔다.
- 현실 적용:
  - worktree 세 개로 기능을 병렬 개발하는 사람 → 세션마다 포트 대역을 할당하는 PreToolUse 훅을 둔다 → `EADDRINUSE`로 서로의 dev 서버를 죽이는 일이 사라진다
  - 16GB 노트북 → 빌드·테스트 전에 `/proc/meminfo` 여유를 확인하는 훅을 건다 → 동시 빌드 두 개가 스왑으로 노트북을 멈추는 것을 막는다
  - `pkill node`를 자주 쓰는 에이전트 → 이름 기준 종료를 PID 기준으로 바꾸게 하는 차단 규칙을 넣는다 → 다른 세션의 서버까지 죽이지 않는다
  - 세션 종료 시 → Stop 훅에서 그 세션이 띄운 자식 프로세스만 정리한다 → 밤새 남은 테스트 러너가 CPU를 잡는 일이 없다
  - 팀 공용 빌드 서버 → 사용자별이 아닌 세션별 락 파일로 무거운 작업을 직렬화한다 → 병렬 에이전트가 CI 서버를 한꺼번에 눌러 느려지는 것을 줄인다

  - 동시성 코드 리뷰 → 에이전트가 쓴 락 제거 패치는 해제 후 재사용(RCU 같은 유예)이 있는지 체크리스트로 본다 → 성능 이득의 대가로 생기는 레이스를 놓치지 않는다
  - 개인 오픈소스 → 에이전트 작업을 `*-with-llm` 같은 별도 브랜치에 두고 PR 설명에 측정 환경을 적는다 → 메인테이너가 병합 전에 재현해 볼 수 있다
  - 회사의 레거시 C/C++ 코드 → 핫패스 하나만 골라 같은 방식(측정 → 패치 → 재측정)으로 시도한다 → 큰 리팩터링 없이 에이전트 효용을 한 곳에서 증명한다

## 9. AI 코딩 에이전트 세팅이 실패하는 15가지 패턴
- 날짜: 2026-10-13
- 출처: https://news.hada.io/topic?id=35266 (원문: https://adrianstudio3.hashnode.dev/15-ways-ai-coding-agents-fail-in-real-repos-and-the-guardrails-that-fix-them)
- 요약: Claude Code·Codex·Gemini CLI를 몇 주 쓰면 작업량은 많은데 반영된 결과가 없는 경우가 생기며, 이는 모델보다 운영 설정 문제라는 글이다. 증거 없는 완료 보고에는 실행한 명령과 결과를 완료 기준에 넣고 같은 문제의 수정 시도를 3회로 제한하라고 한다. 도구별 지침 불일치는 AGENTS.md 한 곳에 두고 CLAUDE.md가 불러오게 하며, 위험 명령은 프롬프트 금지가 아니라 PreToolUse 훅으로 막고, 리뷰어 서브에이전트에는 Edit를 주지 말라고 한다.
- 현실 적용:
  - 팀의 "완료" 정의 → PR 템플릿에 실행한 명령과 출력 붙이기 칸을 넣는다 → 에이전트의 "다 됐습니다"가 증거 없이 머지되는 것을 막는다
  - 같은 오류를 맴도는 세션 → 동일 실패 3회째에 Stop 훅이 멈추고 사람에게 묻게 한다 → 반복 시도로 토큰이 타는 것을 끊는다
  - AGENTS.md와 CLAUDE.md가 갈라진 저장소 → CI에서 CLAUDE.md가 `@AGENTS.md`를 불러오는지 grep으로 검사한다 → 도구마다 다른 규칙으로 일하는 일이 없다
  - 리뷰 서브에이전트 정의 → `tools:`에서 Edit·Write를 빼고 린터로 확인한다 → 리뷰어가 몰래 코드를 고쳐 놓는 일을 없앤다
  - 이 저장소의 daily-lab → 완료 보고 3줄에 테스트 통과 수를 항상 쓴다는 규칙을 이미 따르므로, 실패 시 "시도한 것 3개"도 README 6절에 적게 한다 → 막힌 날의 기록이 다음 날 재시도의 출발점이 된다
