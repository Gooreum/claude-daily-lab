## 1. Claude Enterprise에서 Chat과 Cowork가 하나로 — 모드를 고르지 않고 대화하다가 코드·파일 작업이 필요하면 클라우드 환경이 이어받고, 관리자에게는 Efficient mode·모델 권한·그룹 예산이 생겼다
- 날짜: 2026-10-23
- 출처: https://claude.com/resources/articles/unified-claude-enterprise
- 요약: Enterprise 플랜에서 Chat과 Cowork가 웹·데스크톱·모바일 모두 하나의 경험으로 합쳐져 정식 출시됐다. 대화는 채팅으로 시작하고, 코드나 파일이 필요해지면 Claude가 클라우드 환경에서 이어 작업한 뒤 결과를 돌려주며, 노트북을 닫아도 계속 돌고 다른 기기에서 이어 볼 수 있다. 관리자는 조직 설정에서 롤아웃을 켜고, 역할별 접근, Sonnet·Haiku에 머무르게 하는 Efficient mode, 역할별 모델 권한, 조직·그룹·구성원 단위 지출 한도, 그룹이 월 예산을 함께 쓰는 풀링 예산을 쓴다. 데이터 보관 제로, HIPAA 대응 구성, 고객 관리 암호화 키를 쓰는 조직은 기존 구성에 남는다.
- 현실 적용:
  - Enterprise 관리자 → 롤아웃 전에 역할(개발·법무·영업)별로 쓸 모델을 표로 정하고 모델 권한에 그대로 입력한다 → 비싼 모델이 전원 기본값이 되는 일을 첫날부터 막는다
  - 부서별 비용을 책임지는 재무 담당 → 그룹마다 월 예산을 풀링으로 정하고, 지난 석 달 사용량 중앙값의 1.5배를 시작값으로 둔다 → 한 사람의 폭주가 부서 전체 예산을 한 주 안에 태우는 일을 막는다
  - 보안 담당 → 데이터 보관 제로·HIPAA 구성이라 기존 구성에 남는 조직 단위를 목록으로 뽑아 사용자에게 "합쳐진 화면이 안 보이는 이유" 안내문을 미리 보낸다 → 롤아웃 날 문의가 몰리는 것을 줄인다
  - 클라우드 작업이 낯선 팀 리드 → 팀원 두 명에게 "노트북을 닫고 퇴근했다가 아침에 결과를 확인"하는 장면을 하루 시험하게 하고 결과물이 완성됐는지 기록한다 → 오래 도는 작업을 맡겨도 되는 종류를 팀 규칙으로 정한다
  - 이 저장소의 루틴 → 같은 조직 설정으로 Claude Code 클라우드 세션 권한을 역할로 나눈 2.1.310의 기능과 묶어 "누가 Routine을 만들 수 있나" 표를 README 부록에 남긴다 → 06:45 자동 실행을 만들 권한이 누구에게 있는지 한눈에 본다

## 2. Claude Code 2.1.310(후속: 2.1.309 일부) — Monitor 도구가 Bedrock·Vertex·Foundry에서도 되고, bypass 모드는 위험한 `rm`을 즉시 거부하며, `cleanupPeriodDays`를 크게 잡으면 최근 파일이 지워지던 버그가 고쳐졌다
- 날짜: 2026-10-23
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.310
- 요약: 2.1.310은 Monitor 도구와 플러그인 monitor를 클라우드 제공자 경로와 텔레메트리 끈 환경에서도 쓰게 하고, `effort-2025-11-24` 베타 값이나 대화 중간 시스템 메시지를 거부하는 게이트웨이에서는 그것을 빼고 재시도한다. `cleanupPeriodDays`가 아주 클 때 붙여넣은 이미지 같은 최근 파일을 지우던 문제, "Prompt is too long" 뒤 압축이 base64·SVG 같은 빽빽한 글을 너무 많이 남기던 문제, 읽기 권한 프롬프트가 심볼릭 링크의 도착지를 안 보여 주던 문제, Windows에서 따옴표 문자열뿐인 훅 명령이 Git Bash가 없을 때 도구 호출을 통과시키던 문제도 고쳤다. 어제 요약에 없던 2.1.309 내용으로, bypass 권한 모드에서 위험한 `rm`·`rmdir`이 되물음 없이 거부되고 다시 쓸 명령을 안내하며, `claude ultrareview`가 작업공간 신뢰를 요구해 스크립트는 `--trust-workspace`가 필요하고, `sed -i`는 일반 Bash 명령으로 취급되고, 작업 트리 생성이 git 객체를 그때그때 받지 않는다. 비대화형 세션에서 MCP 도구 호출이 시간 초과되면 Claude에게 "답이 오지 않았으니 같은 호출을 반복하지 말라"고 알린다.
- 현실 적용:

  - `cleanupPeriodDays`를 99999로 올려 대화 기록을 오래 보관해 온 사람 → 2.1.310 전후로 `~/.claude` 아래 붙여넣은 이미지 개수를 세어 사라진 것이 있는지 확인한다 → 지워진 첨부가 있는지 알고 보관 설정을 재점검한다

## 4. Claude Duet 안전·개인정보·보안(후속: 2026-10-22 news 4번 Duet 연구 프리뷰) — 승인 검사는 모델 밖에서 돌고, 결제는 판매자·금액이 묶인 일회용 카드이며, 금융 거래·타인 계정 접근은 승인해도 막힌다
- 날짜: 2026-10-23
- 출처: https://claude.com/resources/articles/claude-duet-safety-privacy-and-security
- 요약: Duet은 대화 기록과 메모리를 사용자가 지우거나 초기화할 때까지 보관하고, 앱 연결을 끊어도 이미 배운 내용은 메모리를 초기화해야 사라진다. 민감한 메시지·결제·삭제 전에는 대상과 전체 내용을 보여 주고 승인을 기다리며, 각 행동이 사용자 의도와 맞는지는 Claude Code auto mode 분류기에 바탕을 둔 별도 검사가 모델 밖에서 확인한다. 브라우저는 별도 클라우드 VM에서 열기·클릭·입력만 받고, 비밀번호는 기기에서 암호화해 브라우저 머신에서만 풀리며, 로그인 토큰은 자리표시자를 프록시가 바꿔 끼운다. 글에는 관리자 정책이나 감사 로그 내보내기에 대한 설명이 없다.
- 현실 적용:
  - Duet을 업무에 도입하려는 보안 담당 → 글에 없는 항목(보관 기간 숫자, 감사 로그, 조직 정책)을 질문 목록으로 만들어 파트너 담당에게 보내고 답이 올 때까지 파일럿을 개인 계정으로 제한한다 → 문서에 없는 통제를 있다고 가정하고 도입하지 않는다
  - 자체 에이전트에 결제 기능을 넣는 개발자 → "판매자와 금액이 묶인 일회용 카드"와 같은 한도 구조를 우리 결제 도구 호출에 맞춰 한 건당 한도로 설계안에 적는다 → 프롬프트 인젝션이 성공해도 피해 상한이 한 건 금액에 머무르게 한다
  - Claude Code에 훅으로 승인 단계를 넣는 팀 → 승인 판단을 모델의 말이 아니라 별도 스크립트(금액·수신자 규칙)로 두는 `PreToolUse` 훅을 하나 만든다 → 숨은 지시문이 판정을 바꾸지 못하는 구조를 이 글의 모델 밖 검사처럼 흉내 낸다
  - 개인 사용자 → Duet에서 은행·건강 앱을 연결하기 전에 "함께 알려도 되는 정보"와 "절대 알리면 안 되는 정보" 표를 먼저 쓴다 → 요청 자체가 동의로 취급된다는 글의 규칙을 알고 말을 고른다
  - 앱 연결을 끊고도 메모리가 남는 점이 걸리는 사람 → 연결을 끊은 날 해당 앱의 메모리를 초기화하는 일을 할 일 목록에 같이 넣는다 → 끊었는데 정보가 남아 있는 상태를 없앤다

## 5. Claude Code 세션 471개, 토큰 61억 개를 읽어 보니 — 토큰의 97%는 캐시 읽기였지만 비용의 38%는 2.8%뿐인 캐시 쓰기였고, 큰 재작성 223건의 대부분은 유휴 시간 뒤 캐시 만료였다
- 날짜: 2026-10-23
- 출처: https://dev.to/danmercede/i-read-all-471-of-my-claude-code-sessions-where-6-billion-tokens-actually-went-1bde
- 요약: 글쓴이는 일주일 동안 API 호출 21,449건·61.5억 토큰을 정가로 환산해 약 2,500달러로 계산했다. 입력은 97.2%가 캐시 읽기, 캐시 쓰기는 토큰의 2.8%인데 비용의 38%였고, 10만 토큰 넘게 쓴 223건이 쓰기 토큰의 42%(약 446달러)를 차지했다. 그중 209건은 유휴 시간 뒤 만료였고 프롬프트 접두가 바뀐 경우는 13건뿐이었으며, 메인 세션이 한 시간 넘게 쉰 뒤가 72건(약 307달러), 서브에이전트 후속이 5분 넘은 뒤가 92건, 서브에이전트가 긴 도구 호출을 기다리다가 42건이다. 서브에이전트가 전체 쓰기의 64%였고, 되살린 서브에이전트의 재작성 중앙값은 17.8만 토큰으로 새로 띄운 것(5.5만)의 세 배였다. 대책은 긴 휴식 뒤에는 인계 메모로 새 세션을 열고, 서브에이전트 후속은 5분 안에 보내거나 새로 띄우고, 긴 기다림은 메인에서 하는 것이다.
- 현실 적용:
  - Claude Code를 하루 종일 켜 두는 개인 개발자 → 점심·회의 뒤 돌아왔을 때 이어 쓰는 대신 "지금까지 한 일과 다음 할 일"을 세 줄로 적어 새 세션을 여는 습관을 한 주 시험한다 → 한 시간 넘게 쉰 메인 세션의 큰 재작성 비용을 줄인다
  - 서브에이전트를 자주 쓰는 팀 → 끝난 서브에이전트에 후속 메시지를 보낼 때 5분이 지났으면 새 서브에이전트에 짧은 브리프를 주는 규칙을 CLAUDE.md에 적는다 → 되살린 서브에이전트가 17.8만 토큰을 다시 쓰는 일을 피한다
  - 사용량 한도가 갑자기 빨리 닳는다고 느끼는 구독자 → 자기 `~/.claude/projects` 기록으로 캐시 적중률이 아니라 "쓰기가 비용에서 차지하는 비율"과 만료 원인을 한 주치로 뽑아 본다 → 한도 소진의 원인이 휴식·서브에이전트 중 어느 쪽인지 추측 대신 숫자로 본다
  - 긴 빌드·테스트를 서브에이전트에 시키는 사람 → 5분 넘게 걸리는 대기는 메인 세션이나 `run_in_background`로 옮기는 변경을 하나만 해 보고 전후 쓰기 토큰을 비교한다 → 서브에이전트가 도구를 기다리다 캐시가 만료되는 42건 같은 경우를 줄인다
  - 이 저장소의 `cache-meter`·`spend-gate`·`loop-caps` → 실제 트랜스크립트에서 캐시 재작성의 원인(유휴·도구 대기·접두 변경)을 분류해 보여 주는 새 CLI를 폴더 하나로 만든다 → 호출 단위 측정과 금액 상한에 없던 "왜 비쌌나"를 채운다

## 오늘의 선정
- 5번(세션 471개 토큰 분석)을 골라, Claude Code 트랜스크립트(`~/.claude/projects/**/*.jsonl`)를 읽어 캐시 쓰기를 원인별(첫 호출 / 유휴 뒤 만료 / 도구 대기 중 만료 / 접두 변경 추정)로 나누고 메인·서브에이전트별 비용을 정가로 계산하는 **cache-break**를 만든다.
- 글은 `session-report` 플러그인과 개인 스크립트로 분석했지만 만료 원인 분류 도구는 없고, 이 저장소의 `cache-meter`는 API 호출 실험, `spend-gate`·`loop-caps`는 상한이라 기존 기록을 되짚어 원인을 가르는 도구가 비어 있다. 표준 라이브러리만으로 키·모델 없이 CI에서 테스트된다.
