## 1. dev.to 11-22 sungwoo_lee — 컨텍스트가 불어나는 가장 큰 몫은 도구 출력이 아니라 생각 토큰(세 프로젝트에서 70.2%·46.8%·57.3%)이고, 트랜스크립트의 블록 크기를 세면 틀린다

- 날짜: 2026-11-22
- 출처: https://dev.to/sungwoo_lee_e0f26be4a29fd/claude-code-context-growth-thinking-tokens-took-47-70-31ll
- 요약: 글쓴이는 자기 프로젝트 셋의 대화 기록에서 컨텍스트 증가의 원인을 가르며, 생각 블록은 본문이 비어 서명만 남으니 블록 바이트를 합치면 생각이 작아 보인다고 지적한다. 처음 쓴 표 세 개(36.1%·29.9%·90.7%)가 서로 어긋나 철회했고, 믿을 만한 방법은 요청마다 `input + cache_read + cache_creation`으로 점유량을 구해 인접한 두 응답의 차이에서 눈에 보이는 바이트(도구 결과·사용자 입력·출력)를 토큰으로 환산해 빼고 남은 몫을 생각으로 보는 것이다. 같은 `requestId`가 두세 번 반복되니 먼저 중복을 지워야 사용량이 1.9배로 부풀지 않으며, 판정은 쌍별 중앙값으로 한다. 환산 계수 4.5는 검증 없이 고른 상수라고 글이 밝힌다.
- 현실 적용:
  - 긴 리팩터링을 하루 종일 한 세션에 돌려 컨텍스트 창이 자주 차는 개인 개발자 → 어제 세션 하나에 쌍별 점유량 증가를 돌려 "생각 몫" 중앙값을 본다 → 압축 빈도를 줄이려고 도구 출력만 줄이다 효과 없던 시간을 아낀다
  - 모델 비용을 보고하는 팀 리드 → 팀원 세션 열 개의 생각 몫 중앙값을 표로 모아 `--effort low`로 돌려도 되는 작업군을 고른다 → 노력도를 일괄로 낮추기 전에 실제로 생각이 큰 세션부터 낮춘다
  - `claude -p`로 야간 리뷰를 돌리는 플랫폼 팀 → 같은 프롬프트를 effort low·high로 두 번 돌려 쌍별 생각 몫이 얼마나 달라지는지 비교한다 → "low로 바꾸면 싸진다"는 가정을 숫자로 확인한다
  - 서브에이전트가 도구 결과를 길게 돌려주는 설계를 다듬는 사람 → 서브에이전트 기록과 메인 기록의 생각 몫을 따로 구해 보고 결과 요약 길이를 줄일지 정한다 → 줄여도 컨텍스트가 안 줄어드는 곳에 손대지 않는다
  - 이 저장소의 `cache-break`·`cost-top` → 둘 다 사용량 합계는 보여 주지만 증가의 원천은 가르지 않으니 같은 트랜스크립트를 읽는 증가 원천 분석을 하나 더한다 → "캐시가 왜 깨졌나"와 "컨텍스트가 왜 커졌나"를 다른 질문으로 나눠 본다
  - 글의 숫자를 인용하려는 블로거·발표자 → 환산 계수를 3.5·4.5·5.5로 바꿔 결과가 얼마나 움직이는지 민감도를 표에 같이 적는다 → 고른 상수 하나에 기댄 퍼센트를 그대로 믿지 않는다

## 2. dev.to 11-23 vildandenai — 편집 직후 `git diff`를 훑어 비밀값 모양이 있으면 값은 출력하지 않고 exit 2로 턴을 멈추는 PostToolUse 훅

- 날짜: 2026-11-23
- 출처: https://dev.to/vildandenai/catch-a-leaked-secret-in-a-claude-code-diff-with-a-posttooluse-hook-27c
- 요약: `.env` 덮어쓰기를 막는 PreToolUse 가드는 이미 소스 파일에 들어간 키를 못 잡는다는 점에서 출발해, Edit·Write 뒤에 `git diff --unified=0 HEAD`를 읽고 정규식 네 개(개인키 머리말, `api_key = "…"` 꼴, `sk_live_`·`pk_test_` 꼴, JWT 꼴)로 거르는 훅을 보인다. 걸리면 무엇이 문제인지만 출력하고 값은 찍지 않으며 exit 2로 끝내고, git이 실패하면 빈 문자열로 통과시켜 세션이 잠기지 않는다. 우리가 그 정규식 네 개를 돌려 보니 `ghp_…`(GitHub 토큰), `AKIA…`(AWS 키 ID), `sk-ant-…`(Anthropic 키)는 잡지 못했다.
- 현실 적용:
  - 훅으로 비밀값 점검을 처음 넣는 개인 개발자 → 글의 정규식에 `ghp_`·`AKIA`·`sk-ant-` 접두 세 개를 더하고 가짜 diff로 시험한다 → 가장 흔한 세 종류가 통과하는 가드를 믿고 커밋하는 일이 없다
  - 신규 파일을 자주 만드는 에이전트 작업(스킬·MCP 서버 만들기) → 훅이 `git diff HEAD`만 보면 추적 전 파일이 빠지니 `git ls-files --others --exclude-standard`도 훑는지 시험한다 → 새 파일에 들어간 키가 diff에 안 보이는 구멍을 찾는다
  - 팀 공용 저장소의 보안 담당 → 훅 출력에 일치한 값이 한 글자도 찍히지 않는지 테스트에서 검사한다 → 로그와 대화 기록에 비밀값이 사본으로 남는 일을 막는다
  - 훅이 느려 불만인 사람 → 큰 diff(수만 줄)에서 훅이 4초 타임아웃에 걸려 통과로 빠지는지 재 보고 걸리면 파일별로 나눠 훑는다 → "타임아웃이면 통과"가 큰 변경에서만 조용히 꺼지는 문제를 일찍 안다
  - 이 저장소의 `/daily-lab` 루틴 → 푸시 직전 재확인에 쓰는 `grep -nE 'sk-ant-|AKIA|ghp_…'` 한 줄을 훅 형태로 만들어 Edit 직후에 돌린다 → 푸시 직전이 아니라 쓴 직후에 잡아 고칠 범위가 작다
  - 커밋 전에만 점검하던 사람 → PostToolUse 훅과 pre-commit 훅이 같은 줄을 같은 이유로 잡는지 한 diff에 양쪽을 돌려 비교한다 → 두 단계가 서로 다른 정규식을 쓰다 한쪽만 통과하는 일을 줄인다

## 오늘의 선정
- 1번 sungwoo_lee 글의 측정법을 구현하는 CLI **`ctx-growth`**를 만든다: 트랜스크립트를 `requestId`로 중복 제거하고 인접 요청의 점유량 증가에서 눈에 보이는 바이트를 빼 "생각 몫"을 쌍별 중앙값으로 낸다. 같은 기록에서 블록 바이트만 센 순진한 방법과, 출력 토큰 기준 교차 점검, 환산 계수 민감도를 나란히 보여 준다.
- 이유: 기존 `cache-break`·`cost-top`은 캐시 쓰기와 비용을 보지만 "컨텍스트가 무엇 때문에 커졌나"는 비어 있다. 키·모델 없이 합성 기록 하나로 전부 시험할 수 있다. 2번의 정규식 구멍(`ghp_`·`AKIA`·`sk-ant-` 통과)은 이미 있는 비밀 가드 계열과 겹쳐 다음 후보(`diff-secret`)로 남긴다.
