## 1. Python SDK 2.5.0·TypeScript SDK 1.5.0 — HTTP 상태와 API 오류 코드별 오류 클래스, `error_code`·`details`·`api_message` 필드, 메모리 도구가 `/memories` 폴더를 지우거나 이름 바꾸지 못하게 막는 수정
- 날짜: 2026-11-04
- 출처: https://github.com/anthropics/anthropic-sdk-python/releases/tag/v2.5.0 (TS: https://github.com/anthropics/anthropic-sdk-typescript/releases/tag/sdk-v1.5.0)
- 요약: 오류를 잡을 때 문자열을 뜯어보지 않아도 되도록 HTTP 상태별·API 오류 코드별 예외 클래스가 생기고, `APIStatusError`에 `error_code`, `details`, `api_message`가 붙었다. `OverloadedError`와 `ServiceUnavailableError`는 `InternalServerError`의 하위 클래스가 되어 기존 `except`가 그대로 잡는다. 메모리 도구는 `/memories` 디렉터리 자체를 이름 바꾸거나 지우지 못하게 고쳐졌고, 경로 매개변수에 `..;x` 같은 값을 넣으면 거절된다.
- 현실 적용:
  - Python으로 Claude를 부르는 백엔드 개발자 → 재시도 래퍼의 `if "overloaded" in str(e)` 같은 문자열 비교를 `except OverloadedError`로 바꾸고 `error_code`를 로그 한 칸으로 남긴다 → 메시지 문구가 바뀌어도 재시도가 깨지지 않는다
  - 이 저장소의 `login-watch`(11-04) → 만료 임박 경고 뒤에 "API가 401로 거절한 사유"를 `error_code`로 분류해 주는 후속 모드를 후보로 올린다 → 만료와 키 오류를 한 표에서 가른다
  - 메모리 도구로 에이전트에게 파일 기억을 주는 개발자 → 업그레이드 전 `/memories`를 지우라고 시키는 프롬프트로 한 번 시험하고 2.5.0에서 거절되는지 본다 → 기억 폴더가 통째로 날아가는 사고를 확인하고 넘어간다
  - SDK를 2.x로 막 올린 팀 → 오류 분류표(상태·코드·재시도 여부)를 사내 위키에 한 장 만들고 `details` 필드 예시를 붙인다 → 새 팀원이 429와 529를 같은 취급으로 재시도하는 실수를 줄인다
  - 비용 감시를 하는 개인 개발자 → 지출 한도 초과 오류 코드가 따로 오는지 샘플 호출 로그에서 찾고, 오면 `spend-gate`(10-13) 알림에 연결한다 → 한도 초과를 일반 실패와 구분해 바로 알린다

## 2. claude-cookbooks에 dreaming 쿡북 — 에이전트가 끝낸 세션 기록을 밤마다 내려받아 위키 형태의 메모리 저장소로 정리(distill)하고, 다음 세션이 그 저장소를 읽기 전용으로 쓰게 하는 예제 (Managed Agents, `dreaming_nightly.py`로 cron 실행)
- 날짜: 2026-11-04
- 출처: https://github.com/anthropics/claude-cookbooks/commit/d4bd2fb364a7daa77fa90390800ba3aafffd2d1f
- 요약: 노트북 하나와 `dreaming_nightly.py`가 들어갔다. 지난 실행 이후 끝난 세션을 기록으로 내보내 분석 에이전트가 읽고, 정리 에이전트가 메모리 저장소를 갱신한다. 밤 실행은 패키지를 새로 설치하지 않고, 기록을 하나라도 분석하지 못하면 종료 코드 1로 끝나며 그 시간 창을 다음 날 다시 처리한다. 예제 데이터는 가상 프로젝트의 대화 기록 10개다.
- 현실 적용:
  - Claude Code를 매일 쓰는 개발자 → 한 주치 `~/.claude/projects/*/memory/` 파일을 한꺼번에 점검하는 스크립트를 만든다(깨진 링크·색인 누락·중복) → 정리 에이전트에 맡기기 전에 기계가 잡을 수 있는 오류부터 걸러낸다
  - 팀 온보딩 담당 → 끝난 세션 기록 10개를 쿡북 예제 형식으로 모아 "우리 저장소 함정" 위키 초안을 만든다 → 신입이 첫 주에 같은 함정을 다시 밟지 않는다
  - 고객 지원 에이전트를 운영하는 팀 → 밤 실행의 종료 코드 1을 알림에 연결하고 실패한 밤의 시간 창이 다음 날 재처리되는지 확인한다 → 분석 누락이 조용히 쌓이지 않는다
  - 이 저장소의 `/daily-lab` 루틴 → 매일의 실패·재시도 기록에서 "다음에 하지 말 것"을 모아 규칙 후보로 올리는 주간 정리를 시도한다 → 같은 실패(예: `--bare` 로그인 실패)를 RULES에 반영한다
  - 메모리 저장소를 읽기 전용으로 마운트하는 서비스 개발자 → 정리 결과에서 API 키 접두어 같은 비밀값 패턴을 걸러내는 검사를 저장 직전에 넣는다 → 기록에 섞인 키가 위키로 굳는 일을 막는다

## 3. Claude Code 2.1.318 후속 — 무인 실행에 닿는 수정들: 실패하는 커스텀 슬래시 명령이 `claude -p`에서 아무것도 안 찍던 문제, 응답이 끊겨도 성공으로 보고하던 문제(`turn.step` 모드), 버전 확인 중 종료하는 stdio MCP 서버를 7일간 구형 핸드셰이크로 고정하는 동작 (후속: 11-04 1·2번과 같은 릴리스)
- 날짜: 2026-11-04
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.318
- 요약: 11-04에 수집한 로그인 만료일·설정 파일 보호 외에도 이 릴리스에는 무인 실행에 닿는 수정이 많다. `claude -p`와 SDK 세션에서 실패하거나 Claude 전용인 슬래시 명령이 이제 이유를 출력하고, API 오류로 응답이 잘렸는데 성공으로 보고하던 경로가 닫혔다. 시작 때 버전 확인에서 죽는 stdio MCP 서버는 매번 다시 확인하지 않고, 자기 탓으로 3초 안에 죽는 서버는 7일간 구형 핸드셰이크로 고정된다. 모드의 `$.model.fork`에는 `effort` 옵션이 생겨 곁가지 작업을 `low`로 돌릴 수 있다.
- 현실 적용:
  - `claude -p`로 CI 리뷰를 돌리는 개발자 → 파이프라인 끝에 "종료 코드 0인데 결과 JSON의 `is_error`가 true"인 경우를 실패로 보는 검사를 넣는다 → 잘린 응답이 초록불로 지나가는 일을 막는다
  - 슬래시 명령을 `claude -p`에서 부르는 자동화 담당 → 일부러 실패하는 명령을 하나 만들어 2.1.318 전후 출력을 비교하고 래퍼의 "빈 출력" 경보 기준을 고친다 → 아무것도 안 나온 이유를 로그에서 바로 읽는다
  - 자작 stdio MCP 서버를 쓰는 개발자 → 서버가 버전 확인 인자(`--version`)에서 종료 코드 0으로 빠지는지 직접 실행해 보고, 아니면 7일 고정이 걸렸는지 `claude mcp list`로 본다 → 서버가 구형 핸드셰이크에 갇힌 걸 모르고 신기능이 안 되는 일을 피한다
  - 이 저장소의 `mcp-probe`(11-01) → 서버가 3초 안에 죽는 경우를 "고정 위험"으로 따로 표시하는 검사를 후보로 올린다 → 7일 동안 조용히 구형으로 도는 서버를 미리 찾는다
  - 모드를 만드는 개발자 → `$.model.fork`에 `effort: "low"`를 준 곁가지(제목 짓기·분류)와 기본 effort를 같은 입력으로 돌려 응답 시간과 토큰을 잰다 → 곁가지 작업의 비용을 숫자로 줄인다
