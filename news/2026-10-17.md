## 1. Claude Code 팀의 코드 리뷰 7겹 구조 — "사람이 읽었나" 대신 "변경이 무엇을 망가뜨릴 수 있나"로 승인 인원을 정한다
- 날짜: 2026-10-15 (후속: 2026-10-16 news 1번 "Code Review GA"의 후속, GeekNews·Simon Willison이 10-16~17에 재인용)
- 출처: https://claude.dev/blog/solving-code-review-at-anthropic/
- 요약: Claude Code는 코드의 약 90%를 Claude가 쓰기 때문에, 팀은 사람 검토 시간을 되돌림·사고 증가 없이 최소화하는 것을 목표로 삼았다고 한다. PR 전 자체 검증, 모든 PR의 AI 리뷰, 병합을 막는 보안 리뷰, 필수 자동 검사, 위험도별 사람 승인, 병합 큐·플래그, 빠른 탐지·롤백의 일곱 겹이다. 승인 인원은 작성자가 아니라 변경의 위험도(낮음 0명·중간 1명·높음 2명)가 정하고, CI 워크플로 파일처럼 민감한 경로는 항상 사람이 본다. PR 템플릿에는 Testing·Risk·How to revert를 요구하며, 에이전트의 승인은 사람의 승인으로 치지 않는다.
- 현실 적용:
  - 3~10명 규모 팀의 리뷰 규칙 → PR 변경 파일 경로로 위험도(낮음·중간·높음)를 계산하는 스크립트를 CI에 붙이고 `.github/workflows/`·결제·인증 경로는 무조건 높음으로 둔다 → 문서만 고친 PR이 사람 승인을 기다리며 하루를 보내는 일이 사라진다
  - PR 템플릿을 쓰는 저장소 → 본문에 Testing·Risk·How to revert 세 항목이 비어 있으면 CI가 실패시킨다 → 되돌릴 방법을 안 적은 PR이 병합 큐에 들어가지 않는다
  - Claude Code로 PR을 대량으로 만드는 개인 개발자 → `REVIEW.md`에 "실패란 무엇인가, 니트 상한, 건너뛸 경로, 근거로 파일·줄 요구"를 적고 첫 줄을 개수 요약으로 시작하게 한다 → 리뷰 댓글을 읽는 시간이 줄고 "문제 없음"이 명시된다
  - 리뷰 봇이 같은 지적을 계속 되풀이하는 팀 → 라운드 상한 3회를 정하고 그 이후 재리뷰는 diff만 보게 한다 → 한 PR이 밤새 50번 리뷰되는 낭비를 막는다
  - 이 저장소의 daily-lab 루틴 → 하루 한 폴더 PR의 위험도를 "폴더 안만 건드림=낮음, 루트 README·워크플로 수정=높음"으로 자동 분류해 요약 메일에 붙인다 → 루트 파일이나 `.github/`를 건드린 날만 사람이 열어 본다

## 2. Claude Code 2.1.302: 자동 모드 분류기 모델 선택, 훅 동시 실행 12개 제한, 포크 서브에이전트 기본 켜짐
- 날짜: 2026-10-16
- 출처: https://code.claude.com/docs/en/changelog
- 요약: `CLAUDE_CODE_AUTO_MODE_MODEL`로 클라이언트 쪽 자동 모드 분류기가 쓸 모델을 고를 수 있고, `/config`에 유휴 압축 켜고 끄는 행이 생겼다. 프롬프트·에이전트 훅은 이벤트당 동시에 12개까지만 돌고 나머지는 기다린다. 포크 서브에이전트(`subagent_type: "fork"`)가 `claude -p`·Agent SDK·데스크톱·VS Code에서 기본으로 켜졌고 `CLAUDE_CODE_FORK_SUBAGENT=0`으로 끈다. 서드파티 제공자에서 권한 모드를 안 정한 `claude -p`는 이제 `default` 모드로 시작한다.
- 현실 적용:
  - 자동 모드를 쓰는 개인 개발자 → `CLAUDE_CODE_AUTO_MODE_MODEL`에 작은 모델을 지정해 한 주 동안 분류기 거부 횟수와 응답 지연을 비교한다 → 도구 호출마다 붙는 분류 지연을 줄일 수 있는지 숫자로 안다
  - Bedrock·Vertex로 `claude -p` 배치를 돌리는 팀 → 권한 모드를 명시하지 않은 스크립트를 `grep`으로 찾아 `--permission-mode`를 박는다 → 업그레이드 뒤 갑자기 `default`로 시작해 도구 승인에서 멈추는 야간 작업을 막는다
  - 프롬프트 훅을 여러 개 단 저장소 → 한 이벤트에 걸린 프롬프트·에이전트 훅 수를 세어 12개를 넘으면 합친다 → 13번째 훅이 앞 훅이 끝나길 기다리며 턴이 느려지는 일을 피한다
  - SDK로 에이전트를 만드는 개발자 → 포크 서브에이전트가 기본으로 켜졌으므로 비용·컨텍스트 상속이 문제인 흐름에서만 `CLAUDE_CODE_FORK_SUBAGENT=0`을 설정한다 → 호출 하나가 대화 전체를 물려받아 토큰을 두 배로 쓰는 놀라움을 막는다
  - 이 저장소의 Actions 워크플로 → `daily-lab.yml`이 `claude -p`를 어떤 권한 모드로 부르는지 확인하고 명시한다 → 제공자나 버전이 바뀌어도 06:45 작업의 승인 동작이 그대로다

## 3. 허용 규칙 `mcp__a`가 서버 `a__b`까지 덮던 문제 — 2.1.299에서 서버 이름 정확히 일치로 변경, 규칙을 `mcp__a__*`로 고쳐야
- 날짜: 2026-10-16 (후속: 2026-10-15 news 2번 "2.1.299·2.1.300"의 MCP 항목을 풀어 쓴 글)
- 출처: https://dev.to/gabrielanhaia/an-allow-rule-for-mcp-server-a-also-matched-ab-how-claude-codes-names-collided-2cm8
- 요약: MCP 도구 이름은 `mcp__<서버>__<도구>` 한 줄이고 서버·도구 이름에도 `__`가 들어갈 수 있어, 서버 `a`의 도구 `b__whoami`와 서버 `a__b`의 도구 `whoami`가 같은 문자열이 된다. 2.1.299 이전에는 `mcp__a` 허용 규칙이 `a__…` 서버까지 덮었고, `mcp__a__b` 같은 deny·ask 규칙은 서버 `a`의 도구 `b`로 읽혀 의도한 서버에 안 걸렸다. 글쓴이는 옛 파서가 첫 `__`에서 잘랐다고 추정한다(변경 기록에 옛 동작은 없다). 이제 서버 이름이 정확히 같을 때만 매칭되며 권장 형태는 서버 전체 정규화 이름에 `__*`를 붙이는 것이다.
- 현실 적용:
  - MCP 서버를 5개 넘게 붙인 개발자 → `~/.claude/settings.json`·`.claude/settings.json`·`.mcp.json`의 `permissions`에서 `mcp__x` 형태 맨몸 규칙을 모아 `mcp__x__*`로 바꾼다 → 신뢰하는 서버 하나의 허용이 이름이 비슷한 다른 서버의 도구까지 무프롬프트로 열던 구멍을 닫는다
  - `deny`로 위험 서버를 막아 둔 보안 담당자 → `mcp__a__b`처럼 `__`가 든 deny·ask 규칙을 찾아 서버 `a__b` 전체 차단은 `mcp__a__b__*`로 다시 쓴다 → 차단했다고 믿은 서버가 실제로는 열려 있던 상태를 바로잡는다
  - 플러그인이 번들한 MCP 서버를 쓰는 팀 → 정규화 이름 `mcp__plugin_<플러그인>_<서버>__*` 규칙이 맞는지 점검한다 → 플러그인 서버의 허용 규칙이 문자 치환(`_`) 때문에 안 맞아 매번 프롬프트가 뜨는 불편을 없앤다
  - CI에서 `--allowedTools`로 Claude를 돌리는 저장소 → 워크플로 YAML의 `--allowedTools` 값에서 `mcp__서버` 맨몸 항목을 grep해 와일드카드 형태로 바꾼다 → 업그레이드 후 CI가 갑자기 도구 거부로 실패하는 일을 미리 막는다
  - 서브에이전트 정의 파일을 모아 둔 저장소 → `.claude/agents/*.md`의 `tools:` 목록에 든 `mcp__` 항목을 같은 기준으로 점검한다 → 서브에이전트가 의도보다 넓은 MCP 권한을 물려받는 일을 줄인다

## 4. 사용 한도에 걸려도 자동으로 이어 가는 Claude Code — 단, 맥이 잠들면 "reset" 메시지에서 멈춘다
- 날짜: 2026-10-16
- 출처: https://dev.to/dawonlee/claude-code-now-resumes-after-a-usage-limit-unless-your-mac-fell-asleep-17k1
- 요약: 구독 계정의 v2.1.234 이상에서는 사용 한도로 작업이 멈추면 세션이 기다렸다가 한도가 풀린 뒤 알아서 이어 간다. 훅 `StopFailure`(matcher `rate_limit`)와 `Notification`(`quota_auto_resume_fired`·`stale`·`disabled`)으로 상태를 알 수 있다. 기다림은 5시간 창 때문에 몇 시간일 수 있고 CPU를 거의 안 써 맥이 유휴로 보여 잠들기 쉬우며, 한도 해제가 잠든 사이 30분 넘게 지나면 세션이 Enter를 기다린다. 글쓴이는 `caffeinate -i`나 `pmset disablesleep`을 권한다(유료 앱 홍보 포함). 2.1.301에서는 무인 재시도 모드의 최대 대기를 제한하는 `CLAUDE_CODE_RETRY_WATCHDOG_MAX_USAGE_LIMIT_WAIT_MS`도 생겼다.
- 현실 적용:
  - 퇴근 전에 긴 작업을 맡기는 개인 개발자 → 세션을 `caffeinate -i -w <claude pid>`로 감싸 시작한다 → 한도 대기 중 맥이 잠들어 아침에 "reset" 메시지에서 멈춰 있는 일을 막는다
  - 야간 배치를 돌리는 사람 → `StopFailure` 훅(matcher `rate_limit`)에서 시각을 파일에 남기고 `quota_auto_resume_stale` 알림이 오면 폰으로 푸시를 보낸다 → 자동 재개가 실패한 밤을 아침에 알게 된다
  - 무인 재시도 모드를 쓰는 서버 → `CLAUDE_CODE_RETRY_WATCHDOG_MAX_USAGE_LIMIT_WAIT_MS`를 6시간으로 두어 주간 한도처럼 먼 해제는 기다리지 않고 끝낸다 → 작업이 이틀 동안 대기 상태로 자원을 잡고 있지 않는다
  - 팀 공용 러너 → 한도 대기에 들어간 세션 수를 훅 로그로 센다 → 계정 한도가 어느 시간대에 몰려 소진되는지 보고 작업 시간을 분산한다
  - 이 저장소의 daily-lab 루틴 → 06:45 실행이 한도에 걸린 날은 `rate_limit` 이벤트를 요약 이슈에 한 줄로 남기게 한다 → "오늘 결과물이 없는 이유"가 실패가 아니라 한도 대기였음을 구분한다
