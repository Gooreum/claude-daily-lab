## 1. 서브에이전트 `disallowedTools: Bash(git push *)`는 Bash 전체를 뺏는다 — 10번 중 10번
- 날짜: 2026-10-12
- 출처: https://dev.to/rulestack/bashgit-push-in-a-claude-code-subagents-disallowedtools-took-away-all-of-bash-in-10-of-10-4ihj
- 요약: Claude Code 2.1.289에서 서브에이전트 다섯 종류로 `claude -p` 39회를 돌려, `disallowedTools`에 `Bash(git push *)`처럼 괄호 지정자를 쓰면 `git push`만이 아니라 Bash 도구 자체가 사라진다는 것을 보였다(`git status`도 0/3). 반대로 설정의 `permissions.deny`에 같은 규칙을 넣으면 Bash는 남지만 `git -C <경로> push`로 3/3 우회됐다. 서브에이전트가 `Agent` 도구로 띄운 손자 에이전트는 제한을 물려받지 않아 Bash로 2/2 푸시했다.
- 현실 적용:
  - 팀의 `.claude/agents/*.md` 저장소 → 프론트매터의 `disallowedTools`·`tools`에 괄호 지정자가 있는지 정적 검사하는 린터를 CI에 건다 → "푸시만 막았다"고 믿고 테스트도 못 돌리는 리뷰 에이전트를 배포 전에 잡는다
  - 리뷰·문서 전용 서브에이전트 정의 → 셸이 필요 없으면 `disallowedTools: Bash`로 명시하고 `Agent`도 함께 뺀다 → 손자 에이전트를 통한 우회 경로를 닫는다
  - 사내 `settings.json`의 `deny: Bash(git push *)` → `git -C`·`git -c k=v`·`env git` 같은 변형까지 잡는 PreToolUse 훅을 짝으로 둔다 → 명령 문자열 규칙만 믿다 원격이 바뀌는 사고를 막는다
  - 이 저장소의 daily-lab 루틴 → 서브에이전트에 수집만 맡길 때 `tools:` 허용 목록(Read·WebFetch·Grep)으로 정의 → 수집 에이전트가 실수로 커밋·푸시하는 경로 제거
  - 서버 측 git 운영 → `main` 보호 브랜치와 pre-receive 훅을 "최종 방어선"으로 두고 클라이언트 규칙은 편의로만 취급 → 권한 규칙 버그가 나와도 원격은 안전
  - 개인 프로젝트 서브에이전트 정의 리뷰 → `claude --debug`로 서브에이전트가 받은 도구 목록을 한 번 출력해 정의와 대조 → 문서와 실제 도구 집합의 차이를 5분 만에 확인

## 2. 편집할 때마다 테스트를 돌리는 PostToolUse 훅
- 날짜: 2026-10-12
- 출처: https://dev.to/vildandenai/make-claude-code-run-your-tests-after-every-edit-with-a-posttooluse-hook-jk3
- 요약: `Edit|Write|MultiEdit` 매처의 PostToolUse 훅이 수정된 파일 확장자(.ts·.tsx·.py)를 보고 `npm test --bail`을 돌리고, 실패하면 출력 끝 1,500자를 stderr로 내고 exit 2로 같은 턴에 에이전트에게 돌려준다. 테스트가 편집보다 오래 걸리면 세션이 대기만 하게 되니 빠른 명령(`pytest -x -q`)을 쓰고 훅은 2~3개로 줄이라고 권한다.
- 현실 적용:
  - 파이썬 위주의 이 저장소 days 폴더 → 편집된 파일이 속한 `days/<폴더>/test.sh`만 찾아 돌리는 훅 → 루트 전체가 아닌 해당 프로젝트만 테스트해 대기 시간을 초 단위로 유지
  - 회사 프론트엔드 모노레포 → 변경 파일의 패키지에서만 `vitest related <file>` 실행 → 수천 개 테스트 전체 실행 없이 깨진 것만 즉시 되돌려 받는다
  - 출력 꼬리만 보내는 한계 → 실패한 테스트 이름 줄만 grep해서 앞에 붙인다 → 1,500자 절단으로 원인이 잘리는 문제 완화
  - 느린 통합 테스트가 있는 백엔드 → PostToolUse는 단위 테스트만, Stop 훅에서 통합 테스트 한 번 → 편집 루프 속도와 최종 검증을 분리
  - 신입 온보딩 문서 → 이 훅을 `settings.example.json`으로 제공하고 `onFailure`를 명시 → 테스트 러너가 없을 때 조용히 통과하는지 막을지 팀이 의식적으로 고른다

## 8. 측정 실패는 $0이 아니다 — 30초 타임아웃이 비용 기록을 지웠다
- 날짜: 2026-10-11
- 출처: https://dev.to/shikiyusuke/the-cost-wasnt-0-my-ai-coding-measurement-timed-out-at-30-seconds-198e
- 요약: AI 코딩 비용 측정이 36초 걸렸는데 호출 측 타임아웃이 30초라 기록 없이 끝났고, 그 공백이 평균에서 0처럼 다뤄졌다. 0·모름·실패·미측정을 다른 상태로 저장하고, 타임아웃을 오류 메시지에 명시하며, exit 0만 보고 측정 완료로 판단하지 말라는 교훈을 정리했다.
- 현실 적용:
  - 이 저장소의 cache-meter·effort-race 결과 JSON → 실패 실행을 `null`과 `status: "timeout"`으로 남기고 평균에서 제외 → 실패가 비용을 낮춰 보이게 하는 왜곡 제거
  - 회사 LLM 비용 대시보드 → "측정 누락 건수" 열을 추가 → 0원 날이 진짜 0원인지 수집 실패인지 구분
  - feed_bookmark의 "조용함/읽기 불가" 구분 → 같은 원칙을 다른 수집 스크립트에도 적용 → 확인 못 한 날을 조용한 날로 기록하지 않는다
  - CI 스크립트 → `timeout`이 죽인 경우 exit 124를 그대로 올리고 메시지에 "타임아웃(30s)"을 출력 → "Command failed"만 보고 원인 찾는 시간 절약
  - 실험 노트 템플릿 → 결과 표에 "측정 상태" 열을 기본 포함 → 리뷰어가 숫자의 신뢰도를 바로 판단
