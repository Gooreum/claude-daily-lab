## 1. 토큰 절약은 "읽지 않는 것"에서 — 락 파일·`*.min.js`·`*.map`·`node_modules` 전체 읽기를 `PreToolUse` 훅으로 막고, 일부 읽기(`offset`/`limit`)는 통과시키는 방법. `.claudeignore`는 Claude Code에서 아무 효과가 없다
- 날짜: 2026-10-25
- 출처: https://dev.to/humaki/cutting-claude-code-token-usage-the-parts-that-actually-matter-41oo
- 요약: 매 메시지가 컨텍스트 전체를 다시 보내므로 가장 싼 토큰은 처음부터 들어오지 않은 토큰이라는 글이다. Read 도구는 호출당 25,000토큰, 256KB 한도가 있고 Bash 출력은 약 30,000자까지 그대로 들어오는데, 낭비의 대부분은 락 파일·번들·소스맵처럼 도움이 안 되는 중간 크기 읽기라고 한다. 글쓴이는 Claude Code 2.1.310에서 68KB `package-lock.json`과 39KB `node_modules` 파일의 전체 읽기를 훅이 거부하고 `offset: 1, limit: 3`이나 `grep -c`는 통과함을 확인했다. `permissions`의 deny 규칙은 작은 부분 읽기까지 다 막으므로 비밀 파일용이고, `.claudeignore`는 효과가 없으니 deny 규칙으로 옮기라고 한다. 절약률은 글에서 측정하지 않았다.
- 현실 적용:
  - Node 프로젝트에서 에이전트에게 "의존성 왜 깨졌지?"를 묻는 개인 개발자 → `Read|Bash`에 걸리는 `PreToolUse` 훅으로 `package-lock.json` 전체 읽기를 거부하고 이유를 모델에게 보여 준다 → 모델이 락 파일 전체를 읽는 대신 `grep`으로 패키지 한 줄만 찾는다
  - `.claudeignore`를 만들어 두고 안심하던 사람 → 파일이 있는데 `Read` deny 규칙이 없으면 경고하고 항목을 deny 규칙으로 옮겨 주는 점검을 한 번 돌린다 → 막은 줄 알았던 `.env`·빌드 산출물이 실제로는 읽히던 구멍을 찾는다
  - 모노레포를 운영하는 팀 → 팀 `.claude/settings.json`에 같은 훅을 올리고 `dist/`·`*.map`·`vendor/`를 거부 목록에 넣는다 → 신입 PC에서 번들 파일을 읽다 한 세션 한도를 태우는 일이 없어진다
  - Python 데이터 작업을 하는 연구자 → 큰 `.csv`·`.parquet`·`.ipynb` 출력 셀 전체 읽기를 거부하고 `head`·`wc -l` 쓰라는 이유를 돌려준다 → 노트북 출력이 컨텍스트를 채워 `/compact`를 자주 하게 되는 일을 줄인다
  - 이 저장소의 `cache-meter`·`cache-break` 옆 → 읽기 차단 훅을 폴더 하나로 만들고 차단 건수를 로그로 남긴다 → 훅이 실제로 몇 번, 어떤 파일에서 막았는지 숫자로 보고 규칙을 다듬는다

## 2. "테스트 통과" 주장을 감시하는 도구가 46건 중 43건 오탐 — 인식 못 한 테스트 명령 22건, 테스트가 맞는 증거가 아닌 주장 12건. 경고로는 못 믿고 조용한 기록으로는 쓸 만하다
- 날짜: 2026-10-25
- 출처: https://dev.to/vitalii_serbyn_bb456e7e80/i-built-a-tool-to-catch-agents-saying-tests-pass-without-proof-it-was-wrong-43-times-out-of-46-1k6j
- 요약: 에이전트가 "고쳤다"·"테스트 통과"라고 말할 때 마지막 코드 수정 뒤에 실제 테스트 실행이 있었는지 훅 기록과 맞춰 보는 플러그인을 만든 글이다. 일주일간 948건 중 315건이 걸렸고, 46건을 세션 전체와 함께 사람이 확인하니 진짜 문제는 3건뿐이었다. 오탐의 절반은 테스트는 돌았는데 명령 형태(파일 직접 실행, 래퍼 스크립트, `grep` 파이프)를 못 알아본 것이고, 12건은 문서·데이터 점검이라 테스트가 맞는 증거가 아니었다. 코드 수정의 약 67%가 훅이 세지 않는 셸 명령으로 이뤄졌다. 글쓴이는 경고를 켜기 전에 일주일은 조용히 기록만 하라고 권한다.
- 현실 적용:
  - 에이전트가 "완료"라고 하면 그대로 머지하던 개인 개발자 → `Stop` 훅에서 마지막 수정 시각과 마지막 테스트 실행 시각만 파일에 한 줄씩 남기고 경고는 켜지 않는다 → 일주일 뒤 "수정 뒤 테스트 없이 끝낸 세션" 비율을 내 데이터로 먼저 본다
  - 팀 CI에 에이전트 PR 검사를 추가하려는 리드 → 훅 로그에서 인식 못 한 명령 형태(`python test_x.py`, `make check`)를 모아 테스트 명령 인식 목록을 먼저 채운다 → 오탐 절반을 차지한 "돌았는데 못 알아본" 경우를 도입 전에 없앤다
  - 문서·설정 변경이 많은 작업(블로그, 데이터 정리)을 맡기는 사람 → 파일 확장자가 `.md`·`.csv`면 테스트 증거를 요구하지 않는 예외를 둔다 → 문서 작업마다 "테스트 안 돌림" 경고가 떠서 경고를 무시하게 되는 일을 막는다
  - 무인 `claude -p` 야간 작업을 돌리는 운영자 → 결과 JSON과 같은 폴더에 "수정 파일 목록·실행한 검증 명령·종료 코드" 요약을 남기게 한다 → 아침에 "성공"만 보고 넘기지 않고 검증이 있었는지 30초 만에 확인한다
  - 이 저장소의 `review-gate`(리뷰 판정을 커밋 해시에 묶는 도구) → "마지막 수정 이후 테스트 실행 여부"를 같은 해시 기준으로 기록하는 후속 이슈를 쓴다 → 리뷰 통과 후 코드가 바뀌었는데 테스트가 다시 안 돈 경우를 잡는다

## 3. 스킬이 안 켜지는 이유를 108회 실험으로 — 이름·설명이 둘 다 흐리면 15회 중 5회만 켜지고, `disable-model-invocation`이면 0회. 설명은 1,536자에서 잘리고 목록 전체는 컨텍스트의 약 1%만 쓴다
- 날짜: 2026-10-25
- 출처: https://dev.to/khadimhussain/claude-code-skills-how-they-work-and-when-they-trigger-26dk
- 요약: Claude Code 2.1.310·Opus 5.5에서 변형 6개를 각 3번씩 돌린 결과를 정리한 글이다. 이름이나 설명 중 하나만 분명해도 15번 모두 켜졌고, 둘 다 흐리면 5번, 모델 호출을 끈 스킬은 0번, 폴더 안에 뭐가 있냐고만 묻는 요청은 어느 변형에서도 안 켜졌다. 각 설명은 목록에서 1,536자에서 잘리고 전체 목록은 컨텍스트의 약 1% 예산을 쓰며, 넘치면 덜 쓰는 스킬은 설명이 빠진 채 이름만 남는다. 프런트매터가 깨지면 필드가 통째로 비고 모르는 필드는 오류 없이 무시된다. `skillListingBudgetFraction`으로 예산을 올리고 `/doctor`가 비용을 추정한다.
- 현실 적용:
  - 스킬을 70개쯤 쌓아 둔 사람 → `/doctor`로 목록 비용을 보고, 설명 앞 80자에 "언제 쓰나"가 없는 스킬을 골라 다시 쓴다 → 설명이 잘리거나 예산 초과로 이름만 남은 스킬이 다시 자동으로 켜진다
  - 팀 공용 스킬 저장소 메인테이너 → 프런트매터 파싱이 깨진 `SKILL.md`를 CI에서 찾고, 모르는 필드 이름(오타)도 경고한다 → 오류 없이 무시되어 "왜 안 켜지지?"로 한 시간 쓰는 일을 막는다
  - `resume`·`review`처럼 내장 명령과 같은 이름의 스킬을 만든 사람 → 이름 충돌 목록을 만들어 바꾼다 → 내장 명령이 스킬에 가려져 이상하게 동작하는 일을 피한다
  - 자동 트리거를 기대하며 `disable-model-invocation: true`를 켜 둔 사람 → 켜 둔 스킬 목록을 뽑아 "정말 수동 전용인가"를 하나씩 확인한다 → 자동으로 켜질 줄 알았던 스킬이 영원히 안 켜지는 상황을 찾는다
  - 이 저장소의 `skill-lint` → 설명 길이·이름 충돌·수동 전용 표시를 이미 보는지 확인하고 빠진 검사를 이슈로 올린다 → 10-23에 만든 린터의 빈칸을 이 실험 숫자로 메운다
