## 1. Claude Code v2.1.327·v2.1.328 (11-17, 11-19) — `/status`가 깨진 스킬·에이전트 파일과 "절대 안 맞는 훅 matcher"를 목록으로 알려 주고, `claude mcp add`가 `.mcp.json`의 다른 키를 지우던 버그가 고쳐졌다
- 날짜: 2026-11-19
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.327
- 요약: v2.1.327은 `/status`에 깨진 에이전트·스킬·명령·출력 스타일 파일, 키 바인딩 오류, 쓸 수 없는 샌드박스, 무시된 권한 설정, 그리고 "절대 맞지 않는 훅 matcher"를 한 목록으로 보여 준다. 프로젝트 범위로 `claude mcp add`·`remove`를 하면 `.mcp.json`의 `$schema` 같은 다른 최상위 키가 지워지던 문제, Remote Control이 worktree 모드로 멈출 때 실행 중 세션의 `.env` 같은 git 무시 파일을 지우던 문제, `/export`가 같은 이름 파일을 묻지 않고 덮어쓰던 문제도 고쳤다. `claude mcp add-json <이름> -`는 서버 JSON을 stdin으로 받아 토큰이 명령줄에 남지 않는다. v2.1.328은 `mcp_tool` 훅에도 `"onFailure": "block"`(호출이 실패하면 동작을 막음)을 추가하고, 스케줄 작업 파일 오류 때 다른 작업까지 지워지던 문제를 고쳤다.
- 현실 적용:
  - 훅을 쓰는 개인 개발자 → 오늘 `claude` 안에서 `/status`를 열어 "never match" 훅 목록이 비었는지 본다 → 설정에 쓴 가드가 이름 오타로 한 번도 안 도는 줄 모르고 지내는 일을 끝낸다
  - 팀 설정 관리자 → 공용 `.claude/settings.json`의 모든 `matcher`를 CI에서 문서 규칙(`mcp__서버`는 정확히 일치만 → `.*` 필요, `bash`는 대소문자 구분)으로 검사하는 스크립트를 PR 체크에 넣는다 → `/status`를 안 열어 본 사람의 PR에서도 죽은 가드가 머지 전에 잡힌다
  - MCP 서버를 `.mcp.json`으로 공유하는 팀 → 프로젝트 범위로 `claude mcp add` 하기 전후의 최상위 키를 비교하는 한 줄 점검을 온보딩 문서에 적는다 → 2.1.327 이전 버전을 쓰는 사람이 `$schema`·다른 도구의 `servers` 키를 날리는 사고를 막는다
  - 토큰이 필요한 MCP 서버를 등록하는 사람 → `claude mcp add-json github - < server.json`으로 등록하고 셸 히스토리에서 토큰 문자열이 안 남았는지 `history | grep -i token`으로 확인한다 → 명령줄 인자로 새던 비밀값이 히스토리·프로세스 목록에서 사라진다
  - 이 저장소의 `/daily-lab` 루틴 → 푸시 직전 재확인 목록에 "훅·스킬 설정 파일 검사 통과"를 한 줄 넣고 `matcher-lint`를 부른다 → 자동 실행 중 죽은 훅이 조용히 늘어나는 것을 매일 숫자로 본다
  - Remote Control·worktree 병렬 세션을 쓰는 사람 → 2.1.327 이전 버전에서 `.env`가 지워졌는지 `git status --ignored`로 점검하고 `.env.example`을 커밋해 둔다 → 이미 지워진 로컬 설정을 복구할 근거를 남긴다

## 2. claude.dev 11-17 "Using a chaos loop to harden the Claude Docs launch" — 스테이징에서 Claude가 2주간 서비스를 일부러 부수고 고치는 루프를 돌려, 출시 1주에 요청 20억 건 중 서버 오류 60건
- 날짜: 2026-11-17
- 출처: https://claude.dev/blog/chaos-loop-claude-docs-launch/
- 요약: Claude Docs 팀은 출시 3주 전 PoC 상태에서, 스테이징에 하루 100만 건 넘는 합성 문서를 흘리고 Claude Code 세션 하나를 2주 동안 켜 둬서 시나리오 선택 → 하네스 실행 → 텔레메트리 읽기 → 수정 제안 → 스테이징 배포를 반복시켰다. 되돌리기 어려운 결정(스키마·키 배치·문서 저장 방식)은 사람 승인을 받게 했고, 두 가지 불변식(문서가 거의 즉시 열린다, 서버가 확인한 편집은 사라지지 않는다)을 지키게 했다. 쿼리 하나마다 스캔한 행 수와 반환한 행 수를 보고하게 하고, GC 없는 Rust를 고르고 의존성을 최소화해 "측정한 숫자가 내 코드로 설명되게" 했다. 결과로 필요한 파드 추정이 500개 이상에서 약 50개로 줄었고 출시 1주에 롤백이 없었다.
- 현실 적용:
  - 백엔드 개발자 → 스테이징 하나에 "장애 시나리오 목록(재연결 폭주, DB 지연, 서버 강제 종료)"을 `scenarios.md`로 쓰고, 세션 하나가 시나리오를 돌며 로그를 읽고 고치도록 `/loop`로 밤새 돌린다 → 사람이 출시 직전에야 처음 보던 병목을 2주 전에 본다
  - 서비스 운영자 → 쿼리마다 "스캔한 행 수 / 반환한 행 수"를 로그에 한 줄 남기는 미들웨어를 오늘 넣는다 → 에이전트가 나쁜 쿼리를 사람 눈 없이 골라낼 수 있는 신호가 생긴다
  - 팀 리드 → 루프 시작 전 "승인 없이 못 하는 변경" 목록(스키마, 키 설계, 저장 방식)을 `CLAUDE.md`에 적고 훅으로 해당 파일 수정을 막는다 → 자율 루프가 되돌리기 어려운 결정을 혼자 내리지 못한다
  - 개인 프로젝트 → 작은 웹 앱의 핵심 불변식 두 개("저장한 데이터는 재시작 뒤에도 있다" 같은)를 테스트로 쓰고 Claude에게 그 불변식을 깨 보라고 시킨다 → 평소 안 보던 경계 조건 버그를 하룻밤에 모은다
  - 이 저장소의 `/daily-lab` 루틴 → 수집 단계에 일부러 깨진 피드(빈 응답, 403, 잘못된 XML)를 섞어 소스 점검 표가 "조용함"과 "읽기 불가"를 가르는지 반복 시험한다 → "확인 못 한 날을 조용한 날로 적는" 오류를 출시 전에 찾는다
  - 비용 담당 → 루프를 돌리기 전에 상한(턴·금액)을 훅으로 걸고 글 끝의 비용 항목처럼 실행 뒤에 실제 사용량을 기록한다 → 2주짜리 자율 루프가 청구서로 먼저 알려지는 일을 막는다

## 3. API 릴리스 노트 11-17 — Linked billing 베타: 고객이 자기 Claude 조직으로 내 앱의 Claude 사용료를 내고, 요청마다 `billing_policy`로 누가 내는지 고른다
- 날짜: 2026-11-17
- 출처: https://platform.claude.com/docs/en/release-notes/api
- 요약: `user-profiles-billing-2026-10-01` 베타 헤더와 함께 Linked billing이 시작됐다. 고객이 조직을 앱에 연결하면 `/v1/messages`·`/v1/chat/completions` 요청마다 `billing_policy`를 지정해 청구 주체를 정하고, 고객은 콘솔에서 앱별 지출 상한을 걸거나 연결을 끊을 수 있다. Anthropic에 API 사용료를 직접 내는 조직의 고객에게만 동작한다. Python SDK v2.10.0이 `billing_policy` 베타 파라미터와 `contract_spend_limit_reached`·`user_profile_billing_not_authorized` 같은 오류 코드를 같이 추가했다.
- 현실 적용:
  - Claude 기반 SaaS를 만드는 팀 → 고객 조직에 연결을 맡기고 `billing_policy`를 요청 래퍼에 한 줄로 넣는 스파이크를 오늘 만든다 → 고객 사용량이 내 청구서에 얹혀 마진이 깎이는 구조를 바꿀 수 있다
  - 백엔드 개발자 → 새 오류 코드 네 개(`contract_spend_limit_reached`, `user_profile_billing_not_authorized` 등)를 앱의 오류 처리 표에 추가하고 "상한 도달"은 재시도하지 않고 고객에게 안내한다 → 상한에 걸린 요청을 무한 재시도해 오류만 쌓는 일을 막는다
  - 제품 기획자 → 고객에게 "연결 해제·상한은 콘솔에서 고객이 직접 건다"는 안내 문구를 설정 화면에 넣는 초안을 오늘 쓴다 → 청구 문의가 지원팀으로 몰리지 않는다
  - 비용 담당 → 연결 고객과 아닌 고객의 요청을 로그에서 `billing_policy` 값으로 나눠 이번 주 토큰 비중을 센다 → 내가 부담하는 몫이 줄었는지 숫자로 확인한다
  - 이 저장소의 `/daily-lab` 같은 개인 자동화 → 개인 키로 도는 지금 구조에는 해당 없음을 확인하고, 베타 헤더가 필요한 API는 `apiver-lint` 식 점검에 베타 헤더 목록을 추가한다 → 베타 헤더 날짜가 바뀌거나 끝났을 때 조용히 400이 나는 것을 미리 찾는다

## 오늘의 선정
- 1번의 `/status` "절대 맞지 않는 훅 matcher" 목록을 CI·저장소 점검으로 옮긴 **`matcher-lint`**를 만든다: 훅 설정 파일(`settings.json`·`settings.local.json`·플러그인 `hooks.json`)을 읽어 문서 규칙대로 matcher를 평가하고, 도구 이름 오타·대소문자·`mcp__서버`(정확 일치라 아무것도 안 맞음)·잘못된 정규식·matcher를 못 쓰는 이벤트·`if`에 넣어야 할 인자를 matcher에 넣은 경우를 잡는다.
- 이유: 기존 `hook-exit-audit`(종료 코드)·`hook-manners`(훅 예절)·`disaster-guard`는 훅이 "돈 뒤"의 동작을 보지만 "아예 안 도는" 훅은 못 본다. 이 저장소에 쌓인 훅 가드(verify-gate 등)도 matcher 오타 하나면 조용히 꺼진다. 모델·키 없이 문서 규칙만으로 전부 시험할 수 있다.
