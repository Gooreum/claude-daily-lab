## 1. Claude Code 2.1.325·Agent SDK 0.3.325 (11-13) — 샌드박스 Bash 자동 승인이 기본 꺼짐, PreToolUse 훅이 답을 못 하면 `hook_no_verdict` 경고, zstd 응답 해석 보안 수정
- 날짜: 2026-11-13
- 출처: https://github.com/anthropics/claude-code/releases/tag/v2.1.325 (SDK: https://github.com/anthropics/claude-agent-sdk-typescript/releases/tag/v0.3.325)
- 요약: Agent SDK의 `sandbox` 옵션을 켜도 샌드박스 안 Bash가 더는 자동 승인되지 않고, `autoAllowBashIfSandboxed: true`를 따로 줘야 이전처럼 돈다(CLI 쪽도 같은 방향의 변경 문구가 있다). PreToolUse 훅이 실행에 실패하거나 시간 초과로 도구 호출을 거절하지도 못했을 때 SDK가 `hook_no_verdict`라는 정보성 경고를 낸다. zstd 압축 응답을 푸는 방식의 보안 문제가 고쳐졌고, 다른 모델을 쓰는 서브에이전트가 `opusplan`·`haiku` 설정 때문에 plan 모델로 옮겨지던 문제, `applyFlagSettings()`에 잘못된 값 하나가 이전 설정 전부를 버리던 문제도 고쳐졌다.
- 현실 적용:
  - SDK로 사내 자동화 봇을 돌리는 팀 → `sandbox` 옵션을 쓰는 호출부를 `grep -rn "sandbox" src/`로 찾아 `autoAllowBashIfSandboxed`를 명시하고 한 번 돌려 승인 프롬프트가 안 뜨는지 본다 → 업그레이드 후 무인 작업이 승인 대기로 멈추는 일을 배포 전에 잡는다
  - PreToolUse 훅으로 위험 명령을 막아 둔 개발자 → `system/informational` 메시지 중 `hook_no_verdict`를 로그에서 세는 한 줄 스크립트를 CI에 둔다 → 훅이 조용히 죽어 보호가 빠진 날을 숫자로 알아챈다
  - `claude -p` 파이프라인 운영자 → 2.1.325로 올린 뒤 `opusplan`·`haiku` 모델 설정에서 서브에이전트 모델이 그대로 유지되는지 한 작업으로 확인한다 → 서브에이전트가 비싼 plan 모델로 몰래 바뀌어 비용이 새던 구멍을 닫는다
  - 사내 프록시·게이트웨이 뒤에서 Claude Code를 쓰는 플랫폼 팀 → 서드파티 게이트웨이에서 컨텍스트 길이 오류로 매 턴 멈추던 건이 고쳐졌으니 해당 게이트웨이 경유 세션 하나를 길게 돌려 본다 → 압축이 제대로 일어나는지 확인해 장애 문의를 줄인다
  - 이 저장소의 루틴 → 설정 점검 도구 묶음에 "SDK 옵션 기본값이 바뀐 곳" 점검 규칙을 더하는 방안을 적어 둔다 → 새 릴리스마다 기본값 변경을 사람이 읽지 않고 기계가 찾는다
  - 개인 개발자 → `claude --version`을 확인해 2.1.325 미만이면 올리고 zstd 보안 수정을 받는다 → 압축 응답을 푸는 쪽 취약점에 노출되는 기간을 줄인다

## 2. Anthropic 11-13 "Building always-on agents" — 항상 켜진 에이전트를 이벤트 인박스·타이머·기억·권한·아웃박스 다섯 부품으로 짓는 설계 글
- 날짜: 2026-11-13
- 출처: https://claude.com/resources/articles/building-always-on-agents
- 요약: 항상 켜진 에이전트는 대부분의 시간을 자다가 이벤트로 깨어 한 번의 "실행(run)"을 하고 기록을 남긴 뒤 다시 잔다. 이벤트 원천은 에이전트를 직접 부르지 않고 내구성 있는 인박스(보통 DB 테이블)에 쓰고, 인박스당 일꾼은 하나만 두며, 출처 식별자로 중복을 거른다. 타이머는 인박스와 다른 저장소에 두고, 스케줄러가 주기적으로 만기 타이머를 찾아 인박스에 이벤트를 넣는 방식이지 실행을 직접 시작하지 않는다. 기억은 일꾼 밖에 따로 두고, 권한은 자격증명을 샌드박스 밖 프록시가 붙이는 구조·auto mode·훅으로 도구 호출 미루기를 권한다.
- 현실 적용:
  - 웹훅으로 깨어나는 PR 리뷰 봇을 만드는 팀 → 웹훅 핸들러가 에이전트를 직접 부르는 대신 SQLite 테이블에 `delivery_id`를 키로 한 행을 쓰게 바꾼다 → GitHub의 재전송 웹훅이 같은 리뷰를 두 번 돌리는 일이 사라진다
  - 알림을 연달아 보내는 개인 비서 에이전트를 가진 개발자 → 사용자 메시지가 짧은 간격으로 3개 들어오면 한 번의 실행으로 묶는 배치 창(예: 10초)을 둔다 → 답장이 3번 오고 서로 엇갈리는 일이 한 번으로 준다
  - 장애 대응 에이전트를 운영하는 SRE 팀 → "30분 뒤 이 알람이 풀렸는지 확인"을 에이전트가 스스로 거는 follow-up 타이머로 만들어 타이머 저장소에 쓰게 한다 → 에이전트 프로세스가 재시작돼도 확인이 사라지지 않는다
  - 일꾼을 두 대 띄워 둔 플랫폼 팀 → 인박스당 활성 일꾼 하나를 보장하는 잠금(임대 시간 포함)이 있는지 시험한다 → 같은 이벤트를 두 일꾼이 동시에 처리해 답이 이중으로 나가는 사고를 막는다
  - 이 저장소의 루틴 → 매일 도는 `/daily-lab`을 "시간표가 이벤트를 인박스에 넣고 일꾼이 하나씩 꺼내는" 구조의 연습 재료로 쓰는 작은 CLI를 만든다 → 실패한 날을 다시 돌릴 때 같은 날을 두 번 처리하지 않는지 시험으로 고정한다
  - 사내 보안 담당 → 인박스 핸들러는 빨리 확인 응답만 하고 프롬프트 인젝션 검사는 실행 안에서 하라는 권고를 체크리스트에 옮긴다 → 웹훅 응답 지연으로 원천이 재전송 폭주하는 일을 막는다

## 3. Anthropic 11-12 "Using Claude Opus 5.5 as your daily driver for knowledge work" — 효과 수준 기본 Medium, 모델을 올리기 전에 효과 수준부터 올리라는 권고
- 날짜: 2026-11-12
- 출처: https://claude.com/resources/articles/using-claude-opus-5-5-as-your-daily-driver-for-knowledge-work
- 요약: Pro·Max·Ultra·Team 플랜에서 Opus 5.5가 기본 모델이라는 전제로 쓰는 법을 정리한 글이다. 효과 수준(effort)은 기본 Medium으로 시작하고, 막힐 때만 High로 올리며, 결과가 아쉬우면 모델을 바꾸기 전에 효과 수준을 먼저 올리라고 한다. 글의 평가에서 Medium의 Opus 5.5가 High의 Opus 5를 맞먹거나 넘었다고 하며, "깊게 생각해 줘" 같은 문구는 빼는 쪽이 첫 답이 빨랐다고 한다. 모델 선택은 Haiku 5.5=짧은 조회·대량 작업, Sonnet 5.5=범위가 분명한 작업, Fable 5.2=가장 어렵고 긴 작업을 Opus로 먼저 시도한 뒤에만 쓰는 것으로 나눈다.
- 현실 적용:
  - Claude Code로 하루 종일 일하는 개발자 → `/model`에서 effort가 Medium인지 확인하고 지난주 High로 두던 작업 한 개를 Medium으로 다시 돌려 비교한다 → 같은 품질에 쓰는 토큰과 한도 소모를 줄인다
  - 프롬프트 템플릿을 공유하는 팀 → 템플릿에서 "think hard"·"think carefully" 문구를 `grep -rn "think hard"`로 찾아 지우고 첫 응답 시간을 전후로 잰다 → 효과 없는 문구를 걷어 응답이 빨라지는지 숫자로 본다
  - 에이전트 파이프라인 비용을 보는 플랫폼 팀 → 단계별 모델 설정표를 만들어 "Haiku 5.5 → Sonnet 5.5 → Opus 5.5 → Fable 5.2" 순서로 올라가는 승격 규칙을 코드에 쓴다 → 비싼 모델을 처음부터 쓰는 호출이 줄어든다
  - 매주 보고서를 쓰는 기획자 → 첫 메시지에 목표·완성물·"어디서 멈추고 물어볼지"를 한 번에 적는 3줄 틀을 만들어 다음 보고서에 쓴다 → 되묻기 왕복이 줄어든다
  - 이 저장소의 루틴 → `/daily-lab`의 모델 호출 기본값(`--effort low`)이 작업별로 적절한지 effort 레인 실험(`effort-race`)을 새 모델 기준으로 다시 돌릴 후보로 적어 둔다 → 모델이 바뀔 때 기본값이 낡지 않게 한다
  - 디자인 시안을 부탁하는 개인 → "피할 스타일"을 구체적으로(크림색 배경, 알약 모양 버튼) 나열해 요청한다 → "뻔한 것 피해 줘" 같은 막연한 요청보다 시안 재작업 횟수가 줄어든다

## 오늘의 선정
- 2번의 "이벤트 인박스" 부품을 만든다. SQLite 한 파일에 이벤트를 쌓고(출처 식별자로 중복 제거), 타이머를 인박스와 별도 테이블에 두고 만기를 이벤트로 바꾸며, 일꾼 잠금(임대)과 배치 창으로 한 번의 "실행"에 묶어 넘기는 CLI `agent-inbox`. 모델·키·네트워크 없이 `--dry-run` 일꾼으로 시험한다.
