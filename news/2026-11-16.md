## 1. dev.to 11-15 "Before you click 'don't ask again'" — "항상 허용"을 누르면 명령이 통째로 `.claude/settings.local.json`에 규칙으로 저장돼, 명령에 적힌 비밀번호도 같이 저장된다
- 날짜: 2026-11-15
- 출처: https://dev.to/roidayan/before-you-click-dont-ask-again-what-your-coding-agent-saves-and-how-to-keep-secrets-out-of-it-j2m
- 요약: 글은 Apiiro 연구진이 11-05에 공개 GitHub 저장소를 훑은 결과를 전한다. `settings.local.json` 사본이 10만 개 넘게 있었고 그중 1,122개에 실제 비밀값(DB 비밀번호·AWS 키 등)이 있었다는 수치다(글이 iTWire 보도를 재인용한 것이라 원 조사는 직접 확인하지 못했다). 원인은 단순하다. 허용 규칙이 곧 명령 문자열이라서 `PGPASSWORD=…`를 붙여 승인하면 비밀번호까지 영구 규칙으로 남는다. 글이 권하는 습관은 명령에 비밀값을 넣지 않기, 비밀 파일 읽기 deny, `settings.local.json`을 `.gitignore`에 넣기, 저장된 규칙을 `/permissions`로 주기적으로 훑기, 푸시 보호 켜기다.
- 현실 적용:
  - 개인 개발자 → 내 저장소들의 `.claude/settings.local.json`에서 `permissions.allow`의 `Bash(...)` 규칙에 `KEY=값` 꼴 인라인 환경변수나 `Authorization: Bearer`가 있는지 스크립트로 한 번 훑는다 → 오래전에 눌러 둔 "항상 허용"에 남은 비밀번호를 커밋 전에 찾아 교체한다
  - 팀 리드 → 팀 저장소에서 `git ls-files .claude/settings.local.json`이 파일을 출력하는지(추적 중인지)와 `.gitignore`에 줄이 있는지를 점검 스크립트로 돌려 결과를 PR 코멘트로 단다 → 로컬 전용 파일이 커밋돼 공개되는 사고를 리뷰 단계에서 막는다
  - 보안 담당 → 사내 저장소 전체에 같은 규칙 점검을 `find … -name settings.local.json`으로 한 번 돌려 건수를 집계한다 → "비밀값이 든 허용 규칙이 몇 곳에 있나"를 숫자로 보고 로테이션 대상을 정한다
  - 이 저장소의 루틴(Routine·Actions에서 매일 도는 `/daily-lab`) → 실행 환경이 만든 `.claude/settings*.json`이 커밋 대상에 섞이지 않았는지 푸시 직전 단계에 점검을 넣는다 → 자동 커밋이 비밀 든 파일을 공개 저장소에 올리는 일을 막는다
  - 신입 온보딩 담당 → 온보딩 문서에 "허용을 누르기 전에 명령에 값이 박혀 있으면 세션 허용으로 바꾼다"는 한 줄과 점검 스크립트 사용법을 넣는다 → 첫 주에 누른 "항상 허용"이 비밀 저장소가 되는 습관을 막는다
  - 유출이 의심되는 사람 → 점검에서 걸린 값을 폐기·재발급하는 순서(먼저 로테이션, 그다음 파일 정리)를 점검 결과 출력 끝에 안내로 붙인다 → 기록을 지우고 안심하는 흔한 실수를 막는다

## 2. dev.to 11-16 "Stop Claude Code from overwriting your .env with a PreToolUse write guard" — 읽기 deny 규칙으로는 막히지 않는 `Write`·`Edit`의 비밀 파일 덮어쓰기를 PreToolUse 훅으로 차단
- 날짜: 2026-11-16
- 출처: https://dev.to/vildandenai/stop-claude-code-from-overwriting-your-env-with-a-pretooluse-write-guard-2n21
- 요약: `Read(./.env)` 같은 deny 규칙은 읽기를 막지만 `Write`·`Edit` 호출이 같은 경로를 만들거나 덮어쓰는 것은 남는다는 지적이다. 해법으로 stdin의 도구 호출 JSON에서 `file_path`를 꺼내 `.env`·`.pem`·`.key`·`id_rsa`·`credentials` 같은 이름이면 exit 2로 막는 짧은 bash 훅을 보인다. 막힌 이유(stderr)는 Claude에게 돌아가 재시도 대신 설명하게 한다. 글 끝은 글쓴이의 설정 모음 홍보다.
- 현실 적용:
  - 개인 개발자 → 위 훅을 `.claude/hooks/`에 두고 `Write|Edit` 매처로 등록한 뒤 `echo '{"tool_input":{"file_path":".env"}}' | bash 훅.sh; echo $?`로 exit 2가 나오는지 확인한다 → 에이전트가 `.env`를 새 예시값으로 덮어써 로컬 설정이 날아가는 일을 막는다
  - 팀 → 훅 패턴 목록이 흔한 이름(`credentials` 등)을 넓게 잡으니, 저장소의 정당한 파일(`credentials.md`, `key_bindings.ts`)이 오탐되는지 `git ls-files`로 대조하는 테스트를 추가한다 → 훅이 일 잘하는 에이전트를 막아 사람들이 훅을 끄는 일을 막는다
  - 이 저장소의 `read-guard`(10-26) → 읽기 쪽만 있는 가드에 "쓰기 쪽 짝"이 있는지 비교하고 빠진 경로 패턴을 후보로 적는다 → 읽기·쓰기 가드 사이의 빈틈이 줄어든다
  - 보안 담당 → 훅이 `Bash`의 `echo … > .env`·`sed -i .env` 같은 우회까지 막는지 확인하는 우회 시험 목록(5개)을 만든다 → `Write`만 막고 셸로 같은 일을 하는 구멍을 알아낸다
  - 서브에이전트를 쓰는 팀 → 서브에이전트에도 같은 훅이 적용되는지 한 번 돌려 본다 → 메인 세션만 막히고 위임된 작업은 통과하는 경로를 배포 전에 안다
  - 훅을 처음 쓰는 사람 → 훅이 `jq`가 없는 환경에서 `path`가 빈 문자열이 되어 아무것도 막지 않고 조용히 통과하는지 확인한다 → 의존 도구가 없을 때 가드가 열려 버리는 사고를 막는다

## 3. dev.to 11-15 "Claude Office Party Enables Linux Code Execution" — 공식 DOCX·PPTX·XLSX 스킬의 헬퍼가 고정된 임시 경로의 `.so`를 검증 없이 불러와 코드가 실행될 수 있다는 AIR Security 보고
- 날짜: 2026-11-15
- 출처: https://dev.to/randomchaos/claude-office-party-enables-linux-code-execution-41h
- 요약: 글에 따르면 AIR Security가 "Office Party"라 이름 붙인 문제는 Anthropic의 문서 처리 스킬이 LibreOffice를 띄우는 `soffice.py`에 있다. 소켓을 못 여는 환경에서는 `LD_PRELOAD` 우회로 공유 라이브러리 `lo_socket_shim.so`를 공용 임시 디렉터리에서 찾아 쓰는데, 그 파일이 어디서 왔는지 확인하지 않아 공격자가 미리 심으면 문서 변환 때 실행된다. 보고자는 다른 스킬이 그 경로에 파일을 풀어 두는 연쇄도 시연했다. Anthropic은 5월에 제보를 받고 샌드박스 안에서만 도는 코드라 보안 경계 밖이라 본다고 하며, 헬퍼는 그대로라고 글은 전한다(보고자 측 주장이라 Anthropic 쪽 입장은 직접 확인하지 못했다).
- 현실 적용:
  - Claude Code에 Anthropic 문서 스킬을 설치한 개발자 → 설치된 스킬 폴더에서 `grep -rn 'LD_PRELOAD\|/tmp/' ~/.claude/skills .claude/skills`로 고정 임시 경로와 `LD_PRELOAD` 쓰는 스크립트를 찾는다 → 내 컴퓨터에서 같은 패턴이 어디에 있는지 오늘 바로 안다
  - 팀 스킬 저장소 리드 → PR 체크에 "스킬 스크립트가 `/tmp` 아래 고정 이름 파일을 읽어 로드·실행하는가"를 `grep`으로 알리는 단계를 넣는다 → 예측 가능한 경로를 실행 입력으로 쓰는 스킬이 리뷰 없이 들어오지 않는다
  - 이 저장소의 `skill-lint`(10-23)·`skill-gate`(11-15) → 위험 패턴 목록에 `LD_PRELOAD`와 "고정 `/tmp` 경로에서 로드"를 후보 규칙으로 적는다 → 스킬 점검이 쓰기·권한 외에 로드 경로도 보게 된다
  - 공용 개발 서버·CI 러너를 쓰는 플랫폼 팀 → 러너의 `/tmp`가 사용자 간 공유인지 확인하고 스킬 실행 때 사용자별 `TMPDIR`을 지정하는 설정을 시험한다 → 한 사용자가 심은 파일이 다른 사용자의 에이전트 실행으로 이어지는 길을 닫는다
  - 보안 담당 → 스킬이 서로의 임시 파일을 읽을 수 있다는 "스킬 조합" 위협을 위협 모델 문서에 한 항목으로 추가한다 → 개별 스킬만 보던 승인 절차가 조합 위험도 묻게 된다
  - 개인 사용자 → 신뢰하지 않는 스킬을 설치하기 전에 스크립트가 쓰는 임시 파일 이름을 `ls -la /tmp`와 비교해 이미 같은 이름이 있는지 본다 → 심어 둔 파일을 실행 전에 발견한다

## 오늘의 선정
- 1번 "항상 허용" 규칙에 비밀값이 저장되는 문제로 **`rule-leak`**를 만든다: `.claude/settings.local.json`·`settings.json`의 `permissions.allow`/`deny` 규칙 문자열에서 인라인 환경변수 비밀번호, Bearer 토큰, 알려진 키 패턴을 찾고, 파일이 git에 추적되는지·`.gitignore`에 있는지를 함께 보고한다. 비밀값은 마스킹해서만 출력하고 모델·키 없이 돈다.
