## 1. Claude Enterprise에 스마트 리포트·앱 내 설문·그룹 공동 월 예산 정식 출시 — 팀 대화 기록을 표본 추출해 워크스트림·지출·막힌 지점을 정리하고, 한도는 그룹 풀과 개인 상한 중 먼저 바닥나는 쪽이 적용된다
- 날짜: 2026-10-28
- 출처: https://claude.com/resources/articles/smart-reports-surveys-pooled-budgets
- 요약: Claude Enterprise 관리자는 팀·기간·제품을 골라 스마트 리포트를 만들 수 있다. Claude가 대화 기록을 표본 추출해 작업을 워크스트림으로 묶고 지출, 산출물, 커넥터 부재·도구 호출 실패 같은 마찰을 보여 주며, 끝에는 스킬로 바꿀 만한 반복 워크플로 같은 권고가 붙는다. 앱 내 설문은 답장 뒤 짧은 카드로 시간 절감·공유할 팁을 묻고 스프레드시트로 내보낼 수 있다. 공동 예산은 그룹에 월 예산 하나를 주고, 모든 요청이 그룹 예산과 개인 한도 양쪽에 차감되어 먼저 닿는 쪽에서 멈춘다. 예산 50·75·95·100%에서 알림 메일이 간다.

## 2. Claude Code 샌드박스 모드 설정 정리 — Bash 쓰기·네트워크만 막고, 읽기·내장 도구·훅·MCP는 막지 않는다. 무인 작업용 엄격 설정은 `failIfUnavailable`·`allowUnsandboxedCommands: false`·자격 증명 deny
- 날짜: 2026-10-28
- 출처: https://dev.to/aobaworks/claude-code-sandbox-mode-exact-config-and-what-it-blocks-309p
- 요약: 샌드박스는 Claude가 실행하는 Bash 명령의 파일 쓰기와 네트워크 목적지를 OS 수준에서 제한한다. 기본값에서는 `~/.ssh`·`~/.aws/credentials` 읽기를 막지 않고, Read·Edit 같은 내장 도구와 훅·로컬 MCP 서버는 샌드박스 밖에서 전체 권한으로 돈다. 무인 작업용으로는 샌드박스를 못 띄우면 시작 단계에서 실패하게 하고, 실패 시 샌드박스 밖 재시도를 끄고, 자격 증명 파일·환경 변수를 `deny`로 두라고 권한다. `strictAllowlist` 같은 키는 프로젝트 설정에서는 무시되고 사용자·관리·CLI 설정에서만 효력이 있다.
- 현실 적용:
  - 밤새 Claude Code를 돌리는 개인 개발자 → `~/.claude/settings.json`에 `sandbox.failIfUnavailable: true`와 `allowUnsandboxedCommands: false`를 넣고 `claude -p "echo ok"`를 bwrap 없는 환경에서 돌려 시작 실패를 본다 → 샌드박스가 꺼진 채 밤새 도는 일을 시작 단계에서 잡는다
  - 서버에 `~/.aws/credentials`가 있는 머신에서 에이전트를 돌리는 팀 → `sandbox.credentials.files`에 해당 경로를 `deny`로, `permissions.deny`에는 `Read(~/.aws/**)`를 같이 넣고 `cat ~/.aws/credentials`와 Read 도구 양쪽이 모두 막히는지 시험한다 → 한쪽만 막아 다른 경로로 새는 일을 피한다
  - 프로젝트 `.claude/settings.json`에 `network.strictAllowlist: true`를 넣어 둔 레포 → 그 키는 프로젝트 설정에서 무시되므로 사용자 설정으로 옮기고 허용 도메인을 패키지 저장소 두세 곳으로 줄인다 → 설정은 있는데 효력이 없는 상태를 없앤다
  - `excludedCommands`에 `docker *`나 `bash *`를 넣어 둔 팀 → 패턴을 `docker compose up *`처럼 좁히거나 컨테이너 안에서 에이전트를 돌리는 쪽으로 옮긴다 → 제외 명령이 샌드박스 전체의 구멍이 되는 것을 막는다
  - 이 저장소의 `mod-audit`(10-18)·`disaster-guard`(10-10) 옆 → 샌드박스 설정 자체를 위 기준으로 점검하는 린트를 하나 둔다 → 설치·행동 단계 점검에 비어 있던 "샌드박스 설정 점검"을 채운다

## 3. 권한 프리셋 3종(엄격·균형·자율)과 어느 쪽도 못 닫는 틈 — 규칙은 명령 접두사로만 맞춰서 `Bash(git:*)` 아래에서 `git push --force`도 통과하고, `Read` 거부 규칙은 Bash의 `cat .env`를 막지 않는다
- 날짜: 2026-10-28
- 출처: https://dev.to/luijhy_michaelguerraflo/3-permission-presets-for-claude-code-strict-balanced-autonomous-and-the-gap-none-of-them-close-4pn8
- 요약: 글쓴이는 `.claude/settings.json`에 둘 권한 프리셋을 셋 제시한다. 엄격은 기본 모드에 읽기 전용 git만 허용하고 `curl`·`wget`·`WebFetch`를 막으며, 균형은 `acceptEdits`에 린트·테스트를 허용하고, 자율은 git·npm·`WebFetch`까지 열되 `.env`와 `secrets` 읽기는 막는다. 규칙은 거부 → 확인 → 허용 순으로 평가된다. 틈은 접두사 매칭이라 안전한 `git push`와 파괴적인 `git push --force`를 구별하지 못하고, Read 거부가 셸의 `cat .env`를 막지 못한다는 점이다. 이를 PreToolUse 훅으로 `exit 2`를 내어 막으라고 권한다.
- 현실 적용:
  - 허용 규칙에 `Bash(git:*)`나 `Bash(npm:*)`를 넣어 둔 개인 개발자 → `permissions.allow`를 전부 읽어 접두사 하나가 파괴적 하위 명령(`push --force`, `reset --hard`, `clean -fd`)까지 덮는지 표로 뽑는다 → 편해서 넣은 한 줄이 열어 둔 범위를 눈으로 본다
  - `Read(.env)`만 거부해 둔 팀 → `permissions.deny`의 `Read(...)` 항목마다 같은 경로를 셸로 읽는 `Bash(cat ...)`·`Bash(less ...)`가 막혀 있는지, 샌드박스 `denyRead`가 겹치는지 대조해 빠진 짝을 찾는다 → Read 도구는 막고 셸로는 읽히는 구멍을 닫는다
  - 새 레포에 처음 프리셋을 입히는 팀 → 엄격 프리셋으로 시작해 일주일 동안 확인 창이 뜬 명령을 기록하고, 3번 넘게 나온 안전한 것만 균형 프리셋으로 옮긴다 → 허용 목록을 추측이 아니라 실제 쓰임으로 키운다
  - 던져 버릴 브랜치에서 자율 프리셋을 쓰는 사람 → 자율 프리셋 옆에 `--force`·`reset --hard`를 막는 PreToolUse 훅 한 개를 같이 넣고 `git push --force`가 막히는지 확인한다 → 브랜치를 잃는 사고를 허용 규칙을 건드리지 않고 막는다
  - 이 저장소의 `agent-scope-lint`(10-12)·`mcp-rule-audit`(10-17) 계열 → 같은 방식으로 `permissions` 규칙끼리의 포함·우회 관계를 정리하는 점검을 후속으로 쓴다 → 규칙 파일이 서로 모순되는 곳을 한 번에 본다

  - 이 저장소의 `claude-tamagotchi`(10-10) 같은 단일 HTML 실험 → 플레이테스트 중 퀘스트가 막히는 버그를 자동으로 찾는 에이전트 스크립트를 후속으로 쓴다 → 사람이 직접 한 판씩 해 보는 시간을 줄인다

## 5. 에이전트가 Supabase를 고르는 이유 (latent.space 대담) — 로컬 환경 마찰 제거, Git에 두는 선언형 스키마, 로그·점검 도구가 에이전트에게 중요하다. 한 달 약 500만 개 데이터베이스가 만들어진다
- 날짜: 2026-10-28
- 출처: https://latent.space/p/supabase/
- 요약: Supabase 공동 창업자들이 에이전트가 앱 백엔드로 Supabase를 자주 고르는 이유를 설명한다. 사람은 가끔 겪는 환경 설정 마찰이 환경을 반복해서 만들고 테스트하는 에이전트에게는 계속 걸림돌이 되므로 이를 줄이는 것이 핵심이라고 한다. Docker 없이 도는 로컬 런타임(알파)과, 긴 마이그레이션 이력 대신 원하는 상태를 파일로 두는 선언형 스키마를 소개한다. 모델이 SQL을 돌릴 수 있어도 데이터 내용과 실패 원인을 알아야 하므로 로그·점검 도구가 필요하다고도 한다.
- 현실 적용:
  - 에이전트에게 데이터베이스 변경을 시키는 개인 개발자 → 마이그레이션 파일을 쌓는 대신 "원하는 스키마" SQL 파일 하나를 레포에 두고 에이전트에게 그것만 고치게 한 뒤 diff로 변경 의도를 본다 → 수십 개 마이그레이션을 읽지 않고도 현재 상태를 안다
  - 신입이 DB 환경을 맞추느라 하루를 쓰는 팀 → 레포 루트에 `make db-up` 한 명령으로 로컬 DB와 시드 데이터를 띄우는 스크립트를 두고 에이전트에게 "이 명령만 써라"고 지침에 적는다 → 환경 설정 마찰로 에이전트가 헤매는 횟수를 줄인다
  - 에이전트가 실패한 쿼리의 원인을 못 찾는 워크플로 → 실패 쿼리와 최근 로그 20줄을 파일로 떨궈 주는 훅을 달아 다음 턴에 읽게 한다 → 에이전트가 "무엇이 실패했는지"를 추측하지 않고 읽는다
  - 스타트업 백엔드를 고르는 창업자 → 같은 요구사항 한 문장을 두 후보 서비스에 대해 에이전트에게 시켜 "처음 동작하는 앱까지 걸린 턴 수"를 비교한다 → 문서의 인기가 아니라 에이전트 친화도로 고른다
  - 이 저장소의 `dir-trust`(10-28) → 선언형 스키마 파일(`schema.sql`)에 `DROP`·`GRANT ALL` 같은 위험 줄이 새로 생겼는지 diff를 잡는 규칙을 후속으로 쓴다 → 에이전트가 고친 스키마의 위험 변경을 커밋 전에 걸러낸다
