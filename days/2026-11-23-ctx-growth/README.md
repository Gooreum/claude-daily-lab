# ctx-growth

> Claude Code 대화 기록에서 "컨텍스트가 무엇 때문에 커졌나"를 생각 몫·보이는 몫으로 가르는 CLI.

## 1. 무엇을 만들었나

CLI 스크립트(`ctx_growth.py`, 표준 라이브러리만). `~/.claude/projects/**/*.jsonl`을 읽어 요청별 점유량(`input + cache_read + cache_creation`)의 인접 증가를 구하고, 거기서 눈에 보이는 바이트(출력 텍스트·도구 호출 입력·사용자 입력·도구 결과)를 토큰으로 환산해 빼, 남는 몫을 "생각 몫"으로 보고한다. 같은 기록에서 (a) 쌍별 중앙값, (b) 합계 기준, (c) 출력 토큰 기준 교차 점검, (d) 블록 바이트만 센 순진한 방법, (e) 환산 계수 민감도를 한 화면에 놓아 비교한다. 네트워크·모델 호출은 없다.

## 2. 왜 만들었나

- 계기: dev.to 11-22 sungwoo_lee, "Claude Code Context Growth: Thinking Tokens Took 47-70%" — https://dev.to/sungwoo_lee_e0f26be4a29fd/claude-code-context-growth-thinking-tokens-took-47-70-31ll
- 글쓴이는 컨텍스트 증가의 가장 큰 몫이 도구 출력이 아니라 생각 토큰(세 프로젝트에서 70.2%·46.8%·57.3%)이라고 하고, 생각 블록은 기록에 서명만 남아 바이트를 세면 틀린다며 처음 낸 표 세 개를 철회했다. 방법(requestId 중복 제거 → 점유량 차이 → 보이는 바이트 차감 → 쌍별 중앙값)이 짧고 검증 가능해서 직접 구현해 볼 만했다.
- 기존 `cache-break`·`cost-top`은 캐시 재작성과 비용을 보지만 컨텍스트가 커지는 원천은 가르지 않는다.

## 3. 어떻게 만들었나

1. 글의 방법을 그대로 옮기되, 계수를 하나로 고정하지 않고 `--bpt`와 `--sensitivity`로 열어 두었다. 글이 4.5를 "고른 상수"라고 밝혔기 때문이다.
2. 같은 `requestId`가 여러 줄로 나오므로 요청 단위로 합치고, 한 요청의 블록(text·tool_use·thinking)은 내용이 같은 반복 줄을 한 번만 센다. 사용량은 줄 중 가장 큰 값을 쓴다.
3. 스레드는 (파일, 서브에이전트 id)로 나눈다. 메인과 서브에이전트가 섞이면 점유량이 서로 뒤엉켜 증가가 음수가 되기 때문이다.
4. 증가가 0 이하인 쌍(압축·새 접두)은 건너뛰고 몇 개인지 센다.
5. 글에 없는 교차 점검을 더했다: 이전 응답의 `output_tokens`에서 보이는 출력(바이트/계수)을 뺀 몫. 점유량과 무관한 두 번째 신호라서 두 값이 크게 어긋나면 추정을 의심할 근거가 된다.
6. 순진한 방법(블록 바이트만)은 대조군으로 같이 낸다. 글이 틀렸다고 지적한 바로 그 방법이 얼마나 작게 나오는지 직접 보이기 위해서다.
7. 정답을 손으로 계산한 합성 기록으로 `test.sh`를 짰다. 처음 돌렸을 때 2건이 실패했는데 코드가 아니라 내 손계산 기대값(합계 기준 0.884 → 실제 3200/4000=0.8, 줄 수 8 → 6)이 틀린 것이어서 기대값만 고쳤다.

## 4. 사용법

```bash
python3 ctx_growth.py                         # ~/.claude/projects 전체
python3 ctx_growth.py ~/.claude/projects/<프로젝트>/<세션>.jsonl
python3 ctx_growth.py ~/.claude/projects --since-days 7 --sensitivity
python3 ctx_growth.py <경로> --bpt 4.5 --min-pairs 5 --top 20
python3 ctx_growth.py <경로> --json
```

종료 코드: 0 정상, 1 쌍이 없음(요청이 둘 이상인 스레드가 없거나 기간 안에 기록 없음), 2 인자·경로 오류.

## 6. 한계와 다음 아이디어

- 비율은 **추정**이다. "남는 몫"은 생각 토큰 + 환산 계수 오차 + 시스템이 덧붙이는 토큰의 합이다. 실제 세션에서 계수만 3→6으로 바꿔도 중앙값이 35%→68%로 움직였다. 한 숫자를 인용하지 말고 범위로 읽어야 한다. 위 실행에서 출력 기준 교차 점검(70%대)과도 차이가 난다.
- 환산 계수는 한 값이다. 코드·한글·JSON은 바이트당 토큰 수가 다른데 본문 종류별로 나누지 않았다. 다음 단계로 종류별 계수를 두거나 `count_tokens`로 보정할 수 있다.
- 이전 턴의 생각 블록이 다음 요청에서 컨텍스트에 남는지는 모델·설정에 따라 다르다. 남지 않는 경우엔 생각이 점유량 증가에 안 잡히고 출력 기준 점검에만 드러난다. 이 도구는 그 구분을 하지 않는다.
- 도구 결과가 이미지·바이너리면 바이트 환산이 크게 어긋난다. 이미지는 따로 세는 편이 낫다.
- 확인한 실제 기록은 이 세션 하나뿐이라 글의 70.2%·46.8%·57.3%와 비교할 만한 표본이 아니다. 여러 세션·프로젝트로 돌려 보는 것이 다음 숙제다.
- 아이디어: effort low/high로 같은 프롬프트를 돌려 두 기록을 `--json`으로 비교하는 모드.
